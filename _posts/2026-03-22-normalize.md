서비스를 운영하고 유지보수를 담당하는 과정에서는 예상하지 못한 이슈들이 반복적으로 발생합니다.
장애 대응이나 급한 요구사항 반영을 위해 임시적인 처리가 필요한 경우도 많습니다.

이러한 상황이 반복되면 데이터 처리 기준이 점점 느슨해지고,
하나의 서비스 내에서도 기능마다 데이터를 처리하는 방식이 달라지게 됩니다. 같은 데이터를 어떤 곳에서는 그대로 저장하고,
어떤 곳에서는 가공해서 저장하면서 구현 방식이 분산됩니다. 이 상태가 누적되면 시스템은 일관성을 잃고,
데이터는 빠르게 오염됩니다.

한 번 오염된 데이터를 정제하는 것은 쉽지 않습니다.
운영 초기에는 가능할 수 있지만, 장기간 운영된 서비스에서는 사실상 매우 어렵습니다.

시간이 흐르면서 서비스는 확장되고,
유입되는 데이터의 양과 형태도 더욱 다양해집니다. 이 과정에서 데이터 오염은 더 빠르게 확산됩니다.

따라서 문제를 사후에 해결하려 하기보다,
개발 초기부터 입력값에 대한 명확한 통제가 필요합니다.

👉 **입력값 통제는 사후 대응이 아니라, 시스템의 품질을 결정하는 초기 설계 기준입니다.**


---

## 1. 입력값 통제가 없는 경우 발생하는 문제

### 1.1. 동일한 데이터가 서로 다른 형태로 저장

입력 데이터에 대한 기준이 없으면,
같은 의미를 가진 데이터라도 서로 다른 형태로 저장됩니다.

예를 들어 전화번호는 다음과 같이 다양한 형태로 입력될 수 있습니다.

* 010-1234-5678
* 01012345678
* 010 1234 5678

겉보기에는 동일한 값이지만, 그대로 저장되면
시스템에서는 서로 다른 데이터로 인식됩니다.

이러한 상태가 누적되면 다음과 같은 문제가 발생합니다.

* 동일 데이터를 하나로 식별할 수 없음
* 중복 데이터 증가
* 조회 결과의 일관성 저하

### 1.2. 검증 없이 잘못된 데이터가 저장

입력값에 대한 검증이 없다면,
시스템은 잘못된 데이터도 정상 데이터로 받아들이게 됩니다.

예를 들어 다음과 같은 상황이 발생할 수 있습니다.

* 전화번호 컬럼에 이름과 같은 관련 없는 값이 저장되는 경우
* 데이터 형식이 맞지 않는 값이 그대로 저장되는 경우
* 필수 컬럼에 값이 null로 저장되는 경우

이러한 데이터가 누적되면, 다음과 같은 문제가 발생합니다.

* 데이터에 대한 신뢰도 저하
* 잘못된 조회 결과나 분석 결과가 발생
* 비즈니스 로직의 결함 원인으로 작용

이 두 가지 문제는 개별적으로 발생하기도 하지만,
대부분 복합적으로 나타나면서 데이터를 오염시키고 서비스 품질을 빠르게 악화시킵니다.

이러한 문제는 시간이 지날수록 자연스럽게 해결되지 않으며,
입력값 통제가 없는 상태에서는 지속적으로 누적될 수밖에 없습니다.

---

## 2. 해결의 출발점: 입력값 통제

앞에서 살펴본 두 가지 문제의 공통 원인은, 입력값을 통제하는 기준이 없다는 점입니다.

입력값 통제란, 시스템이 받아들일 수 있는 데이터의 형태와 유효성을 사전에 정의하고,
그 기준에 맞는 데이터만 저장하도록 제한하는 것을 의미합니다.

시스템이 어떤 형태의 데이터를 받아들이고,
어떤 데이터를 허용하지 않을지에 대한 명확한 기준이 없다면
데이터 품질은 시간이 지날수록 자연스럽게 무너지게 됩니다.

이 문제를 해결하기 위한 출발점은 입력 시점에서 데이터를 통제하는 것입니다.

그 핵심이 바로 다음 두 가지입니다.

* 정규화 (normalize)
* 검증 (validate)

입력값 통제는 결국,
정규화와 검증을 통해 시스템이 허용할 수 있는 데이터만 받아들이도록 만드는 과정입니다.

👉 **즉, 시스템의 데이터 품질을 결정하는 첫 번째 관문입니다.**

### 2.1. 정규화(Normalize)

정규화는 입력된 데이터를 **일관된 형태로 변환하는 과정**입니다. 같은 의미를 가진 데이터가 서로 다른 형태로 저장되지 않도록,
하나의 기준으로 통일하는 역할을 합니다.

예를 들어 전화번호를 다음과 같이 변환할 수 있습니다.

```text
010-1234-5678 → 01012345678
```

이처럼 데이터의 표현 방식을 통일하면,

* 동일 데이터를 정확하게 식별할 수 있고
* 중복 데이터 발생을 방지할 수 있으며
* 조회 결과의 일관성을 유지할 수 있습니다

정규화는 데이터의 **“표현을 통제”**하는 역할을 합니다.

### 2.2. 검증(Validate)

검증은 입력된 데이터가 **정상적인 값인지 확인하는 과정**입니다. 정규화가 “형태를 맞추는 것”이라면,
검증은 “유효한 값인지 판단하는 것”입니다.

일반적으로 다음과 같은 항목을 확인합니다.

* 길이 및 형식 검증
* 허용 가능한 값 범위 확인
* 필수값 존재 여부 확인

검증이 없다면 잘못된 데이터도 그대로 저장되기 때문에,
데이터의 신뢰도를 유지할 수 없습니다.

검증은 데이터의 **“유효성을 통제”**하는 역할을 합니다.

## 3. 올바른 데이터 처리 흐름

정규화와 검증은 순서가 중요합니다.

입력 데이터는 반드시 다음과 같은 흐름으로 처리되어야 합니다.

```text
입력값
  ↓
정규화 (normalize)
  ↓
검증 (validate)
  ↓
저장
```

먼저 데이터를 일관된 형태로 변환한 뒤,
그 값이 유효한지 검증해야 합니다.

이 순서가 뒤바뀌거나 생략되면,
앞에서 살펴본 문제들이 다시 발생하게 됩니다.

정규화와 검증은 선택적인 기능이 아닙니다. 시스템이 데이터를 받아들이기 위한 최소한의 기준입니다.

이 기준이 없다면,

* 데이터는 계속 오염되고
* 기능은 점점 복잡해지며
* 시스템은 점점 수정하기 어려운 구조로 변하게 됩니다

---

## 4. 마무리

데이터 품질은 저장 이후에 개선되는 것이 아니라, 입력 시점에서 결정됩니다. 정규화와 검증은 작은 구현처럼 보이지만, 서비스 전체의 품질을 좌우하는 핵심 설계입니다. 입력값 통제가 없는 서비스는 결국 데이터가 아니라 문제를 축적하게 됩니다.
