## 스프링 애플리케이션에서 설정의 출발

스프링 애플리케이션에서 설정을 다룰 때, 그 출발점은 application.properties 또는 application.yaml 파일입니다.
이 파일들이 애플리케이션에 제공할 설정 정보를 포함하고 있기 때문입니다.

**application.properties 예시**
```bash
feature.logging.enabled=true
external.api.timeout=3000
```

**application.yaml 예시**
```bash
feature:
  logging:
    enabled: true

external:
  api:
    timeout: 3000
```

두 파일은 표현 방식만 다를 뿐, 스프링 입장에서는 동일한 설정 정보를 가지고 있습니다. 프로젝트의 특성이나 팀의 선호에 따라서 선택해서 사용하면 됩니다. 개인적으로는 설정의 개수가 늘어나고, 복잡한 계층 구조를 가지는 설정을 표현하는 경우에는
application.yaml을 사용하는 것이 조금 더 읽기 쉽다고 느껴졌습니다.

## 스프링에서 설정을 다루는 가장 간단한 방법, @Value

설정 구조가 간단하다면 `@Value` 어노테이션을 사용해서 매우 직관적이고 편리하게 처리할 수 있습니다. 

@Value 어노테이션의 사용 방법은 다음과 같습니다. 
> @Value(${키:기본값})

설정 파일(`application.properties` 혹은 `application.yaml`)에서 external.api.timeout에 해당되는 값을 가져와서 설정해야 한다면 아래처럼 코드를 작성하면 됩니다.
    
```java
@Value("${external.api.timeout:3000}")
private int timeout;
```

external.api.timeout에 해당하는 값이 존재하지 않다면 기본값으로 정의된 3000이 주입됩니다.

## @Value의 한계

하지만 설정의 구조가 점점 복잡해질수록, @Value 어노테이션만으로 설정을 관리하는 데에는 한계가 드러나기 시작합니다. 그 이유를 예제 코드와 함께 설명해보도록 하겠습니다.

**application.yaml**
```bash
external:
  api:
    url: https://example.com
    timeout: 3000
    retry:
      count: 3
```

1️⃣ 설정과 관련된 코드의 분산

위의 설정 파일('application.yaml')에는 external.api라는 단위 기능 영역에 대한 url,timeout,retry.count 속성이 정의되어 있습니다. 하지만 @Value 어노테이션을 사용해 설정 값을 주입하다 보면, 아래와 같이 단위 기능을 구성하는 설정 코드가
여러 클래스에 분산되기 쉽습니다.

```java
@Component
public class ExternalApiClient {

    @Value("${external.api.url}")
    private String apiUrl;

    @Value("${external.api.timeout:3000}")
    private int timeout;
}

@Component
public class ExternalApiRetryPolicy {

    @Value("${external.api.retry.count:3}")
    private int retryCount;
}
```
이렇게 되면, 해당 기능이 어떤 설정들로 구성되어 있는지 구조를 직관적으로 파악하기 어려워집니다. 그리고 설정과 관련된 동작을 이해하기 위해 여러 클래스의 코드를 함께 살펴봐야 하는 상황이 발생하게 됩니다.



이 경우
“외부 API와 관련된 설정이 어떤 것들이 있는지”를 파악하기 위해
여러 클래스의 코드를 함께 살펴봐야 한다는 점이 아쉬운 부분입니다.

설정 값을 주입하는 코드가 분산되면서 


기본 값 자체는 코드에 정의되어 있지만, 왜 이 값이 기본값인지 알기 어렵습니다.
설정 항목들이 서로 어떤 관계를 가지는지에 대한 맥락을 파악하기 어렵습니다.

설정의 의미가 코드에 종속되는 느낌을 받게 되는 지점이기도 합니다.

2️⃣ @Value 선언의 반복

하나의 기능이 여러 설정 값을 필요로 하는 경우,
@Value 선언이 반복적으로 등장하게 됩니다.

```java
@Component
public class FeatureService {

    @Value("${feature.logging.enabled:false}")
    private boolean enabled;

    @Value("${feature.logging.level:INFO}")
    private String level;

    @Value("${feature.logging.masking:false}")
    private boolean masking;
}
```

설정 자체는 하나의 기능(feature.logging)에 속해 있지만,
코드에서는 개별 필드 단위로 분리되어 선언됩니다.

이 구조에서는
해당 기능에 어떤 설정들이 필요한지
한눈에 파악하기 어렵다는 점이 아쉬웠습니다.

3️⃣ 설정의 의미와 기본값이 코드에 분산되는 경우

@Value는 기본값을 함께 정의할 수 있다는 장점이 있지만,
설정이 많아질수록 기본값의 의미가 코드 곳곳에 흩어지게 됩니다.

```java
@Value("${external.api.timeout:3000}")
private int timeout;

@Value("${external.api.retry.count:3}")
private int retryCount;
```

기본값 자체는 코드에 드러나 있지만,
왜 이 값이 기본값인지,
서로 어떤 관계를 가지는지에 대한 맥락은 코드만으로는 파악하기 어렵습니다.

설정의 의미가 코드에 종속되는 느낌을 받게 되는 지점이기도 합니다.

4️⃣ 설정 구조가 코드에 잘 드러나지 않는 경우

application.yaml에서는 계층 구조로 설정을 표현할 수 있지만,
@Value를 사용하는 경우
이 구조가 코드에서는 자연스럽게 드러나지 않습니다.



위와 같은 설정 구조가 있더라도,
코드에서는 각각의 값을 개별적으로 꺼내 사용하는 형태가 됩니다.

@Value("${external.api.url}")
private String apiUrl;

@Value("${external.api.timeout}")
private int timeout;

@Value("${external.api.retry.count}")
private int retryCount;


설정 파일에서는 구조가 보이지만,
코드에서는 그 구조를 그대로 표현하기 어렵다는 한계가 있습니다.



이 경우
“외부 API 관련 설정이 어떤 것들이 있는지”를 파악하려면
설정 파일뿐만 아니라 여러 클래스의 코드를 함께 확인해야 합니다.


시작하면 @Value 방식으로는 한계가 있습니다.

* 설정 값이 여러 클래스에 흩어져 관리되기 쉽습니다.
* 하나의 기능을 위해 여러 개의 @Value 선언이 필요해질 수 있습니다.
* 설정 간의 관계나 묶음이 코드상에서 잘 드러나지 않습니다.

이러한 구조에서는 설정 자체를 한눈에 파악하기보다는,
코드를 따라가며 설정을 이해해야 하는 경우가 많아집니다.

설정이 단순한 값의 모음을 넘어
기능의 동작 방식이나 범위를 결정하기 시작하면,
설정을 보다 구조적으로 관리할 필요성이 생깁니다.

특히 다음과 같은 경우에는
@Value 방식만으로는 관리가 점점 부담스러워질 수 있습니다.

기능 단위로 여러 설정 값이 함께 사용되는 경우

설정의 기본값이나 의미를 한곳에서 확인하고 싶은 경우

설정 구조가 변경될 가능성이 있는 경우

이러한 상황에서는
설정을 개별 값이 아닌,
하나의 의미 있는 묶음으로 다루는 방식이 필요해집니다.

MVP(Minimum Viable Product) 수준으로 구현된 애플리케이션이라면 설정 구조가 단순해서 @Value 어노테이션만 사용해도 충분할 수 있습니다. 하지만 시간이 지나면서 많은 기능이 추가되고, 점점 설정 구조가 복잡해지면 한계에 부딪힐 수 있습니다.
