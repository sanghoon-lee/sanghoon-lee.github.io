## 애플리케이션 설정

애플리케이션 설정은 애플리케이션의 동작을 규정하는 값을 외부에서 정의하고, 이를 실행 시점에 주입하는 절차를 의미합니다. 또한, 애플리케이션이 어떻게 동작해야 하는지를 결정하는
기준을 정의하는 과정으로 볼 수도 있습니다.

**예시) 애플리케이션 설정으로 주입되는 값**

1. 외부 연동
    * API URL
    * 타임아웃 값
    * 연결 재시도 횟수
2. 기능 동작
    * 특정 기능의 활성화 여부
    * 기능별 동작 옵션
3. 환경 정보
    * 개발/스테이징/운영 환경별 구동 정보
    * 로그 레벨
    * 임계값(threshold)

이러한 값들은 코드 내부에 직접 정의하기보다는,
애플리케이션 외부에서 정의하고 실행 시점에 주입하는 방식으로
관리하는 것이 일반적입니다. 환경이나 정책이 변경되더라도
코드의 변경없이 유연하게 대응하기 위함입니다.

## 스프링에서 애플리케이션 설정의 출발점

스프링에서 `application.properties` 또는 `application.yaml` 파일은 애플리케이션 설정의 출발점입니다. 스프링으로 개발된 애플리케이션은 구동되면서, 이 파일을 로딩하고 설정에서 주입할 값을 가져오기 때문입니다.

**예시) application.properties**
```bash
feature.logging.enabled=true
external.api.timeout=3000
```

**예시) application.yaml**
```bash
feature:
  logging:
    enabled: true

external:
  api:
    timeout: 3000
```

두 파일은 표현 방식만 조금 다를 뿐, 동일한 설정 정보를 가지고 있습니다. 프로젝트의 특성이나 팀의 선호에 따라서 선택해서 사용하면 됩니다. 다만, 개인적으로는 설정의 개수가 늘어나고 복잡한 계층 구조를 가지는 설정을 표현하는 경우에는 
`application.yaml`을 사용하는 것이 조금 더 가독성이 좋게 느껴졌습니다.

## 애플리케이션 설정을 구현하는 가장 간단한 방법, @Value

`@Value` 어노테이션을 사용하면 매우 직관적이고, 간편하게 애플리케이션 설정을 구현할 수 있습니다. `application.properties` 또는 `application.yaml` 파일에 정의된 속성의 키와 코드 내부에서 선언된 변수를 직접 연결해 주기 때문입니다.

사용 방법은 다음과 같습니다. 
> @Value(${키:기본값})

예를 들어, external.api.timeout 속성의 값을 timeout이라는 변수에 주입하고 싶으면 아래와 같이 코드를 작성하면 됩니다. 이때, 속성의 값이 정의되어 있지 않으면 기본값으로 지정된 3000이 주입됩니다.
    
```java
@Value("${external.api.timeout:3000}")
private int timeout;
```

다음과 같은 상황에서는 `@Value` 어노테이션을 사용해서 애플리케이션 설정을 구현하는 것이 적합합니다.

* 설정의 개수가 많지 않은 경우
* 설정 구조가 계층적이지 않은 경우
* 단일 값 위주로 주입되는 경우

## @Value의 한계

하지만, 애플리케이션의 규모가 커지고 복잡해지면서 `@Value` 어노테이션은 한계가 드러나게 됩니다.

어떤 애플리케이션에서 API를 사용하는 외부 시스템과 연동 정보를 설정하기 위해서 url,timeout,retry라는 3개의 속성이 필요하다고 가정해보겠습니다. 

아래처럼 `application.yaml`를 작성할 수 있을 것입니다.

**application.yaml**
```bash
external:
    api:
        url: https://example.com
        timeout: 3000
        retry: 3
```

외부 시스템과 연동을 위한 설정 구조가 비교적 명확하게 정의되어 있습니다.

하지만, `@Value` 어노테이션으로 설정을 구현하다보면 아래처럼 설정을 구현하는 코드가 여러 클래스로 흩어지기 쉽습니다.

```java
@Component
public class ExternalApiClient {

    @Value("${api.url}")
    private String apiUrl;

    @Value("${api.timeout:3000}")
    private int timeout;
}

@Component
public class ExternalApiRetryPolicy {

    @Value("${api.retry:3}")
    private int retryCount;
}
```

분명 하나의 단위 기능(외부 시스템과 연동)에 대한 설정이지만,
`ExternalApiClient`와 `ExternalApiRetryPolicy` 클래스에 코드가 나뉘어 구현되어 있습니다. 이렇게 되면, 해당 기능이 어떤 설정들로 구성되어 있는지
코드만 보고 직관적으로 파악하기 어렵습니다. 

즉, **"설정의 구조와 의도가 코드에 자연스럽게 드러나지 않는다."**라는 문제가 나타나게 됩니다. 결국, 나중에 새로운 설정이 추가되거나 구조가 변경되면 대응하기 어려워질 수도 있습니다. 

## 설정을 객체로 묶어 표현하는 방법, @ConfigurationProperties

지금까지 살펴본 것처럼, 설정의 개수가 늘어나고 계층 구조를 가지기 시작하면 @Value 어노테이션만으로는 설정의 구조와 의도를 코드에 명확하게 드러내기 어렵게 됩니다.

이러한 문제의 해결책으로 스프링은 설정을 객체 단위로 묶어서 바인딩할 수 있는 방법을 제공합니다. 이때 사용하는 어노테이션이 바로 @ConfigurationProperties입니다.
