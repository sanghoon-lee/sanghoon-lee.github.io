## 애플리케이션 설정

애플리케이션 설정은 애플리케이션의 동작을 규정하는 값을 외부에서 정의하고, 이를 실행 시점에 주입하는 절차를 의미합니다. 애플리케이션이 어떻게 동작해야 하는지를 결정하는 과정으로 볼 수도 있습니다.

**예시) 애플리케이션 설정으로 주입되는 값**

1. 외부 연동
    * API URL
    * 타임아웃 값
    * 연결 재시도 횟수
2. 기능 동작
    * 특정 기능의 활성화 여부
    * 기능별 동작 옵션
3. 환경 정보
    * 개발/스테이징/운영 환경별 구동 정보
    * 로그 레벨
    * 임계값(threshold)

이러한 값들은 코드 내부에 직접 정의하기보다는 애플리케이션 외부에서 정의하고 실행 시점에 주입하는 방식으로 관리하는 것이 일반적입니다. 환경이나 정책이 변경되더라도 코드의 변경없이 유연하게 대응하기 위함입니다.

## 스프링에서 애플리케이션 설정의 출발점

스프링에서 `application.properties` 또는 `application.yaml` 파일은 애플리케이션 설정의 출발점입니다. 애플리케이션이 구동되면서 설정에서 주입할 값을 이 파일에서 가져오기 때문입니다.

**예시) application.properties**
```bash
feature.logging.enabled=true
external.api.timeout=3000
```

**예시) application.yaml**
```yaml
feature:
  logging:
    enabled: true

external:
  api:
    timeout: 3000
```

두 파일은 표현 방식만 조금 다를 뿐, 동일한 설정 정보를 가지고 있습니다. 프로젝트의 특성이나 팀의 선호에 따라서 선택해서 사용하면 됩니다. 다만, 개인적으로는 설정의 개수가 늘어나고 복잡한 계층 구조를 가지는 설정을 표현하는 경우에는 
`application.yaml`을 사용하는 것이 조금 더 가독성이 좋게 느껴졌습니다.

## 애플리케이션 설정을 구현하는 가장 간단한 방법, @Value

`@Value` 어노테이션을 사용하면 매우 직관적이고, 간편하게 애플리케이션 설정을 구현할 수 있습니다. `application.properties` 또는 `application.yaml` 파일에 선언된 키와 코드 내부에서 선언된 변수를 직접 연결해 주기 때문입니다.

사용 방법은 다음과 같습니다. 
> @Value(${키:기본값})

예를 들어 `application.properties` 또는 `application.yaml` 파일에 선언된 external.api.timeout에 할당된 값을 코드 내부의 timeout에 변수에 주입하고 싶으면 아래와 같이 코드를 작성하면 됩니다. 만약 external.api.timeout에 값이 할당되어 있지 않다면, 기본값으로 선언된 3000이 주입됩니다.
    
```java
@Value("${external.api.timeout:3000}")
private int timeout;
```

## @Value 어노테이션의 한계

아래와 같은 상황에서는 `@Value` 어노테이션으로 애플리케이션 설정을 구현하는 것이 효과적입니다.

* 설정 개수가 많지 않은 경우
* 설정이 단일 값 주입 위주로 구성된 경우
* 설정 구조가 계층적이지 않은 경우

하지만, 애플리케이션의 규모가 커지고 복잡해지면 `@Value` 어노테이션은 한계가 드러나게 됩니다.

@Value 어노테이션의 한계를 설명하기 위해서 API를 사용하는 외부 시스템과 연동 정보를 설정하는 것을 가정해보겠습니다. 이때, 연동 정보는 url,timeout,retry 3개의 속성으로 구성됩니다.

이러한 정보를 바탕으로 `application.yaml` 파일을 아래처럼 작성할 수 있을 것입니다.

**application.yaml**
```yaml
external:
    api:
        url: https://example.com
        timeout: 3000
        retry: 3
```

외부 시스템과 연동을 위한 설정 구조가 `application.yaml` 파일에 비교적 명확하게 정의되었습니다.

그렇지만, 동일한 단위 기능을 구성하는 설정들이 여러 클래스로 흩어져서 구현되기 쉽습니다. 

```java
@Component
public class ExternalApiClient {

    @Value("${external.api.url}")
    private String apiUrl;

    @Value("${external.api.timeout:3000}")
    private int timeout;
}

@Component
public class ExternalApiRetryPolicy {

    @Value("${external.api.retry:3}")
    private int retryCount;
}
```

위의 코드는 `ExternalApiClient` 클래스에서는 url과 timeout을 설정하고, `ExternalApiRetryPolicy` 클래스에서는 retry를 설정하고 있습니다. 이렇게 단위 기능을 구성하는 설정들이 분산되어 있으면 해당 기능이 어떻게 동작하는지 코드만 보고 직관적으로 파악하기 어렵습니다.

설정의 구조와 의도가 코드에 자연스럽게 드러나지 않으면서, 설정이 추가되거나 구조가 변경될수록 유지보수의 부담도 함께 커지게 됩니다.

## 설정을 객체로 묶어 표현하는 방법, @ConfigurationProperties

애플리케이션의 규모가 커서 설정의 개수가 많거나, 계층 구조가 복잡하다면 객체 단위로 묶여서 바인딩하는 방법이 효과적일 수 있습니다. 

스프링에서는 `@ConfigurationProperties` 어노테이션을 사용하면 됩니다. 그렇게 하면 `application.properties` 또는 `application.yaml` 파일에 정의된 설정 구조가 그대로 코드 내부의 필드 구조로 표현될 수 있습니다.

앞에서 사용했던 `application.yaml` 파일의 내용을 다시 한번 살펴보겠습니다.

```yaml
external:
  api:
    url: https://example.com
    timeout: 3000
    retry: 3
```

위의 설정을 객체 단위로 묶어서 바인딩하기 위해서는 `@ConfigurationProperties` 어노테이션으로 클래스를 선언해야 합니다.

```java
@ConfigurationProperties(prefix = "external.api")
public class ExternalApiProperties {

    private String url;
    private int timeout;
    private int retry;

    // getter / setter
}
```

**중요한 포인트**

> prefix = "external.api"은 `application.yaml` 파일의 external.api 하위 설정을 바인딩하도록 요청하는 것을 의미합니다.

`ExternalApiProperties` 클래스만 보면 외부 시스템과 연동을 위해 어떤 설정들이 필요한지 한눈에 파악됩니다. 

이제는 아래 코드처럼 설정이 바인딩된 `properties` 객체를 통해서 코드 내부에 값을 주입할 수 있습니다. 

```java
@Component
public class ExternalApiClient {

    private final ExternalApiProperties properties;

    public ExternalApiClient(ExternalApiProperties properties) {
        this.properties = properties;
    }

    public void call() {
        String url = properties.getUrl();
        int timeout = properties.getTimeout();
        // ...
    }
}

@Component
public class ExternalApiRetryPolicy {

    private final ExternalApiProperties properties;

    public ExternalApiRetryPolicy(ExternalApiProperties properties) {
        this.properties = properties;
    }

    public int retryCount() {
        return properties.getRetry();
    }
}
```

이렇게 하면 설정이 개별 값이 아닌 의미 있는 단위로 묶어 표현되기 때문에, 설정 구조가 복잡해지더라도 유지보수의 부담을 줄일 수 있습니다.

## 다음 포스팅으로 넘어가며...

그 동안은 정말 아무 생각없이 애플리케이션의 설정을 구현하고 있었던 것 같습니다. 공부를 조금 해보니 설정도 애플리케이션 설계의 일부로 보이게 되었습니다.

다음 포스팅에서는 `@EnableConfigurationProperties`과 `@ConditionalOnProperty`를 함께 사용해서 
어떻게 더 유연하게 설정을 구현할 수 있는지를 설명해 보려고 합니다.
