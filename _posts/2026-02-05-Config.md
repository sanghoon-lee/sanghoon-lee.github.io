## 스프링 애플리케이션에서 설정의 출발

스프링 애플리케이션에서 설정을 다룰 때, 그 출발점은 설정 정보를 정의하는 `application.properties` 또는 `application.yaml` 파일입니다.

**application.properties 예시**
```bash
feature.logging.enabled=true
external.api.timeout=3000
```

**application.yaml 예시**
```bash
feature:
  logging:
    enabled: true

external:
  api:
    timeout: 3000
```

두 파일은 표현 방식만 다를 뿐, 스프링 입장에서는 동일한 설정 정보를 가지고 있습니다. 프로젝트의 특성이나 팀의 선호에 따라서 선택해서 사용하면 됩니다. 개인적으로는 설정의 개수가 늘어나고, 복잡한 계층 구조를 가지는 설정을 표현하는 경우에는
application.yaml을 사용하는 것이 조금 더 읽기 쉽다고 느껴졌습니다.

## 스프링에서 설정을 다루는 가장 간단한 방법, @Value

`@Value` 어노테이션을 사용하면 매우 직관적이고, 간편하게 설정 정보를 처리할 수 있습니다. 

사용 방법은 다음과 같습니다. 
> @Value(${키:기본값})

`application.properties` 또는 `application.yaml`에서 external.api.timeout 속성에 할당된 값을 가져와서 사용하려면 아래처럼 코드를 작성하면 됩니다. 해당 속성이 존재하지 않거나 값이 할당되어 있지 않다면, 기본값으로 지정된 3000이 사용될 것입니다.
    
```java
@Value("${external.api.timeout:3000}")
private int timeout;
```

## @Value의 한계

하지만, 설정의 개수가 늘어나면서 계층 구조가 복잡해지면 @Value 어노테이션은 한계가 드러나기 시작합니다.

어떤 애플리케이션에서 API의 동작을 설정하기 위해서 url,timeout,retry라는 3개의 속성이 필요하다고 가정해보겠습니다. 

`application.yaml` 파일을 생성하고, API라는 단위 기능을 통합하는 api라는 속성을 먼저 정의합니다. 그리고 하위 속성으로 url,timeout,retry를 순서대로 정의합니다.

즉, 아래와 같이 `application.yaml`을 작성합니다.
**application.yaml**
```bash
api:
    url: https://example.com
    timeout: 3000
    retry: 3
```

여기까지는 문제가 될만한 부분이 보이지 않습니다. 하지만 @Value 어노테이션으로 애플리케이션의 동작을 설정하는 코드를 작성하다보면, 다음과 같은 문제와 마주칠 수 있습니다.

1️⃣ 설정 코드의 분산

분명 동일한 단위 기능을 구성하는 속성이지만, 값을 가져와서 설정하는 코드가 여러 클래스에 분산되어 구현되기 쉽습니다.

아래 코드가 그런 사례에 해당됩니다. `ExternalApiClient`라는 클래스에서 url과 timeout 속성의 값을 가져와서 설정하는 코드를 구현하고 있지만, retry 속성의 값을 가져와서 설정하는 코드는 `ExternalApiRetryPolicy`라는 클래스에서 구현하고 있습니다.

```java
@Component
public class ExternalApiClient {

    @Value("${api.url}")
    private String apiUrl;

    @Value("${api.timeout:3000}")
    private int timeout;
}

@Component
public class ExternalApiRetryPolicy {

    @Value("${api.retry:3}")
    private int retryCount;
}
```

이렇게 되면 애플리케이션의 동작 방식을 결정하는 설정 구조를 직관적으로 파악하기 어려워지게 됩니다.
