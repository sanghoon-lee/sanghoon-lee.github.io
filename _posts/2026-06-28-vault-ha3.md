지금까지 Vault가 고가용성을 어떤 방식으로 제공하는지 살펴보고, 실제로 3개의 Vault 노드를 이용해 HA 클러스터를 구축해봤습니다.

하지만 클러스터가 구축되었다고 해서 곧바로 고가용성이 검증되었다고 보기는 어렵습니다. Leader 노드에 장애가 발생하더라도 새로운 Leader가 자동으로 선출되고, 서비스가 중단 없이 제공되는지 확인해야 합니다.

그래서 이번 포스팅에서는 Leader 노드를 강제로 종료하여 장애 상황을 재현하고, Leader Election과 Failover가 실제로 어떻게 이루어지는지 단계별로 확인해보겠습니다. 이어서 장애 상황에서도 Vault의 시크릿 조회 기능이 중단 없이 정상적으로 동작하는지 직접 검증해보겠습니다.

---

## 1. 실습 준비

Leader 노드에 장애가 발생한 이후에도 Vault의 시크릿 조회 기능이 정상적으로 동작하는지 검증하기 위해 실습에 사용할 데이터가 필요했습니다.

실습에 사용할 데이터는 Leader 노드에서만 저장하면 됩니다. Vault는 Raft를 통해 설정과 데이터를 다른 노드에도 자동으로 복제하기 때문입니다.

이미 지난 포스팅에서 현재 Leader 노드가 `vault-1`인 것을 확인했습니다. 먼저 `vault-1` 컨테이너에 접속했습니다.

```bash
$ docker exec -it vault-1 sh
```

---

### 1.1. KV Engine 활성화 

시크릿 관리 기능을 사용하려면 먼저 KV Engine이 활성화되어 있어야 합니다. 따라서 아래 명령을 실행하여 KV Engine을 활성화했습니다.

```bash
/ # vault secrets enable -path=secret kv-v2
```

KV Engine 활성화에 대한 자세한 설명은 이전에 포스팅한 [[토이프로젝트] Vault를 이용한 KMS 대체 검토: (2) KV Engine을 이용한 암호화 키 저장과 조회 실습](https://sanghoon-lee.github.io/2026/04/10/vault1-1-rewriting/)를 참고하면 됩니다.

명령이 정상적으로 실행되고, KV Engine이 활성화되었다는 메시지가 출력되었습니다.

```nohighlight
Success! Enabled the kv-v2 secrets engine at: secret/
```

현재 활성화된 Secret Engine 목록도 조회했습니다.

```bash
/ # vault secrets list
```

조회 결과 secret/ 경로에 KV Engine이 추가된 것을 확인할 수 있었습니다.

```nohighlight
Path          Type         Accessor              Description
----          ----         --------              -----------
cubbyhole/    cubbyhole    cubbyhole_69774e67    per-token private secret storage
identity/     identity     identity_98fb821e     identity store
secret/       kv           kv_c9d26563           n/a
sys/          system       system_b2098bcd       system endpoints used for control, policy and debugging
```


---

### 1.2. 시크릿 생성

시크릿은 여러 개의 Key-Value 형태의 데이터를 하나의 경로(Path)에 저장합니다. 이번 실습에서는 secret/vault-test 경로에 name과 blog 값을 저장했습니다.

```bash
/ # vault kv put secret/vault-test name=sanghoon blog=https://sanghoon-lee.github.io
```

명령이 정상적으로 실행되고, 시크릿의 저장 경로와 메타데이터가 출력되었습니다.

```nohighlight
===== Secret Path =====
secret/data/vault-test

======= Metadata =======
Key                Value
---                -----
created_time       2026-06-29T11:52:28.836931496Z
custom_metadata    <nil>
deletion_time      n/a
destroyed          false
version            1
```

저장된 시크릿을 조회해봤습니다.

```bash
/ # vault kv get secret/vault-test
```

조회 결과 저장했던 name과 blog 값이 정상적으로 출력되는 것을 확인할 수 있었습니다.

```nohighlight
===== Secret Path =====
secret/data/vault-test

======= Metadata =======
Key                Value
---                -----
created_time       2026-06-29T11:52:28.836931496Z
custom_metadata    <nil>
deletion_time      n/a
destroyed          false
version            1

==== Data ====
Key     Value
---     -----
blog    https://sanghoon-lee.github.io
name    sanghoon
```

이후 Leader 노드에 장애를 발생시킨 뒤에도 저장한 시크릿이 정상적으로 조회되는지 확인해보겠습니다.

## 2. 데이터 복제 확인

Leader 노드를 강제로 종료하여 장애 상황을 재현하기 전에 `vault-1`에서 저장한 시크릿이 다른 노드에도 정상적으로 복제되었는지 확인했습니다.

`vault-1`의 설정과 데이터가 다른 노드에도 정상적으로 복제가 되었다면 시크릿이 동일한 값으로 조회되어야 합니다. 

이를 확인하기 위해 이번에는 `vault-2` 컨테이너에 접속했습니다. 

```bash
$ docker exec -it vault-2 sh
```

**참고**

> 컨테이너에 다시 접속한 경우에는 VAULT_ADDR과 VAULT_TOKEN 환경변수를 다시 설정해야 합니다. 이 과정을 반복하기 번거롭다면 컨테이너 실행 시 환경변수로 함께 설정해두는 것도 좋은 방법입니다. 

그리고 secret/vault-test 경로에서 시크릿을 조회했습니다. 

```bash
/ # vault kv get secret/vault-test
```

`vault-2`에서는 별도로 KV Engine을 활성화하거나 시크릿을 생성하지 않았습니다. 그럼에도 아래와 같이 `vault-1`에서 저장한 name과 blog 값이 동일하게 조회되었습니다.

```nohighlight
===== Secret Path =====
secret/data/vault-test

======= Metadata =======
Key                Value
---                -----
created_time       2026-06-29T11:52:28.836931496Z
custom_metadata    <nil>
deletion_time      n/a
destroyed          false
version            1

==== Data ====
Key     Value
---     -----
blog    https://sanghoon-lee.github.io
name    sanghoon
```

이를 통해 Leader 노드에서 생성한 설정과 데이터가 Raft를 통해 다른 노드에도 정상적으로 복제되었음을 확인할 수 있었습니다. 

동일한 방법으로 `vault-3`에서도 시크릿을 조회한 결과, 동일한 값이 정상적으로 출력되는 것을 확인했습니다.

## 3. Leader 장애 재현

이제 모든 노드에 동일한 데이터가 복제된 것을 확인했으므로, 다음으로 Leader 노드에 장애를 발생시켜도 시크릿을 정상적으로 조회할 수 있는지 확인해보겠습니다.
