지금까지 Vault가 고가용성을 어떤 방식으로 제공하는지 살펴보고, 실제로 3개의 노드를 이용해 클러스터를 구축해봤습니다.

하지만 클러스터가 구축되었다고 해서 곧바로 고가용성이 검증되었다고 보기는 어렵습니다. Active 노드에 장애가 발생하더라도 새로운 Active 노드가 자동으로 선출되고, 서비스가 중단 없이 제공되는지 확인해야 합니다.

그래서 이번 포스팅에서는 장애 상황에서 Leader Election과 Failover가 실제로 어떻게 이루어지는지 단계별로 확인해보겠습니다. 

---

## 1. 실습 준비

Active 노드에 장애가 발생한 이후에도 Vault의 시크릿 조회 기능이 정상적으로 동작하는지 검증하기 위해 실습에 사용할 데이터가 필요했습니다.

먼저 Vault의 KV Engine을 활성화하고, 실습에 사용할 데이터를 저장해야 합니다. 이 작업은 Active 노드에서만 수행하면 됩니다. 정상적으로 클러스터가 구축되어 있다면 작업을 통해 변경된 설정과 데이터는 다른 노드에도 자동으로 복제되기 때문입니다.

이미 지난 포스팅에서 현재 Active 노드가 `vault-1`인 것을 확인했습니다. 작업을 수행하기 위해 `vault-1` 컨테이너에 다시 접속했습니다.

```bash
$ docker exec -it vault-1 sh
```

이때 주의할 점이 있습니다. 기존에 접속했던 컨테이너에 다시 접속하면 VAULT_ADDR과 VAULT_TOKEN 환경변수를 다시 설정해야 합니다. 이 과정을 반복하기 번거롭다면 컨테이너 실행 시 환경변수로 함께 설정해두는 것도 좋은 방법입니다. 

---

### 1.1. KV Engine 활성화 

Vault에서 KV Engine을 사용할 수 있도록 활성화했습니다.

```bash
/ # vault secrets enable -path=secret kv-v2
```

명령이 정상적으로 실행되면서 KV Engine이 활성화되었다는 메시지가 출력되는 것을 확인할 수 있었습니다.

```nohighlight
Success! Enabled the kv-v2 secrets engine at: secret/
```

KV Engine 활성화에 대해서 추가적인 설명이 필요하면 이전에 포스팅한 [[토이프로젝트] Vault를 이용한 KMS 대체 검토: (2) KV Engine을 이용한 암호화 키 저장과 조회 실습](https://sanghoon-lee.github.io/2026/04/10/vault1-1-rewriting/)를 참고하면 됩니다.


활성화된 Secret Engine 목록을 조회해서 KV Engine이 활성화되었는지 다시 한번 확인해봤습니다.

```bash
/ # vault secrets list
```

아래와 같이 `secret/` 경로에 KV Engine이 추가된 것을 확인할 수 있었습니다.

```nohighlight
Path          Type         Accessor              Description
----          ----         --------              -----------
cubbyhole/    cubbyhole    cubbyhole_69774e67    per-token private secret storage
identity/     identity     identity_98fb821e     identity store
secret/       kv           kv_c9d26563           n/a
sys/          system       system_b2098bcd       system endpoints used for control, policy and debugging
```

### 1.2. 시크릿 생성

시크릿은 여러 개의 Key-Value 형태의 데이터를 하나의 경로(Path)에 저장합니다. 이번 실습을 위해서 secret/vault-test 경로에 name과 blog 값을 저장했습니다.

```bash
/ # vault kv put secret/vault-test name=sanghoon blog=https://sanghoon-lee.github.io
```

명령이 정상적으로 실행되고, 시크릿의 저장 경로와 메타데이터가 출력되었습니다.

```nohighlight
===== Secret Path =====
secret/data/vault-test

======= Metadata =======
Key                Value
---                -----
created_time       2026-06-29T11:52:28.836931496Z
custom_metadata    <nil>
deletion_time      n/a
destroyed          false
version            1
```

저장된 시크릿을 정상적으로 조회할 수 있었습니다.

```bash
/ # vault kv get secret/vault-test
```

시크릿 조회 결과에는 데이터 뿐만 아니라 저장 경로와 메타데이터까지 포함됩니다.

```nohighlight
===== Secret Path =====
secret/data/vault-test

======= Metadata =======
Key                Value
---                -----
created_time       2026-06-29T11:52:28.836931496Z
custom_metadata    <nil>
deletion_time      n/a
destroyed          false
version            1

==== Data ====
Key     Value
---     -----
blog    https://sanghoon-lee.github.io
name    sanghoon
```

## 2. 데이터 복제 확인

`vault-1`의 설정과 데이터가 다른 노드에도 정상적으로 복제가 되었다면 다른 노드에서도 시크릿이 동일한 값으로 조회되어야 합니다. 

이번에는 `vault-2` 컨테이너에 접속했습니다. 

```bash
$ docker exec -it vault-2 sh
```

그리고 secret/vault-test 경로에서 시크릿을 조회했습니다. 

```bash
/ # vault kv get secret/vault-test
```

`vault-2`에서는 별도로 KV Engine을 활성화하거나 시크릿을 생성하지 않았습니다. 그럼에도 `vault-1`에서 저장한 name과 blog 값이 동일하게 조회되었습니다.

```nohighlight
===== Secret Path =====
secret/data/vault-test

======= Metadata =======
Key                Value
---                -----
created_time       2026-06-29T11:52:28.836931496Z
custom_metadata    <nil>
deletion_time      n/a
destroyed          false
version            1

==== Data ====
Key     Value
---     -----
blog    https://sanghoon-lee.github.io
name    sanghoon
```

이를 통해 Active 노드인 `vault-1`에서 생성한 설정과 데이터가 다른 노드에도 정상적으로 복제되었음을 확인할 수 있었습니다. 

동일한 방법으로 `vault-3`에서도 시크릿을 정상적으로 조회할 수 있었습니다.

---

## 3. 장애 상황 재현

모든 노드에 동일한 설정과 데이터가 복제된 것은 확인했습니다. 실습을 진행하기 위해 Active 노드를 종료하여 장애 상황을 재현했습니다.

```bash
$ docker kill vault-1
```
이 상태에서 `vault-2` 컨테이너 내부에서 현재 클러스터 상태를 조회했습니다.

```bash
/ # vault operator raft list-peers
```

그리고 이제는 `vault-1`이 아닌 `vault-2`의 State가 leader로 변경된 것을 확인할 수 있었습니다. 

/ # vault operator raft list-peers
Node       Address         State       Voter
----       -------         -----       -----
vault-1    vault-1:8201    follower    true
vault-2    vault-2:8201    leader      true
vault-3    vault-3:8201    follower    true

즉, 현재 Active 노드는 `vault-2`입니다.

## 4. 실습: 장애 상황에서 Leader Election과 Failover 동작 확인

이제 실습을 통해 Active 노드에서 장애가 발생하더라도 Leader Election과 Failover가 동작하는지 검증해볼 차례입니다. 정상적으로 동작한다면 시크릿 조회가 가능해야 합니다. 

지금까지는 컨테이너 내부에 접속한 상태에서 Vault CLI를 통해 시크릿을 조회했었습니다. 실습에서는 컨테이너 접속을 모두 종료하고, 가상머신에서 Vault API를 호출하는 방식으로 시크릿을 조회했습니다.

우선 API를 호출하려면 Token이 필요합니다. 매번 요청마다 Token을 입력하는 것이 번거로워 환경변수의 값으로 이전에 발급받았던 Initial Root Token을 저장했습니다.

```bash
$ export VAULT_TOKEN={실제 발급받았던 Initial Root Token 값}
```

처음에는 8200 포트를 사용하는 `vault-1`에 API를 호출해봤습니다.

```bash
$ curl \
  --header "X-Vault-Token: $VAULT_TOKEN" \
  http://127.0.0.1:8200/v1/secret/data/vault-test
```

앞에서 해당 노드를 강제로 종료시켰기 때문에 당연히 오류가 발생합니다.

```nohighlight
curl: (7) Failed to connect to 127.0.0.1 port 8200 after 0 ms: Couldn't connect to server
```

이어서 현재 Active 노드인 `vault-2`에도 API를 호출해봤습니다. 

```bash
$ curl \
  --header "X-Vault-Token: $VAULT_TOKEN" \
  http://127.0.0.1:8202/v1/secret/data/vault-test
```

`vault-2`는 8202 포트를 사용합니다.

```json
{
  "request_id":"50c3fa67-3503-fcae-f84d-93c96c5e626f","lease_id":"",
  "renewable":false,
  "lease_duration":0,
  "data":
  {
    "data":
    {
      "blog":"https://sanghoon-lee.github.io",
      "name":"sanghoon"
    },
    "metadata":
    {
      "created_time":"2026-06-29T11:52:28.836931496Z","custom_metadata":null,
      "deletion_time":"",
      "destroyed":false,
      "version":1

```

마지막으로 프로세스가 실행되고 있지만 Standby 노드인 `vault-3`에도 API를 호출해봤습니다.

```bash
$ curl \
  --header "X-Vault-Token: $VAULT_TOKEN" \
  http://127.0.0.1:8204/v1/secret/data/vault-test
```

`vault-3`는 8204 포트를 사용합니다. 

```json
{

  "warnings":null,

```

Standby 노드라 API를 호출하더라도 정상 응답을 받지 못할 것이라 생각했지만 예상과 다르게 정상 응답이 반환되었습니다.

## 5. Vault의 Request Forwarding 기능

`vault-3`은 Standby 노드이지만 요청이 들어오면 Active 노드에게 요청을 전달합니다. 그리고 응답을 받아서 이를 클라이언트에 전달합니다. 이를 Request Forwarding 기능이라고 합니다.

```md
클라이언트
   |
   v
vault-3 (Standby)
   |
   |  Request Forwarding
   v
vault-2 (Leader)
   |
   |  응답
   v
vault-3
   |
   v
클라이언트
```

만약 Request Forwarding이 없다면 클라이언트는 매번 Active 노드를 찾는 과정을 반복해야 합니다.

Vault는 이를 피하기 위해 Standby 노드가 Active 노드에게 요청을 대신 전달해 주는 기능을 제공합니다.
