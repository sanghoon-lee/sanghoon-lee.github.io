지난 포스팅에서는 DB 레벨 암호화와 애플리케이션 레벨 암호화의 차이, 그리고 이 토이 프로젝트를 통해 무엇을 해보고 싶은지에 대해 설명했습니다.

이제부터는 조금 더 구체적으로, 애플리케이션 레벨 암호화를 실제 코드 구조로 어떻게 풀어낼 것인지에 대한 이야기로 넘어가려고 합니다.

## 구현 방식의 선택

애플리케이션 레벨 암호화를 구현하는 방식은 생각보다 다양합니다.

가장 먼저 떠오른 구현 방식은 서비스 계층에 암·복호화 로직을 두고 직접 수행하는 것이었습니다. 단순하고, 직관적으로 보였기 때문입니다. 

**서비스 계층에 암·복호화 로직을 두고 직접 수행하는 경우의 한계**

서비스 계층에 암·복호화 로직을 두는 것이 가장 구현이 쉬우면서, 빠르게 시작할 수 있는 선택지는 분명합니다. 하지만 애플리케이션의 규모가 조금만 커져도 비즈니스 코드의 오염, 암호화 적용 누락 위험, 그리고 공통 규칙 유지의 어려움과 같은 문제를 피하기 어렵게 됩니다.

| 문제점 | 내용 |
| ---- | ---- |
| 비즈니스 코드의 오염  | 서비스 계층은 본래 비즈니스 규칙을 표현하는 역할을 담당합니다. 하지만, 데이터의 암·복호화 로직이 이 계층에 들어오기 시작하면서 비즈니스 로직과 보안 로직의 경계가 흐려지게 됩니다. 결국, 서비스 계층의 책임이 점점 무거워질 수밖에 없습니다. |
| 암호화 적용 누락 위험  | 개발자가 암호화 대상인 필드를 정확히 기억하고, 서비스 코드에 반영해야만 합니다. 개발자의 실수에 의해 암호화 처리가 한 번이라도 빠지면, 민감한 데이터가 평문으로 저장될 위험이 있습니다. 보안과 관련된 로직은 “실수하지 않도록 주의한다”는 전제보다는, 구조적으로 실수를 어렵게 만드는 방향이 더 적절합니다. |
| 공통 규칙 유지의 어려움 | 데이터의 암·복호화라는 공통의 관심사가 서비스의 여러 곳에 분산되면서 중복 구현되고, 정책 변경 시 수정 범위도 넓어지게 됩니다. |

이러한 이유로, 이 프로젝트에서는 암호화 로직을 서비스 계층에 두는 방식은 우선적으로 배제하게 되었습니다.
