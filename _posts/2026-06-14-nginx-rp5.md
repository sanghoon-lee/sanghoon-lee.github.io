Nginx를 이용해 Reverse Proxy를 구축하고, 애플리케이션 서버 대신 외부에 노출되어 클라이언트의 요청을 처리하도록 구성해봤습니다.

이를 통해 Reverse Proxy가 내부의 애플리케이션 서버를 보호하는 역할을 수행할 수 있다는 점을 확인할 수 있었습니다.

하지만 실제 서비스 운영 환경에서는 Reverse Proxy가 단순히 애플리케이션 서버를 보호하는 역할만 수행하지 않습니다.

트래픽을 여러 서버에 분산하는 로드밸런싱(Load Balancing), HTTPS 통신을 처리하는 SSL 종료(SSL Termination), 그리고 이미지·CSS·JavaScript와 같은 정적 콘텐츠를 직접 제공하는 기능 등 다양한 역할도 함께 수행합니다.

이러한 기능들은 서비스의 확장성과 성능, 그리고 운영 효율성을 높이는 데 중요한 역할을 하게 됩니다. 대부분의 운영 환경에서 Reverse Proxy가 핵심 인프라로 활용되고 있는 이유이기도 합니다.

이번 포스팅에서는 Reverse Proxy의 로드밸런싱 기능이 실제로 어떻게 동작하는지 검증해보도록 하겠습니다.

---

## 1. 로드밸런싱 실습 준비

하나의 애플리케이션 서버로 구성된 환경에서 서비스를 운영하면 모든 요청은 해당 서버에 집중됩니다. 

이러한 구성에서는 트래픽이 증가할수록 애플리케이션 서버의 부하도 증가하게 됩니다. 애플리케이션 서버에 장애가 발생하면 서비스 전체가 중단될 위험도 존재합니다.

이러한 위험을 방지하기 위해서 사용되는 기능이 로드밸런싱(Load Balancing)입니다.

로드밸런싱은 다수의 애플리케이션 서버가 구성된 환경에서 클라이언트의 요청을 각 애플리케이션 서버로 분산하여 처리하는 기능을 의미합니다.

---

### 1.1. 현재 구성의 한계

현재 Reverse Proxy의 애플리케이션 서버 보호 기능을 검증하기 위해 하나의 애플리케이션 서버(api-01)만 구동되고 있습니다.

```nohighlight
Client 
  ↓ 
Nginx 
  ↓ 
api-01
```

클라이언트의 요청을 분산하여 처리하는 로드밸런싱 기능의 동작을 확인하려면 애플리케이션 서버가 추가되어야 합니다. 

---

### 1.2. 애플리케이션 서버 추가

로드밸런싱 동작을 확인해 볼 수 있도록 애플리케이션 서버(api-02)를 추가로 구성했습니다.

```bash
$ docker run -d \
  --name api-02 \
  --network rp-network \
  -e SERVER_NAME=api-02 \
  simple-api
```

현재 구동되어 있는 애플리케이션 서버와 구분하기 위해 컨테이너 이름과 SERVER_NAME 환경변수를 모두 api-02로 지정했습니다.

SERVER_NAME의 값은 응답 결과에 포함되므로 어떤 애플리케이션 서버가 요청을 처리했는지 쉽게 확인할 수 있습니다.

```nohighlight
┌─────────────────────────┐
│       Windows 11        │
│       (Client)          │
└──────────┬──────────────┘
           │
           ▼
        nginx-rp
           │
           ▼
      rp-network
           │
     ┌─────┴─────┐
     ▼           ▼
  api-01      api-02
```

두 개의 애플리케이션 서버(api-01, api-02)가 준비되었지만, 아직 Reverse Proxy는 api-01에만 요청을 전달할 수 있도록 구성되어 있습니다. 따라서 현재 상태에서는 모든 요청이 여전히 api-01로만 전달됩니다.

---

### 1.3. Nginx의 설정 변경

이제 로드밸런싱 기능이 동작할 수 있도록 Reverse Proxy로 구성된 Nginx의 설정을 변경해야 합니다.

Nginx는 upstream 지시어를 이용해서 여러 백엔드 서버를 하나의 그룹으로 관리할 수 있습니다.

그리고 proxy_pass에서 개별 서버가 아닌 upstream 그룹을 지정하면 Nginx가 내부적으로 요청을 분산하여 전달하게 됩니다.

이를 위해 nginx.conf 파일을 아래와 같이 수정했습니다.

```nohighlight
http {

    upstream backend {
        server api-01:8000;
        server api-02:8000;
    }

    server {

        listen 80;

        location / {
            proxy_pass http://backend;
        }
    }
}
```

nginx.conf 파일에서 추가된 내용은 upstream backend 설정입니다.

```nohighlight
upstream backend {
    server api-01:8000;
    server api-02:8000;
}

upstream backend는 api-01과 api-02를 하나의 서버 그룹으로 정의하는 설정입니다.

그리고 proxy_pass에서 개별 서버 대신 backend 그룹을 지정하면 Nginx는 해당 그룹에 포함된 애플리케이션 서버로 요청을 전달하게 됩니다.

---

### 1.4. Reverse Proxy 서버 재구성

변경된 설정을 적용하려면 Reverse Proxy 서버(nginx-rp)를 재시작하기 위해 기존의 컨테이너를 제거했습니다.

```bash
$ docker rm -f nginx-rp
```

그리고 컨테이너를 다시 시작했습니다.

```bash
$ docker run -d \
  --name nginx-rp \
  --network rp-network \
  -p 80:80 \
  -v /home/sanghoon/nginx/nginx.conf:/etc/nginx/nginx.conf:ro \
  nginx
```

## 2. 실습 : 로드밸런싱 기능 검증

Reverse Proxy가 제공하는 로드밸런싱 기능의 동작을 확인하기 위해 여러 번 애플리케이션 서버를 호출했습니다.

```bash
$ curl http://192.168.56.11:80/api/server
```

아래 응답 예시처럼 api-01과 api-02가 번갈아 응답되고 있었습니다. 이를 통해 Nginx가 클라이언트의 요청을 두 개의 애플리케이션 서버에 분산하여 전달하고 있음을 확인할 수 있었습니다.

```json
{
    "time":"2026-06-14T02:13:12.679279473",
    "serverName":"api-01"
}
```

```json
{
    "time":"2026-06-14T02:13:14.290094732",
    "serverName":"api-02"
}
```

```json
{
    "time":"2026-06-14T02:13:15.112594293",
    "serverName":"api-01"
}
```
