Nginx를 이용해 Reverse Proxy를 구축하고, 애플리케이션 서버 대신 외부에 노출되어 클라이언트의 요청을 처리하도록 구성해봤습니다.

이를 통해 Reverse Proxy가 내부의 애플리케이션 서버를 보호하는 역할을 수행할 수 있다는 점을 확인할 수 있었습니다.

하지만 실제 서비스 운영 환경에서는 Reverse Proxy가 단순히 애플리케이션 서버를 보호하는 역할만 수행하지 않습니다.

트래픽을 여러 서버에 분산하는 로드밸런싱(Load Balancing) 기능 역시 Reverse Proxy의 대표적인 기능 중 하나입니다.

이번 포스팅에서는 대부분의 운영 환경에서 활용되고 있는 Reverse Proxy의 로드밸런싱 기능을 구성하고, 실제로 어떻게 동작하는지 검증해보도록 하겠습니다.

---

## 1. 로드밸런싱 실습 준비

하나의 애플리케이션 서버로 구성된 환경에서 서비스를 운영하면 모든 요청은 해당 서버에 집중됩니다. 

이러한 구성에서는 트래픽이 증가할수록 애플리케이션 서버의 부하도 증가하게 됩니다. 또한 애플리케이션 서버에 장애가 발생하면 요청을 처리할 수 있는 서버가 존재하지 않기 때문에 서비스 전체가 중단될 위험도 존재합니다.

이러한 위험을 방지하기 위해서 사용되는 기능이 로드밸런싱(Load Balancing)입니다.

로드밸런싱은 다수의 애플리케이션 서버가 구성된 환경에서 클라이언트의 요청을 여러 애플리케이션 서버에 분산하여 처리하는 기능을 의미합니다.

이를 통해 특정 서버에 요청이 집중되는 현상을 방지하고, 서비스의 확장성과 가용성을 향상시킬 수 있습니다.

---

### 1.1. 현재 구성의 한계

현재 Reverse Proxy의 애플리케이션 서버 보호 기능을 검증하기 위해 하나의 애플리케이션 서버(api-01)만 구동되고 있습니다.

```nohighlight
Client 
  ↓ 
Nginx 
  ↓ 
api-01
```

클라이언트의 요청을 분산하여 처리하는 로드밸런싱 기능의 동작을 확인하려면 애플리케이션 서버가 추가되어야 합니다. 

---

### 1.2. 애플리케이션 서버 추가

로드밸런싱 동작을 확인할 수 있도록 애플리케이션 서버(api-02)를 추가로 구성했습니다.

```bash
$ docker run -d \
  --name api-02 \
  --network rp-network \
  -e SERVER_NAME=api-02 \
  simple-api
```

기존 애플리케이션 서버(api-01)와 구분하기 위해 컨테이너 이름과 SERVER_NAME 환경변수를 모두 api-02로 지정했습니다.

SERVER_NAME의 값은 응답 결과에 포함되므로 어떤 애플리케이션 서버가 요청을 처리했는지 쉽게 확인할 수 있습니다.

```nohighlight
┌─────────────────────────┐
│       Windows 11        │
│       (Client)          │
└──────────┬──────────────┘
           │
           ▼
        nginx-rp
           │
           ▼
      rp-network
           │
     ┌─────┴─────┐
     ▼           ▼
  api-01      api-02
```

두 개의 애플리케이션 서버(api-01, api-02)가 준비되었지만, 아직 Reverse Proxy는 api-01에만 요청을 전달할 수 있도록 구성되어 있습니다. 따라서 현재 상태에서는 모든 요청이 여전히 api-01로만 전달됩니다.

---

### 1.3. Nginx 설정 변경

이제 로드밸런싱 기능이 동작할 수 있도록 Reverse Proxy로 구성된 Nginx의 설정을 변경해야 합니다.

Nginx는 upstream 지시어를 이용해서 여러 백엔드 서버를 하나의 서버 그룹으로 관리할 수 있습니다.

그리고 proxy_pass에서 개별 서버가 아닌 upstream 그룹을 지정하면 Nginx가 내부적으로 요청을 분산하여 전달하게 됩니다.

이를 위해 nginx.conf 파일을 아래와 같이 수정했습니다.

```nohighlight
http {

    upstream backend {
        server api-01:8000;
        server api-02:8000;
    }

    server {

        listen 80;

        location / {
            proxy_pass http://backend;
        }
    }
}
```

nginx.conf 파일에서 추가된 내용은 upstream backend 설정입니다.

```nohighlight
upstream backend {
    server api-01:8000;
    server api-02:8000;
}
```

upstream backend는 api-01과 api-02를 하나의 서버 그룹으로 정의하는 설정입니다.

기존에는 proxy_pass가 api-01 하나만 바라보고 있었기 때문에 모든 요청이 api-01으로 전달되었습니다.

하지만 이제는 api-01과 api-02를 하나의 서버 그룹으로 구성하고 proxy_pass가 해당 그룹(backend)을 바라보도록 변경했습니다.

proxy_pass에서 개별 서버 대신 그룹의 이름을 지정하면 Nginx는 해당 그룹에 포함된 애플리케이션 서버로 요청을 분산하여 전달하게 됩니다.

별도의 로드밸런싱 방식을 지정하지 않으면 Nginx는 기본적으로 Round Robin 방식을 사용합니다.

---

### 1.4. Reverse Proxy 서버 재구성

Reverse Proxy 서버(nginx-rp)를 재구성해서 변경된 Nginx의 설정이 적용되도록 해야 합니다. 우선 기존 컨테이너를 제거했습니다.

```bash
$ docker rm -f nginx-rp
```

그리고 아래와 같이 컨테이너를 다시 실행했습니다.

```bash
$ docker run -d \
  --name nginx-rp \
  --network rp-network \
  -p 80:80 \
  -v /home/sanghoon/nginx/nginx.conf:/etc/nginx/nginx.conf:ro \
  nginx
```

## 2. 실습 : 로드밸런싱 기능 검증

실습을 진행하기에 앞서 현재 가상머신에 구동되어 있는 컨테이너 목록을 조회해봤습니다.

```bash
$ docker ps

CONTAINER ID   IMAGE        COMMAND                  CREATED       STATUS       PORTS                                 NAMES
ded73c8b79f6   nginx        "/docker-entrypoint.…"   2 hours ago   Up 2 hours   0.0.0.0:80->80/tcp, [::]:80->80/tcp   nginx-rp
f96d293bcf49   simple-api   "java -jar simple-ap…"   2 hours ago   Up 2 hours                                         api-02
e5df7d564aab   simple-api   "java -jar simple-ap…"   2 days ago    Up 2 days                                          api-01
```

Reverse Proxy 서버(nginx-rp)와 2개의 애플리케이션 서버(api-01, api-02)가 모두 정상적으로 실행 중인 상태였습니다.

이 상태에서 로드밸런싱 기능의 동작을 확인하기 위해 동일한 API를 반복적으로 호출했습니다.

```bash
$ curl http://192.168.56.11:80/api/server
```

응답 결과에 포함된 serverName 값을 통해 어떤 애플리케이션 서버가 요청을 처리했는지 확인할 수 있는데, 아래처럼 api-01과 api-02가 번갈아 응답되고 있었습니다. 

이를 통해 Nginx가 클라이언트의 요청을 두 개의 애플리케이션 서버에 분산하여 전달하고 있음을 확인할 수 있었습니다. 또한 특정 서버가 아닌 서버 그룹(backend)을 대상으로 요청을 전달하고 있다는 점도 확인할 수 있었습니다.

```json
{
    "time":"2026-06-14T02:13:12.679279473",
    "serverName":"api-01"
}
```

```json
{
    "time":"2026-06-14T02:13:14.290094732",
    "serverName":"api-02"
}
```

```json
{
    "time":"2026-06-14T02:13:15.112594293",
    "serverName":"api-01"
}
```

앞에서도 언급했지만 Nginx의 기본 로드밸런싱 방식은 Round Robin입니다.

로드밸런싱 방식을 별도로 지정하지 않으면 Nginx는 요청을 순차적으로 각 애플리케이션 서버에 전달합니다.

실습 결과에서도 api-01과 api-02가 번갈아 응답하는 모습을 볼 수 있었으며, Nginx가 Round Robin 방식으로 요청을 분산하고 있음을 확인할 수 있었습니다.

실제 운영 환경에서는 이러한 로드밸런싱 기능을 활용해 서버 부하를 분산하고 서비스의 가용성을 높일 수 있습니다.

이번 실습을 통해 Reverse Proxy가 단순히 애플리케이션 서버를 보호하는 역할뿐만 아니라, 서비스의 확장성과 안정성을 높이는 데에도 활용될 수 있다는 점을 확인할 수 있었습니다.
