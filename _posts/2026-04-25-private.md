Java에서 유틸리티 클래스는 보통 static 메서드만을 제공하며, 인스턴스를 생성할 필요가 없는 클래스를 의미합니다.

회사에서 사용할 라이브러리를 개발하고 있었는데, 유틸리티 클래스를 구현하면서 생성자를 별도로 정의하지 않았습니다.

어차피 인스턴스를 생성할 필요가 없으니 생성자도 정의할 필요가 없다고 생각했기 때문입니다.

<img class="main-image" src="/assets/images/java_logo" alt="Java">

하지만 제가 너무 단순하게 생각했던 것 같습니다. 

SonarQube로 코드를 검사해보니, 유틸리티 클래스에는 private 생성자를 명시적으로 정의해야 한다는 권고가 다수 확인되었습니다.

**필요도 없는 private 생성자를 왜 정의하라는 것이지?**라는 궁금증이 생겼습니다. 

---

## 1. 생성자를 정의하지 않으면 어떻게 될까?

Java에서는 클래스에 생성자를 직접 정의하지 않으면 컴파일러가 기본 생성자를 자동으로 생성합니다.

```java
public class SomeUtils {
    // 생성자를 정의하지 않음
}
```

위의 SomeUtils 클래스와 같이 생성자가 정의되지 않는 경우 컴파일러는 내부적으로 다음과 같은 코드를 만들어줍니다.

```java
public class SomeUtils {

    public SomeUtils() {
        super();
    }
}
```

즉, public 생성자가 자동으로 생성되는 것입니다.

---

## 2. 그래서 뭐가 문제일까?

겉보기에는 별 문제가 없어 보일 수 있습니다. 

하지만 생성자를 정의하지 않으면 public 생성자가 자동으로 생성되고, 그 결과 잘못된 사용이 아무 제약 없이 허용된다는 문제가 있습니다.

즉, **“잘못된 사용을 막지 못하는 구조”**가 되는 것입니다.

---

### 2.1. 의미 없는 객체의 생성

```java
SomeUtils utils = new SomeUtils();
```

생성자가 정의되지 않으면 public 생성자가 자동으로 생성되기 때문에 위의 코드는 정상 동작하게 됩니다.

즉, SomeUtils 클래스의 인스턴스가 생성되는 것입니다. 하지만 아래와 같은 이유들로 존재 이유가 없는 불필요한 객체가 됩니다.

* 상태 없음
* 필드 없음
* 인스턴스 메서드 없음

이건 잘못된 사용을 허용하는 설계에 해당되는 경우입니다.

---

### 2.2. 일관되지 않는 사용 방식 허용

**정상적인 사용**
```java
SomeUtils.isEmpty(str);
```

**비정상적인 사용, 하지만 허용**
```java
new SomeUtils().isEmpty(str); // static 메서드를 인스턴스로 호출하는 것은 권장되지 않는 방식입니다.
```

동일한 기능을 두 가지 방식으로 사용할 수 있게 됩니다.

시간이 지나면서 두 가지 방식이 혼용되면 코드의 일관성이 깨지고, 결과적으로 유지보수 비용이 증가하게 됩니다.

---

### 2.3. 불필요한 자원의 낭비

크리티컬한 문제는 아니지만, 자원의 분명한 낭비입니다.

* GC 대상 증가
* 객체 생성 비용 증가

특히 반복적으로 사용될 경우 자원의 낭비가 누적되면서 성능 저하까지 이어질 수 있습니다.

---

## 3. 해결 방법: private 생성자

```java
public class SomeUtils {

    private SomeUtils() {
        throw new AssertionError("유틸리티 클래스는 인스턴스화 할 수 없습니다.");
    }

    public static boolean isEmpty(String str) {
        return str == null || str.isEmpty();
    }
}
```

SonarQube에서는 유틸리티 클래스에 private 생성자를 명시적으로 정의할 것을 권고하고 있습니다.

이는 잘못된 사용을 사전에 차단하고, 코드의 의도를 명확히 하기 위한 설계 원칙입니다.

이러한 패턴은 단순히 불필요한 객체 생성을 막기 위한 문법만은 아닙니다. 

클래스의 설계 의도를 명확하게 표현하는 방법입니다.

* 이 클래스는 상태를 가지지 않는다
* 인스턴스가 필요 없다
* static 메서드만 사용해야 한다

이러한 의도들을 코드로 강제하는 것입니다.

private 생성자는 기능이 아니라 의도를 표현하는 코드인 것입니다. 

SonarQube에서는 이러한 문제를 단순한 문법 오류가 아닌 Code Smell(설계 문제)로 판단합니다.

---

## 4. AssertionError를 던지는 이유

생성자를 private으로 막았는데 왜 굳이 예외까지 던져야 할까요?

이유는 리플렉션 때문입니다.

```java
Constructor<?> constructor = SomeUtils.class.getDeclaredConstructor();
constructor.setAccessible(true);
constructor.newInstance();
```

리플렉션을 사용하면 private 생성자도 호출할 수 있습니다.

그래서 예외를 던져 의도하지 않은 인스턴스 생성을 한 번 더 방어하기 위함입니다.

실제 실무에서는 리플렉션으로 생성자를 호출하는 경우는 드물지만, 방어적인 차원에서 추가하는 것이 더 안전합니다.

---

## 5. 정리

유틸리티 클래스에 private 생성자를 정의하는 것은 잘못된 사용을 원천 차단하여 설계 의도를 명확하게 만드는 안전 장치입니다.

특히 공통 라이브러리에서 이러한 설계 원칙을 일관되게 적용하는 것이 중요합니다.

사소하게 보일 수 있지만, 결국 이런 작은 습관들이 모여 코드의 품질을 지키고 더 안정적인 시스템을 만들어가는 토대가 되는 것입니다.
