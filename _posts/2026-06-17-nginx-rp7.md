지금까지 Nginx로 Reverse Proxy를 구성하고, 실습을 통해 아래 기능들의 동작을 직접 확인해봤습니다.

* 애플리케이션 서버 보호
* 로드밸런싱 
* SSL 종료

이제 마지막으로 정적 콘텐츠 처리 기능을 검증할 차례입니다.

사실 이미지, CSS, JavaScript, HTML 등과 같은 정적 콘텐츠를 제공하는 기능은 일반적으로 `웹 서버(Web Server)`의 역할로 분류됩니다.

반면 `Reverse Proxy`의 주요 역할은 클라이언트의 요청을 적절한 애플리케이션 서버로 전달하고, 서버를 보호하거나 트래픽을 분산하는 것입니다.

하지만 Nginx는 Reverse Proxy 기능과 웹 서버 기능을 모두 제공하고 있습니다.

그래서 최근에는 Nginx를 Reverse Proxy로 사용하면서 동시에 웹 서버 역할까지 담당하도록 구성하는 사례가 많습니다.

---

## 1. 정적 콘텐츠 처리 실습 준비

일반적으로 웹 서버는 디스크에 저장된 HTML, CSS, JavaScript, 이미지 파일 등 클라이언트가 요청한 정적 콘텐츠를 반환합니다.

이번 실습에서는 이러한 기능이 정상적으로 동작하는지 확인하기 위해 간단한 HTML 파일을 생성했습니다.

---

### 1.1. 정적 콘텐츠 생성

제 실습 환경에서는 /home/sanghoon/nginx 폴더가 Reverse Proxy 컨테이너(nginx-rp)와 공유되도록 마운트되어 있습니다.

그래서 /home/sanghoon/nginx 폴더 하위에 static 폴더를 생성하고, 다음과 같이 index.html 파일을 작성했습니다.

**index.html**

```html
<!DOCTYPE html>
<html lang="ko">
<head>
    <meta charset="UTF-8">
    <title>Nginx로 Reverse Proxy 구성하기</title>
</head>
<body>
    <h1>정적 콘텐츠 처리 기능 검증</h1>
</body>
</html>
```

정적 콘텐츠는 /static 경로를 통해 접근할 수 있도록 실습 환경을 구성했습니다. 즉 index.html 파일은 다음과 같이 요청할 수 있습니다.
 
```http
GET /static/index.html HTTP/1.1
```

---

### 1.2. Nginx 설정 변경

/static 경로로 들어오는 요청을 처리할 수 있도록 아래와 같이 nginx.conf 파일을 수정해야 합니다.

```nohighlight
http {

    upstream backend {
        server api-01:8000;
        server api-02:8000;
    }

    server {
        listen 80;
        return 301 https://$host$request_uri;
    }

    server {

        listen 443 ssl;

        ssl_certificate     /etc/nginx/certs/nginx.crt;
        ssl_certificate_key /etc/nginx/certs/nginx.key;

        location /static/ {
            root /usr/share/nginx;
        }

        location / {
            proxy_pass http://backend;
        }
    }
}
```

이번에 추가된 설정은 아래 부분입니다.

```nohighlight
location /static/ {
    root /usr/share/nginx;
}
```

예를 들어 클라이언트가 /static/index.html을 요청하면 Nginx는 root 설정값인 /usr/share/nginx와 요청 경로를 조합하여 /usr/share/nginx/static/index.html 파일을 찾아 응답하게 됩니다.

---

### 1.3. Reverse Proxy 서버 재구성

정상적인 실습을 위해 컨테이너가 /home/sanghoon/nginx/static 폴더에 있는 index.html 파일에 접근할 수 있어야 합니다.

그래서 가상머신에 생성한 /home/sanghoon/nginx/static 폴더를 컨테이너 내부의 /usr/share/nginx/static 폴더에 마운트했습니다. 이를 통해 Nginx가 index.html 파일에 직접 접근할 수 있도록 구성했습니다.

우선 기존 컨테이너를 제거했습니다.

```bash
$ docker rm -f nginx-rp
```

그리고 아래와 같이 컨테이너를 다시 실행했습니다.

```bash
$ docker run -d \
  --name nginx-rp \
  --network rp-network \
  -p 80:80 \
  -p 443:443 \
  -v /home/sanghoon/nginx/nginx.conf:/etc/nginx/nginx.conf:ro \
  -v /home/sanghoon/nginx/certs:/etc/nginx/certs:ro \
  -v /home/sanghoon/nginx/static:/usr/share/nginx/static:ro \
  nginx
```

이제 Nginx는 정적 콘텐츠를 직접 제공할 수 있는 상태가 되었습니다.

---

## 2. 실습 : 정적 콘텐츠 처리 기능 검증

웹 브라우저에서 아래 주소로 접속을 해보면 index.html 파일의 내용이 정상적으로 출력되는 것을 확인할 수 있었습니다.

```http
http://192.168.56.11/static/index.html
```

http(80 포트)로 요청을 하더라도 https(443 포트)로 리다이렉션 되도록 설정이 되어 있습니다. 하지만 실습 환경에서는 정식 인증서가 아니라 OpenSSL을 이용해서 생성한 자체 서명 인증서를 사용하고 있기 때문에 브라우저에서 신뢰할 수 없는 인증서로 경고가 표시되고 있습니다.

<img class="main-image" src="/assets/images/index-html.png" alt="index.html">

---

### 2.1. 정적 콘텐츠 요청 처리 확인

정적 콘텐츠 요청이 Reverse Proxy에서 직접 처리되었는지 검증하기 위해 애플리케이션 서버 컨테이너의 로그를 확인했었습니다.

```bash
$ docker logs api-01

$ docker logs api-02
```

정적 콘텐츠 요청 후에도 index.html 요청과 관련된 로그는 출력되지 않았습니다.

이를 통해 정적 콘텐츠 요청은 Reverse Proxy 컨테이너가 직접 처리되고 있는 것을 확인할 수 있었습니다.

물론 /api/server 요청은 애플리케이션 서버로 유입되어 정상적으로 동작하고 있었습니다.

```bash
$ curl -k https://192.168.56.11/api/server

{
    "serverName":"api-02",
    "time":"2026-06-20T03:04:48.465454311"
}
```


```nohighlight
                Client
                   │
                   ▼
                Nginx
        ┌──────────┴──────────┐
        ▼                     ▼
/static/index.html      /api/server
        │                     │
        ▼                     ▼
   직접 응답         Application Server
```

---

### 2.2. 정적 콘텐츠 처리의 장점

이번 실습을 통해 Nginx로 구성된 Reverse Proxy가 웹 서버의 역할까지 수행할 수 있다는 점을 직접 확인할 수 있었습니다.

Nginx가 정적 콘텐츠를 직접 제공하면 애플리케이션 서버는 API 처리와 같은 동적 요청에 집중할 수 있습니다.

또한 정적 콘텐츠는 일반적으로 변경 빈도가 낮고 요청량이 많기 때문에 웹 서버가 직접 처리하는 것이 효율적입니다. 이를 통해 애플리케이션 서버의 불필요한 부하를 줄이고 전체 서비스의 응답 성능을 향상시킬 수 있습니다.

실제 운영 환경에서도 이러한 이유로 이미지, CSS, JavaScript 파일과 같은 정적 콘텐츠는 웹 서버나 CDN이 제공하고, 애플리케이션 서버는 비즈니스 로직 처리에 집중하도록 구성하는 경우가 많습니다.

---

## 3. 마무리

이번 시리즈에서는 Nginx를 이용해 Reverse Proxy를 구성하고, 애플리케이션 서버 보호, 로드밸런싱, SSL 종료, 정적 콘텐츠 처리 기능까지 단계적으로 검증해봤습니다.

이를 통해 Reverse Proxy가 단순히 요청을 전달하는 구성 요소가 아니라 애플리케이션 서버를 보호하고, 트래픽을 분산하며, HTTPS 통신을 처리하는 중요한 인프라 구성 요소라는 점을 확인할 수 있었습니다.

또한 Nginx는 이러한 Reverse Proxy 기능과 함께 웹 서버 기능도 제공함으로써 정적 콘텐츠 처리까지 담당할 수 있다는 점도 함께 확인할 수 있었습니다.

이것으로 Nginx를 이용한 Reverse Proxy 구성하기 포스팅 시리즈를 마무리하도록 하겠습니다.
