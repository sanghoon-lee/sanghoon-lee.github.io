대부분의 개발자는 오픈소스 라이브러리를 사용하는 것에 대해 크게 고민할 필요가 없습니다.

Gradle이나 Maven과 같은 빌드 도구가 공개된 라이브러리 저장소에 접근해서 필요한 라이브러리를 알아서 가져오기 때문입니다.

개발자는 빌드 도구의 설정에 필요한 라이브러리 정보만 등록해두면 됩니다. 

하지만 인터넷이 차단된 폐쇄망 네트워크에서는 빌드 도구가 공개된 라이브러리 저장소에 접근할 수 없기 때문에 추가적인 아키텍처 구성이 필요합니다. 

---

## 1. 일반적인 개발환경과 폐쇄망 개발환경의 차이

인터넷 사용이 자유로운 일반적인 개발환경에서는 개발자의 PC나 CI 서버에서 실행되는 빌드 도구가 필요한 라이브러리를 가져오기 위해서 외부의 공개된 저장소에 제약없이 접근할 수 있습니다.

```nohighlight
개발자 PC / CI 서버
       ↓
외부의 공개 저장소(예: Maven Central)
       ↓
Dependency Download
```

하지만, 폐쇄망 네트워크를 사용하는 개발환경에서는 상황이 완전히 달라집니다. 인터넷이 차단되어 있기 때문에 외부의 공개된 저장소에 접근할 수 없습니다. 그렇기 때문에 필요한 라이브러리를 가져오기 위해서 다운로드 받는 것도 불가능합니다.

```nohighlight
개발자 PC / CI 서버
       ↓
     (차단)
       ↓
외부의 공개 저장소(예: Maven Central)
```

그러면 자연스럽게 다음과 같은 질문이 생깁니다.

> 폐쇄망 네트워크를 사용한 환경에서는 어떻게 빌드에 필요한 라이브러리를 가져올 수 있을까요?

---

## 2. 폐쇄망 개발환경에 라이브러리를 수동으로 반입하는 방식의 문제점

가장 단순한 방법은 인터넷 사용이 자유로운 환경에서 필요한 라이브러리를 다운로드하고, 수동으로 폐쇄망으로 반입하는 것입니다.

다음과 같은 방식입니다.

```nohighlight
1. 인터넷 사용이 가능한 환경에서 라이브러리 다운로드
2. 라이브러리 파일을 폐쇄망으로 반입 요청
3. 보안 담당자 확인 및 승인
4. 반입된 라이브러리 파일을 프로젝트에 직접 추가하거나 내부 저장소에 업로드
```

하지만 이런 방식을 사용하면 다음과 같은 문제가 발생할 수 있습니다. 

---

### 2.1. 라이브러리 반입 과정의 번거로움

대부분의 라이브러리는 또 다른 라이브러리들과 복잡한 의존관계를 형성하고 있는 경우가 대부분입니다. 

따라서 의존성까지 고려해 어떤 라이브러리들을 함께 가져와야 하는지 파악해야 합니다.

이 과정은 생각보다 복잡하며 매번 반복되어야 합니다. 결과적으로 개발 생산성 저하로 이어질 수 있습니다.

---

### 2.2. 버전 관리의 어려움

또한 어떤 버전의 라이브러리가 조직 내에서 사용되고 있는지 추적하는 것이 어렵습니다. 

그래서 이미 과거에 반입된 라이브러리임에도 불구하고, 다른 팀이나 프로젝트에서는 이를 알지 못해 다시 반입하는 일이 발생하기도 합니다.

동일한 라이브러리를 팀마다 서로 다른 버전으로 사용하고 있거나, 라이브러리를 직접 프로젝트 내부에 포함시켜서 유지보수를 어렵게 만들기도 합니다. 

---

## 3. 폐쇄망 개발환경에 내부 저장소 구축이 필요한 이유

위와 같은 문제를 해결하기 위해서 결국 내부로 반입된 라이브러리를 통제하고, 관리할 수 있는 별도의 방법이 필요합니다.

그래서 폐쇄망 네트워크를 사용해야 하는 개발조직에서는 대부분 **내부 저장소(Artifact Repository)**를 구축해서 운영하고 있습니다.

**내부 저장소**를 구축하는데 사용되는 대표적인 도구로 **Nexus**가 있습니다.

<img class="main-image" src="/assets/images/nexus2.jpg" alt="nexus repository">

**내부 저장소**는 외부 라이브러리가 폐쇄망 내부로 유입되는 유일한 경로가 됩니다. 즉, 라이브러리를 조직 내부에서 일관된 방식으로 통제할 수 있게 됩니다. 

조직 운영 관점에서 **내부 저장소**는 보안 통제 지점(Security Control Point)으로 중요한 역할을 하게 됩니다.

* 사용한 라이브러리 추적 가능
* 보안 취약점 발생 시 영향 범위 분석 가능
* 감사 대응 자료 확보 가능

---

## 4. 프록시 서버의 활용

하지만 **내부 저장소**가 구축되더라도 여전히 폐쇄망 네트워크에서 실행되는 빌드 도구는 외부의 공개 저장소에 접근할 수 없습니다.

그렇기 때문에 라이브러리는 여전히 수동으로 반입되어야 합니다. 일반적인 환경과 동일하게 라이브러리 반입까지 자동화할 수 없을까요?

라이브러리 반입을 자동화하려면 결국 **내부 저장소**에서 외부의 공개 저장소에 접근이 가능해야 합니다.

하지만 보안상 이유로 폐쇄망 네트워크를 인터넷과 직접 연결하기는 어렵습니다.

이런 경우 대부분 프록시 서버를 활용해서 문제를 해결하고 있습니다.

```nohighlight
개발자 PC / CI 서버
       ↓
내부 저장소 - 폐쇄망(Trust Zone)
       ↓
프록시 서버 - 폐쇄망(DMZ)
       ↓ 
외부의 공개 저장소(예: Maven Central) - 인터넷 
       ↓
Dependency Download
```

개발자 PC나 CI서버는 **내부 저장소**를 통해서만 라이브러리에 접근하고, 필요한 경우 **내부 저장소**가 프록시 서버를 경유하여 외부의 공개 저장소와 연동하도록 하는 것입니다.

이렇게 환경이 구성되면 **내부 저장소**가 프록시 서버의 통제를 받으면서 허용된 경로로 안전하게 외부와 연결되는 구조가 될 수 있습니다.
