대부분의 개발자는 외부 라이브러리를 사용하는 것에 대해 크게 고민하지 않습니다.
Gradle이나 Maven과 같은 빌드 도구를 사용하면 Maven Central과 같은 공개 저장소에 쉽게 접근할 수 있기 때문입니다.
빌드 도구에 공개 저장소 정보를 설정해두기만 하면 개발자가 특별히 신경쓰지 않아도 필요한 라이브러리를 사용할 수 있습니다.

하지만 모든 개발 환경이 동일한 것은 아닙니다. 
보안 정책이나 네트워크 정책에 따라 외부 인터넷 접근이 제한되는 네트워크 환경에서 개발하는 조직도 적지 않습니다. 
저 역시 이런 환경에서 개발을 하고 있습니다.

자연스럽게 다음과 같은 질문이 생깁니다.

> 개발자가 사용하는 PC나 CI 서버가 외부 인터넷에 직접 접근할 수 없는 폐쇄망 환경에서는
> 오픈소스 라이브러리를 어떻게 가져와서 사용할 수 있을까요?

## 1. 일반적인 개발환경과 폐쇄망 개발환경의 차이

인터넷 사용이 자유로운 일반적인 개발환경에서는 외부 라이브러리를 사용하는 과정이 매우 단순합니다.
개발자가 사용하는 PC나 CI 서버가 인터넷에 직접 접근할 수 있기 때문에, 필요한 라이브러리를 공개 저장소에서 바로 다운로드할 수 있습니다.

이 구조를 단순하게 표현하면 다음과 같습니다.

```nohighlight
Developer / CI
       ↓
Maven Central
       ↓
Dependency Download
```

하지만 폐쇄망 개발환경에서는 상황이 완전히 달라집니다.
보안 정책에 따라 개발 환경에서 외부 인터넷으로의 직접 접근이 차단되기 때문입니다.

```nohighlight
Developer / CI
       ↓
   (차단)
       ↓
Internet / Maven Central
```
이 구조에서는 개발자가 사용하는 PC나 CI 서버가 공개 저장소에 직접 접근할 수 없습니다. 따라서 일반적인 개발환경과 같은 방식으로는 외부 라이브러리를 사용할 수 없습니다.

이 차이로 인해 폐쇄망 개발환경에서는 외부 라이브러리를 내부로 가져와서 관리하는 별도의 방법이 필요합니다.

## 2. 폐쇄망 개발환경에서 외부 라이브러리를 사용하는 문제

앞에서 살펴본 것처럼 폐쇄망 개발환경에서는 외부 인터넷에 직접 접근할 수 없습니다.
따라서 Maven Central과 같은 공개 저장소에서 라이브러리를 바로 다운로드하는 방식은 사용할 수 없습니다.

이 경우 가장 단순하게 생각할 수 있는 방법은
외부에서 라이브러리를 다운로드한 뒤 내부 네트워크로 반입하는 것입니다.

예를 들어 다음과 같은 방식입니다.

```nohighlight
1. 외부 인터넷이 가능한 환경에서 라이브러리 다운로드
2. 파일을 내부 네트워크로 전달
3. 프로젝트에 직접 추가하거나 내부 저장소에 업로드
```

하지만 이러한 방식은 여러 가지 문제를 발생시킵니다.

### 2.1. 라이브러리 반입 과정의 번거로움

필요한 라이브러리가 생길 때마다 외부에서 다운로드하고 내부로 반입해야 합니다.
의존성이 하나만 있는 경우는 괜찮지만, 실제 프로젝트에서는 수십 개 이상의 라이브러리가 함께 사용됩니다.

또한 라이브러리 간의 의존성까지 고려하면
어떤 파일을 함께 가져와야 하는지 파악하는 것 자체도 번거로운 작업이 됩니다.

### 2.2. 팀마다 다른 방식으로 관리되는 문제

중앙에서 관리되는 저장소가 없다면 각 팀이나 개발자가
각자 다른 방식으로 라이브러리를 관리하게 될 가능성이 높습니다.

예를 들어

* 어떤 팀은 특정 버전을 사용하고
* 다른 팀은 다른 버전을 사용하며
* 라이브러리를 프로젝트 내부에 직접 포함시키는 경우도 발생할 수 있습니다

이러한 상황은 장기적으로 유지보수를 어렵게 만듭니다.

### 2.3. 버전 관리와 재현성 문제

외부에서 수동으로 라이브러리를 반입하는 방식은
어떤 버전의 라이브러리를 사용하고 있는지 추적하기 어렵습니다.

또한 시간이 지나면서 동일한 환경을 다시 구성하려고 할 때
같은 라이브러리를 다시 확보하기 어려운 경우도 발생할 수 있습니다.

결과적으로 빌드 재현성이 떨어지게 됩니다.

### 2.4. 보안 및 검증의 어려움

외부에서 가져온 라이브러리를 별도의 검증 없이 사용하는 경우
보안 취약점이나 라이선스 문제를 사전에 인지하기 어렵습니다.

특히 조직 차원에서 사용하는 오픈소스 라이브러리를 관리하려면
어떤 라이브러리가 사용되고 있는지 중앙에서 파악할 수 있어야 합니다.

이처럼 폐쇄망 환경에서 단순히 라이브러리를 “파일로 반입”하는 방식은
운영이 번거롭고, 장기적으로 관리가 어려운 구조를 만들게 됩니다.

따라서 이러한 문제를 해결하기 위해서는
외부 오픈소스 라이브러리를 내부에서 체계적으로 관리할 수 있는 구조가 필요합니다.

## 3. 폐쇄망 개발환경에서 문제 해결방법: 내부 라이브러리 저장소 구축

이러한 문제를 해결하기 위해 많은 조직에서는 **내부 라이브러리 저장소(Artifact Repository)**를 구축하여 운영합니다.
외부 라이브러리를 내부에서 통제된 방식으로 관리하고, 개발 환경에서 편리하고 안전하게 사용할 수 있기 때문입니다.

대표적인 도구로는 `Nexus`나 `Artifactory`와 같은 저장소 관리 시스템이 있습니다.

```nohighlight
+----------------------+
|   Development Zone   |
|----------------------|
| Developer PC         |
| CI/CD Server         |
| Build Server         |
+----------+-----------+
           |
           | internal access only
           v
+----------------------+
|      Trust Zone      |
|----------------------|
| Nexus Repository     |
|  - proxy repo        |
|  - hosted repo       |
|  - group repo        |
+----------+-----------+
           |
           | outbound via proxy only
           v
+----------------------+
|         DMZ          |
|----------------------|
| Forward Proxy        |
| (Outbound Proxy)     |
+----------+-----------+
           |
           | controlled internet access
           v
+----------------------+
|       Internet       |
|----------------------|
| Maven Central        |
| npm registry         |
| PyPI                 |
| Docker Hub           |
+----------------------+
```
