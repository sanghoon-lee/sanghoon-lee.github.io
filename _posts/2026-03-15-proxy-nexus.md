대부분의 개발자는 오픈소스 라이브러리를 사용하는 것에 대해 크게 고민하지 않습니다.
Gradle이나 Maven과 같은 빌드 도구가 Maven Central과 같은 공개 저장소에서 필요한 라이브러리를 찾아서 다운로드해주기 때문입니다.
개발자는 단순히 사용하고 싶은 라이브러리 정보를 빌드 도구의 설정파일에 추가해두기만 하면 됩니다.

하지만 모든 개발 환경이 동일한 것은 아닙니다. 
보안 정책에 따라 외부 인터넷 접근이 제한되는 환경에서 개발해야 하는 경우도 적지 않습니다. 
저 역시 이런 환경에서 개발을 하고 있습니다.

## 1. 일반적인 개발환경과 폐쇄망 개발환경의 차이

인터넷에 직접 접근이 가능한 일반적인 개발환경에서는 오픈소스 라이브러리를 사용하는 과정이 매우 단순합니다.
개발자가 사용하는 PC나 CI 서버가 공개 저장소를 통해서 필요한 라이브러리를 바로 다운로드하는 방식입니다.

이 구조를 단순하게 표현하면 다음과 같습니다.

```nohighlight
개발자 PC / CI 서버
       ↓
외부의 공개 저장소(예: Maven Central)
       ↓
Dependency Download
```

하지만, 폐쇄망 개발환경에서는 상황이 완전히 달라집니다. 외부 인터넷으로의 직접 접근이 차단되기 때문입니다.

이 구조를 단순하게 표현하면 다음과 같습니다.
```nohighlight
개발자 PC / CI 서버
       ↓
     (차단)
       ↓
외부의 공개 저장소(예: Maven Central)
```
이러한 구조에서는 개발자가 사용하는 PC나 CI 서버가 공개 저장소에서 필요한 라이브러리를 다운로드할 수 없습니다.

그러면 자연스럽게 다음과 같은 질문이 생깁니다.

> 개발자가 사용하는 PC나 CI 서버가 외부 인터넷에 직접 접근할 수 없는 폐쇄망 환경에서는
> 오픈소스 라이브러리를 어떻게 가져와서 사용할 수 있을까요?

## 2. 폐쇄망 개발환경에 라이브러리를 수동으로 반입하는 방식의 문제점

가장 단순하게 생각할 수 있는 방법은 인터넷이 되는 환경에서 필요한 라이브러리를 다운로드한 뒤 수동으로 폐쇄망 개발환경으로 반입하는 것입니다.

예를 들어 다음과 같은 방식입니다.

```nohighlight
1. 외부 인터넷이 가능한 환경에서 라이브러리 다운로드
2. 파일을 내부 네트워크로 전달
3. 프로젝트에 직접 추가하거나 내부 저장소에 업로드
```

이런 방식으로 라이브러리를 반입하면 다음과 같은 문제가 발생할 수 있습니다. 

### 2.1. 라이브러리 반입 과정의 번거로움

대부분의 라이브러리는 또 다른 라이브러리들과 복잡한 의존관계를 형성하고 있는 경우가 대부분입니다. 
따라서 필요한 라이브러리뿐만 아니라, 의존성까지 고려해 어떤 라이브러리를 함께 가져와야 하는지 파악해야 합니다.

이 과정은 생각보다 복잡하며, 필요한 라이브러리가 생길 때마다 반복됩니다. 결과적으로 번거롭고 어려운 작업이 반복되면서 개발 생산성을 저하시키게 됩니다.

### 2.2. 버전 관리와 재현성 문제

또한, 어떤 버전의 라이브러리가 조직 내에서 사용되고 있는지 추적하기 어렵게 됩니다. 그래서 이미 과거에 반입된 라이브러리임에도 불구하고, 다른 팀이나 프로젝트에서는 이를 알지 못해 다시 반입하는 일이 발생하기도 합니다.

동일한 라이브러리를 팀마다 서로 다른 버전으로 사용하고 있거나, 라이브러리를 직접 프로젝트 내부에 포함시켜놓아 유지보수를 어렵게 만들기도 합니다. 

### 3. 폐쇄망 개발환경에 내부 라이브러리 저장소 구축이 필요한 이유

위와 같은 문제를 해결하기 위해서 결국 내부로 반입된 라이브러리를 통제하고, 관리할 수 있는 별도의 방법이 필요합니다.
그래서 폐쇄망 개발환경을 사용하는 많은 조직에서는 **내부 라이브러리 저장소(Artifact Repository)**를 구축해서 운영하고 있습니다.

대표적인 도구로는 `Nexus`나 `Artifactory`와 같은 저장소 관리 시스템이 있습니다. 이러한 도구들을 통해 **내부 라이브러리 저장소**를 구축하면 반입된 라이브러리를 중앙에서 관리하고, 조직 내에서 일관된 방식으로 사용할 수 있습니다.

### 4. 폐쇄망 개발환경에서 라이브러리 반입 자동화

**내부 라이브러리 저장소**가 구축되면 개발자는 일반적인 개발환경과 동일하게 라이브러리 정보를 빌드 도구의 설정 파일에 추가해두기만 하면 됩니다.
다만, 공개 저장소가 아닌 내부에 구축된 **내부 라이브러리 저장소**를 바라보도록 설정해야 한다는 차이가 있습니다.

**일반적인 개발환경**

> 개발자 PC / CI 서버 → 공개 저장소(예: Maven Central)

**내부 라이브러리 저장소가 구축된 폐쇄망 개발환경**

> 개발자 PC / CI 서버 → 내부 저장소 → (필요 시) 공개 저장소(예: Maven Central)

개발자는 내부 저장소만 바라보고, 내부 저장소가 필요한 경우 공개 저장소에서 라이브러리를 가져오는 구조입니다. 결과적으로 라이브러리 반입까지 자동화할 수 있습니다. 

그렇지만, 폐쇄망에서 어떻게 **내부 라이브러리 저장소**가 인터넷을 통해서 외부의 공개 저장소에 접근할 수 있을까요?

이 문제를 해결하기 위해 `Forward Proxy` 서버를 활용할 수 있습니다.

`Forward Proxy` 서버를 경유해서 내부 저장소에서 외부 공개 저장소로 나가는 요청을 통제하고, 허용된 경로를 통해 안전하게 라이브러리를 가져올 수 있도록
네트워크를 구성합니다. 

```nohighlight
개발자 PC / CI 서버
       ↓
내부 라이브러리 저장소 - 폐쇄망(Trust Zone)
       ↓
Forward Proxy - 폐쇄망(DMZ)
       ↓ 
외부의 공개 저장소(예: Maven Central) - 인터넷 
       ↓
Dependency Download
```
