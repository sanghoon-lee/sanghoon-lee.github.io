실습은 Oracle VM으로 생성한 가상머신 환경에서 진행했습니다.

Reverse Proxy는 Nginx를 이용하여 구성하고, 요청을 처리할 애플리케이션 서버는 Spring Boot로 구현했습니다.

실습 환경은 다음과 같습니다.

* Oracle VM(Ubuntu Linux)
* Docker
* Spring Boot API 애플리케이션(애플리케이션 서버)
* Nginx

이번 포스팅에서는 Reverse Proxy 구성에 앞서 요청을 처리할 애플리케이션 서버를 먼저 구현하고, Docker 컨테이너로 실행하는 과정까지 정리해보려고 합니다.

Oracle VM에서 가상머신을 생성하고 Docker를 설치하는 과정은 이미 완료된 상태라고 가정합니다.

---

## 1. 애플리케이션 서버 개발

실습을 위해서는 Reverse Proxy로부터 요청을 전달받아 이를 처리할 애플리케이션 서버가 필요합니다.

그래서 Java 기반 프레임워크인 Spring Boot로 애플리케이션 서버를 직접 구현했습니다.

물론, 실제 운영 환경에서는 다양한 기능이 포함된 애플리케이션 서버가 사용될 것입니다.

하지만 이번 학습의 목적은 Reverse Proxy의 동작을 확인하는 것이므로, 애플리케이션 서버의 기능 구현 범위는 요청을 수신하고 응답을 반환하는 단순한 API로 최소화했습니다.

---

프로젝트 생성 정보는 다음과 같습니다.

* Project: Gradle-Groovy
* Language: Java
* Spring Boot: 3.5.14
* Group: sanghoon.study
* Artifact: simple-api
* Packaging: Jar
* Java: 17

의존성은 REST API 구현에 필요한 Spring Web만 추가했습니다.

### 1.2. API 정의

애플리케이션 서버는 Reverse Proxy로부터 전달받은 요청을 처리할 수 있어야 합니다.

이번 실습에서는 요청을 처리한 서버의 이름과 시간을 반환하는 간단한 API를 구현했습니다.

요청 형식은 다음과 같습니다.

**요청**
```http
GET /api/server HTTP/1.1
```

**응답 예시**
```json
{
    "serverName":"api-01",
    "time":"2026-06-05T20:50:34.578004200"
}
```

이 API를 사용하면 다수의 애플리케이션 서버가 동작하는 환경에서도 어떤 서버가 요청을 처리했는지 쉽게 확인할 수 있습니다.

---

### 1.3. 프로젝트 구조

애플리케이션 서버의 프로젝트 구조는 다음과 같습니다.

```nohighlight
src 
 └─ main 
     ├─ java 
     │   └─ sanghoon.study.simpleapi 
     │      ├─ SimpleApiApplication.java 
     │      └─ controller
     │          └─ ApiController.java  
     └─ resources 
         └─ application.yaml
```

프로젝트는 최대한 단순한 구조로 구성했습니다.

이번 실습에서는 앞에서 정의한 API만 제공하면 되므로 별도의 Service나 Repository 계층은 생성하지 않았습니다.

API 요청을 처리하는 ApiController 클래스와 애플리케이션 설정을 위한 application.yaml 파일만 생성했습니다.

---

### 1.4. ApiController 클래스

ApiController 클래스는 /api/server 요청을 처리하도록 구현했습니다.

요청이 수신되면 서버 이름과 현재 시간을 응답으로 반환합니다. 서버 이름은 SERVER_NAME 환경변수를 통해 전달받은 값을 사용하도록 구성했습니다.

**ApiController.java**
```java
package sanghoon.study.simpleapi.controller;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

import java.time.LocalDateTime;
import java.util.Map;

@RestController
@RequestMapping("/api")
public class ApiController {
    @Value("${SERVER_NAME:unknown}")
    private String serverName;

    @GetMapping("/server")
    public Map<String, String> server() {
        return Map.of(
                "serverName", serverName,
                "time", LocalDateTime.now().toString()
        );
    }
}
```

### 1.5. 설정 파일

Spring Boot의 기본 포트는 8080입니다.

이번 실습에서는 애플리케이션 서버의 포트를 8000으로 사용하도록 구성했습니다. 그래서 application.yaml 파일을 다음과 같이 작성했습니다.

**application.yaml**
```yaml
server:
  port: 8000
```

## 2. 애플리케이션 서버 배포 및 실행

Docker를 이용하면 애플리케이션 서버를 독립된 컨테이너 형태로 구동할 수 있습니다. 이러한 특성은 다수의 애플리케이션 서버가 필요한 실습 환경을 구성할 때도 유용합니다.

이제 지금까지 구현한 애플리케이션 서버를 Docker 이미지로 생성하고 컨테이너로 실행해보겠습니다.

---

### 2.1. 소스코드 Clone

애플리케이션 서버의 개발은 Windows 환경에서 진행했습니다. 

반면 실습 환경은 Ubuntu 리눅스가 설치된 가상머신에 구성했습니다. Docker도 가상머신에 설치되어 있습니다.

따라서 Docker 이미지를 생성하기 전에 Github 저장소에 등록해놓은 애플리케이션 서버의 소스코드를 가상머신으로 가져와야 했습니다.

소스코드는 Github 저장소에 등록해놓았습니다. 저장소 주소는 다음과 같습니다.

* [https://github.com/sanghoon-lee/simple-api.git](https://github.com/sanghoon-lee/simple-api.git)


가상머신에서 다음 명령어를 실행해서 소스코드를 가져왔습니다. 
```bash
$ git clone https://github.com/sanghoon-lee/simple-api.git
```

---

### 2.2. Dockerfile 작성

Docker 이미지를 생성하려면 프로젝트 루트 경로에 Dockerfile을 작성해야 합니다.

Dockerfile은 Docker 이미지 생성에 필요한 정보를 정의하는 설정 파일입니다. 어떤 운영체제 이미지를 사용할지와 애플리케이션을 어떻게 실행할지 등과 같은 정보가 포함됩니다.

애플리케이션을 JAR 파일로 빌드하고 Docker 이미지 내부에서 실행하도록 구성했습니다.

**Dockerfile**

```dockerfile
FROM eclipse-temurin:17-jre

WORKDIR /app

COPY build/libs/simple-api-0.0.1-SNAPSHOT.jar simple-api.jar

ENTRYPOINT ["java", "-jar", "simple-api.jar"]
```

각 설정의 의미는 다음과 같습니다.

* eclipse-temurin:17-jre 이미지를 기반으로 컨테이너를 생성합니다.
* WORKDIR은 애플리케이션이 실행될 작업 디렉터리를 지정합니다.
* COPY는 빌드된 JAR 파일을 컨테이너 내부로 복사합니다.
* ENTRYPOINT는 컨테이너 시작 시 Spring Boot 애플리케이션을 실행합니다.

> eclipse-temurin:17-jre는 Java 17 JRE가 포함된 Docker 이미지입니다. 이 이미지를 사용하면 별도의 Java 설치 과정 없이 Spring Boot 애플리케이션을 실행할 수 있습니다.

---

### 2.3. 애플리케이션 빌드

앞에서 작성한 Dockerfile은 빌드 결과물인 JAR 파일을 Docker 이미지 내부로 복사하도록 구성했습니다. 따라서 Docker 이미지를 생성하기 전에 먼저 애플리케이션을 빌드해야 합니다.

다음의 명령어를 실행해서 애플리케이션을 빌드했습니다.

```bash
$ ./gradlew clean build
```

빌드가 완료되면 build/libs 디렉터리에 JAR 파일이 생성됩니다.

```nohighlight
build
 └─ libs
     └─ simple-api-0.0.1-SNAPSHOT.jar
```

Dockerfile의 COPY 명령은 생성된 JAR 파일을 Docker 이미지 내부로 복사하는 역할을 수행합니다.

> **트러블슈팅: gradlew 실행 권한 오류**
>
> 가상머신에서 애플리케이션 빌드를 위해 `./gradlew clean build` 명령을 실행했을 때 `command not found` 오류가 발생했습니다.
>
> 확인해보니 `gradlew` 파일에 실행 권한이 부여되지 않은 상태였습니다.  
>
> Linux 환경에서는 스크립트 파일에 실행 권한이 있어야 실행할 수 있습니다. 하지만 Windows에서 생성한 프로젝트를 Linux 환경으로 옮기면 실행 권한이 유지되지 않는 경우가 있습니다.
>
> 그래서 아래 명령어를 통해 권한을 추가한 뒤 빌드를 진행했습니다.
>
> ```bash
> chmod +x gradlew
> ```
>
> 이후 `./gradlew clean build` 명령이 정상적으로 실행되었습니다.

---

### 2.4. Docker 이미지 생성

애플리케이션 빌드가 완료되었으면 Docker 이미지를 생성할 수 있습니다.

Docker 이미지는 컨테이너 실행에 필요한 파일과 설정 정보를 포함하는 패키지입니다. 앞에서 작성한 Dockerfile을 기반으로 이미지를 생성했습니다.

다음 명령어를 실행합니다.

```bash
$ docker build -t simple-api .
```

명령어의 의미는 다음과 같습니다.

* `docker build` : Docker 이미지를 생성합니다.
* `-t simple-api` : 생성할 이미지의 이름을 지정합니다.
* `.` : 현재 디렉터리의 Dockerfile을 사용하여 이미지를 생성합니다.

이미지 생성이 완료되면 다음 명령어를 통해 생성된 이미지를 확인할 수 있습니다.

```bash
$ docker images
```

아래는 제가 사용한 가상머신에서 확인한 결과입니다.

```nohighlight
IMAGE               ID             DISK USAGE   CONTENT SIZE   EXTRA
simple-api:latest   50ac61d202ac        465MB          128MB
```

simple-api 이미지가 정상적으로 생성된 것을 확인할 수 있습니다.

Docker 이미지는 컨테이너 실행을 위한 템플릿 역할을 합니다. 다음 단계에서는 생성한 이미지를 이용하여 실제 애플리케이션 서버 컨테이너를 실행해보겠습니다.

---

### 2.5. Docker 컨테이너 실행

생성된 Docker 이미지는 다음 명령어를 사용해서 실행할 수 있습니다.

```bash
$ docker run -d \
  --name api-01 \
  -e SERVER_NAME=api-01 \
  -p 8001:8000 \
  simple-api
```

각 옵션의 의미는 다음과 같습니다.

* `-d` : 컨테이너를 백그라운드에서 실행합니다.
* `--name api-01` : 컨테이너 이름을 api-01로 지정합니다.
* `-e SERVER_NAME=api-01` : SERVER_NAME 환경변수를 설정합니다.
* `-p 8001:8000` : 호스트의 8001 포트를 컨테이너의 8000 포트와 연결합니다.
* `simple-api` : 실행할 Docker 이미지 이름입니다.

다음 명령어를 사용해서 컨테이너가 정상적으로 실행되었는지 확인할 수 있습니다.

```bash
$ docker ps
```

아래는 제가 사용한 가상머신에서 확인한 결과입니다.

```nohighlight
CONTAINER ID   IMAGE        COMMAND                  CREATED          STATUS          PORTS                                         NAMES
85b2de399fc1   simple-api   "java -jar simple-ap…"   19 seconds ago   Up 18 seconds   0.0.0.0:8001->8000/tcp, [::]:8001->8000/tcp   api-01
```

api-01 컨테이너가 정상적으로 실행 중이며 호스트의 8001 포트와 연결된 것을 확인할 수 있습니다.

컨테이너가 실행되었으므로 curl 명령어를 이용해 API를 호출해봤습니다.

이번에는 애플리케이션 서버가 가상머신에 설치된 Docker 컨테이너 내부에서 실행 중입니다. 따라서 가상머신의 IP와 Docker 포트 매핑 정보를 이용해 요청을 전송했습니다.

**요청**

```http
curl http://192.168.56.11:8001/api/server
```

SERVER_NAME 환경변수로 설정한 api-01 값이 정상적으로 반환되는 것을 확인할 수 있었습니다.

**응답**

```json
{
    "time":"2026-06-06T05:59:55.374174811",
    "serverName":"api-01"
}
```

## 3. 마치며

지금까지 애플리케이션 서버를 구현하고 Docker 이미지로 생성해서 컨테이너로 실행하는 과정까지 살펴봤습니다.

애플리케이션 서버는 Docker 컨테이너 형태로 실행 중이며, API 요청을 받으면 정상적으로 처리할 수 있는 상태입니다. 

현재 구조에서는 클라이언트가 애플리케이션 서버에 직접 요청을 보내고, 응답을 받을 수 있습니다. 

하지만 실제 운영 환경에서는 애플리케이션 서버를 외부에 직접 노출하기보다는 Reverse Proxy를 앞단에 배치하는 구성이 일반적입니다.

이를 통해 애플리케이션 서버 보호, 접근 제어, SSL 종료 등의 기능을 보다 효율적으로 적용할 수 있습니다.

다음 포스팅에서는 Nginx를 이용해 Reverse Proxy 서버를 구성하고, 클라이언트와 애플리케이션 서버 사이에서 요청을 중계하는 구조를 만들어보도록 하겠습니다.
