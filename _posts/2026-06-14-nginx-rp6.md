Reverse Proxy를 구성하여 애플리케이션 서버를 외부로부터 보호하고, 로드밸런싱을 통해 여러 서버에 요청을 분산하는 기능을 직접 확인해봤습니다.

실제 운영 환경에서 Reverse Proxy는 이보다 더 많은 역할을 수행합니다. 대표적인 기능으로 SSL 종료(SSL Termination)가 있습니다.

SSL 종료는 HTTPS 통신에 필요한 TLS 연결 처리와 암호화·복호화 작업을 Reverse Proxy가 대신 수행하는 방식입니다.

이를 통해 애플리케이션 서버는 HTTPS 설정 없이도 HTTP 기반으로 서비스를 제공할 수 있으며, 인증서 관리 또한 Reverse Proxy에서 일원화할 수 있습니다.

이번 포스팅에서는 Nginx를 HTTPS로 구성하고 SSL 종료 기능이 실제로 어떻게 동작하는지 검증해보겠습니다.

---

## 1. SSL 종료(SSL Termination) 실습 준비

HTTPS는 클라이언트와 서버 간의 통신 내용을 암호화하여 전송하는 방식입니다.

이를 위해 서버는 인증서를 보유해야 하며, HTTPS 요청을 처리할 때마다 암호화 및 복호화 작업을 수행해야 합니다.

> 참고: 일반적으로 SSL 인증서라고 부르지만 사실 TLS 인증서라는 표현이 더 정확합니다.

만약 모든 애플리케이션 서버가 직접 HTTPS를 처리하도록 구성한다면 서버마다 인증서를 관리해야 하고, HTTPS 설정도 각각 적용해야 합니다.

이러한 문제를 해결하기 위해 실제 운영 환경에서는 Reverse Proxy가 HTTPS 통신을 처리하는 경우가 많습니다.

Reverse Proxy가 클라이언트와의 HTTPS 통신을 담당하고, 내부의 애플리케이션 서버에는 HTTP로 요청을 전달하는 방식이 바로 SSL 종료(SSL Termination)입니다.

```nohighlight
Client
  │ HTTPS
  ▼
Reverse Proxy
  │ HTTP
  ▼
Application Server
```

즉 클라이언트와 Reverse Proxy 구간에서는 HTTPS가 사용되지만, Reverse Proxy와 애플리케이션 서버 사이에서는 HTTP가 사용되는 것입니다.

SSL 종료를 사용하면 인증서를 Reverse Proxy에서 일원화하여 관리할 수 있으며, 애플리케이션 서버는 HTTPS 설정 없이도 서비스를 제공할 수 있습니다.

또한 TLS 연결 처리에 필요한 부담을 Reverse Proxy가 담당하므로 애플리케이션 서버는 비즈니스 로직 처리에 집중할 수 있습니다.

---

### 1.1. SSL 인증서 생성

SSL 종료 기능을 검증하려면 HTTPS 통신에 사용할 SSL 인증서가 필요합니다. 실제 운영 환경에서는 공인 인증기관(CA)이 발급한 인증서를 사용해야 하지만, 이번 실습에서는 동작 확인을 위해 자체 서명(Self-Signed) 인증서를 사용했습니다.

자체 서명 인증서는 아래 명령을 실행하면 생성할 수 있습니다.

```bash
$ mkdir certs

$ openssl req -x509 \
  -nodes \
  -days 365 \
  -newkey rsa:2048 \
  -keyout certs/nginx.key \
  -out certs/nginx.crt
```

실행이 완료되면 다음과 같은 파일이 생성됩니다.

```nohighlight
certs
 ├─ nginx.crt
 └─ nginx.key
```

* nginx.crt : 서버 인증서
* nginx.key : 개인 키

> 자체 서명 인증서를 사용하기 때문에 브라우저에서 신뢰할 수 없는 인증서 경고가 표시될 수 있습니다.

---

### 1.2. Nginx 설정 변경

생성한 인증서를 사용하도록 아래와 같이 nginx.conf 파일을 수정했습니다.

```nohighlight
http {
    upstream backend {
        server api-01:8000;
        server api-02:8000;
    }

    server {

        listen 443 ssl;

        ssl_certificate     /etc/nginx/certs/nginx.crt;
        ssl_certificate_key /etc/nginx/certs/nginx.key;

        location / {
            proxy_pass http://backend;
        }
    }
}
```

기존에는 80 포트에서 HTTP 요청을 수신했지만, 이제는 443 포트에서 HTTPS 요청을 수신하도록 변경했습니다.

또한 ssl_certificate와 ssl_certificate_key 설정을 통해 생성한 인증서를 Nginx에 등록했습니다.

애플리케이션 서버는 별도의 HTTPS 설정 없이 기존과 동일하게 HTTP 기반으로 동작합니다.

---

### 1.3. Reverse Proxy 서버 재구성

변경된 Nginx의 설정이 적용되도록 Reverse Proxy 서버(nginx-rp)를 재구성해야 합니다. 우선 기존 컨테이너를 제거했습니다.

```bash
$ docker rm -f nginx-rp
```

그리고 아래와 같이 인증서 디렉터리를 마운트하여 컨테이너를 다시 실행했습니다.

```bash
$ docker run -d \
  --name nginx-rp \
  --network rp-network \
  -p 443:443 \
  -v /home/sanghoon/nginx/nginx.conf:/etc/nginx/nginx.conf:ro \
  -v /home/sanghoon/nginx/certs:/etc/nginx/certs:ro \
  nginx
```

## 2. 실습 : SSL 종료 기능 검증

SSL 인증서가 적용되었고, Reverse Proxy 서버는 443 포트에서 HTTPS 요청을 수신하도록 구성되었습니다.

이제 80 포트를 사용하는 HTTP 통신으로는 요청을 보낼 수 없습니다. Reverse Proxy가 443 포트만 노출하고 있기 때문입니다.

```bash
$ curl http://192.168.56.11/api/server

curl: (7) Failed to connect to 192.168.56.11 port 80 after 0 ms: Couldn't connect to server
```

반면 443 포트를 사용하는 HTTPS 통신으로는 Reverse Proxy에 요청을 보낼 수 있었습니다. 다만 실습 환경에서는 자체 서명 인증서를 사용하고 있기 때문에 curl 명령에 -k 옵션을 추가해야 합니다.

```bash
$ curl -k https://192.168.56.11/api/server
```

요청을 보내면 아래와 같이 정상적인 응답이 반환되었습니다.

```json
{
    "time":"2026-06-14T11:59:21.023254620",
    "serverName":"api-02"
}
```

현재 애플리케이션 서버(api-01, api-02)는 HTTPS 설정을 전혀 적용하지 않은 상태이며, 여전히 8000 포트에서 HTTP로만 동작하고 있습니다.


```nohighlight
client 
  │ HTTPS 
  ▼ 
Reverse Proxy(nginx-rp) 
  │ HTTP 
  ▼ 
애플리케이션 서버(api-01, api-02)
```

그럼에도 HTTPS 요청이 정상적으로 처리된다는 것은 Reverse Proxy가 클라이언트와의 HTTPS 통신을 처리한 뒤 내부의 애플리케이션 서버에는 HTTP로 요청을 전달하고 있음을 의미합니다.

이를 통해 SSL 종료가 정상적으로 동작하고 있다는 사실을 확인할 수 있었습니다.

실제 운영 환경에서 이러한 SSL 종료 방식을 사용하면 인증서를 Reverse Proxy에서 일괄 관리할 수 있으며, 애플리케이션 서버는 HTTPS 설정 없이 비즈니스 로직 처리에만 집중할 수 있습니다.

## 3. 추가: HTTP → HTTPS 강제 리다이렉트

Reverse Proxy에 HTTP로 요청이 들어오면 HTTPS로 강제 리다이렉트하도록 구성할 수 있습니다.

### 3.1. Nginx 설정 변경

우선 HTTP로 요청이 들어오면 Reverse Proxy가 301(Moved Permanently) 상태코드와 함께 HTTPS 주소를 반환하도록 설정을 변경해야 합니다. 

클라이언트(브라우저 등)는 상태코드가 301로 반환되면 응답에 포함된 Location 헤더를 확인한 뒤 해당 HTTPS 주소로 리다이렉션하게 됩니다.

이를 위해 아래와 같이 nginx.conf 파일을 수정했습니다.

```nohighlight
http {

    upstream backend {
        server api-01:8000;
        server api-02:8000;
    }

    server {
        listen 80;
        return 301 https://$host$request_uri;
    }

    server {

        listen 443 ssl;

        ssl_certificate     /etc/nginx/certs/nginx.crt;
        ssl_certificate_key /etc/nginx/certs/nginx.key;

        location / {
            proxy_pass http://backend;
        }
    }
}
```

새로운 server 블록을 추가해서 80 포트로 요청이 들어오면 상태코드 301과 리다이렉트될 주소가 함께 반환되도록 설정을 변경했습니다.

---

### 3.2. Reverse Proxy 재구성

Reverse Proxy 서버(nginx-rp)를 다시 재구성해서 변경된 Nginx의 설정이 적용되도록 해야 합니다. 우선 기존 컨테이너를 제거했습니다.

```bash
$ docker rm -f nginx-rp
```

그리고 아래와 같이 컨테이너를 다시 실행했습니다.

```bash
$ docker run -d \
  --name nginx-rp \
  --network rp-network \
  -p 443:443 \
  -p 80:80 \
  -v /home/sanghoon/nginx/nginx.conf:/etc/nginx/nginx.conf:ro \
  -v /home/sanghoon/nginx/certs:/etc/nginx/certs:ro \
  nginx
```

HTTP 요청을 수신하고 HTTPS로 리다이렉트하기 위해 컨테이너 실행 시 80 포트와 443 포트를 모두 매핑했습니다.

---

### 3.3. 동작 확인

HTTP로 요청을 보내고 HTTPS로 강제 리다이렉션되는지 확인하기 위해 이번에는 -I 옵션을 사용해서 curl 명령을 실행했습니다.

```bash
$ curl -I http://192.168.56.11/api/server
```

http://192.168.56.11/api/server 요청에 301 상태코드와 리다이렉션될 주소가 반환되는 것을 확인할 수 있었습니다.

```http
HTTP/1.1 301 Moved Permanently
Server: nginx/1.31.1
Date: Sun, 14 Jun 2026 12:32:37 GMT
Content-Type: text/html
Content-Length: 169
Connection: keep-alive
Location: https://192.168.56.11/api/server
```

실제 리다이렉션이 되는지 -L 옵션을 사용해서 curl 명령을 다시 실행해봤습니다. 

```bash
$ curl -k -L http://192.168.56.11/api/server
```

이때도 정상적으로 응답이 반환되는 것을 확인할 수 있었습니다.

```json
{
    "time":"2026-06-14T12:36:46.311165528",
    "serverName":"api-01"
}
```

HTTP 요청이 HTTPS로 자동 전환되는 것까지 확인함으로써 Reverse Proxy가 SSL 종료뿐만 아니라 HTTPS 사용을 강제하는 역할도 수행할 수 있다는 점을 확인할 수 있었습니다.

실제 운영 환경에서는 이러한 구성을 통해 모든 사용자 요청을 HTTPS로 보호하고, 인증서 역시 Reverse Proxy에서 일괄 관리하는 경우가 많습니다.

다음 포스팅에서는 Reverse Proxy가 웹 서버로서 정적 콘텐츠를 직접 제공하는 기능도 수행할 수 있는지 검증해보겠습니다.
