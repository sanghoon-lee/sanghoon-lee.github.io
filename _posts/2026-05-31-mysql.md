최근 웹 보안을 공부하면서 실습 환경 구축이 필요했습니다. 

그래서 개인 노트북에 Oracle VM으로 가상머신을 생성하고, 도커로 필요한 프로그램들을 하나씩 설치하고 있었습니다.

MySQL도 필요한 프로그램 중 하나였습니다. 하지만 MySQL 컨테이너가 예상과 다르게 정상적으로 실행되지 않았습니다.

<img class="main-image" src="/assets/images/mysql.jpg" alt="MySQL">

여러 원인을 의심하며 로그를 추적한 결과, 도커 데몬 접근 권한 문제와 가상 머신의 디스크 공간 부족이 원인이었습니다.

이번 포스팅을 통해 MySQL 컨테이너가 실행되지 않았던 원인을 단계적으로 추적하고 해결한 과정을 정리해보겠습니다.

---

## 1. MySQL 컨테이너 생성과 비정상적인 종료

MySQL을 실행하기 위해서 다음과 같이 컨테이너를 생성했습니다.

```bash
$ docker run --name mysql \
  -e MYSQL_ROOT_PASSWORD=password \
  -p 3306:3306 \
  -v /home/sanghoon/mysql:/var/lib/mysql \
  -d mysql:9.7
```

하지만 `docker ps` 명령으로 확인해보니 컨테이너는 정상적으로 실행되지 않고 즉시 종료되었습니다.

원인을 파악하기 위해 로그부터 확인해보기로 했습니다.

---

## 2. 문제#1: 도커 데몬의 접근 권한 문제

아래의 명령으로 컨테이너가 남긴 로그를 조회했습니다.

```bash
$ docker logs mysql
```

하지만 컨테이너가 아닌 도커 데몬에서 남긴 메시지만 확인할 수 있었습니다.  

```text
permission denied while trying to connect to the docker API at unix:///var/run/docker.sock
```

메시지 내용은 도커 데몬에 접근할 권한이 없다는 것이었습니다.

즉, MySQL 컨테이너의 문제가 아니라 도커 데몬에 접근할 수 없는 상태였습니다. 따라서 컨테이너 로그를 확인하는 것조차 불가능한 상황이었습니다.

따라서 도커 데몬의 접근 권한 문제부터 해결해야 했습니다.

우선 사용자를 도커 그룹에 추가했습니다.

```bash
$ sudo usermod -aG docker $USER
```

그 후 새로운 터미널 세션을 열고 권한 문제는 해결된 것을 확인했습니다. 하지만 MySQL 컨테이너는 여전히 정상적으로 실행되지 않았습니다.

---

## 3. 문제#2: 디스크 공간 부족

로그를 다시 조회했습니다. 도커 데몬의 접근 권한 문제가 해결이 되어서 이번에는 MySQL 컨테이너가 남긴 메시지를 확인할 수 있었습니다.

```text
mysqld: Error writing file '/var/lib/mysql/auto.cnf'
(OS errno 28 - No space left on device)
```

**No space left on device**는 디스크에 더 이상 데이터를 기록할 수 없다는 의미입니다. 이 메시지가 바로 문제의 핵심이었습니다.

MySQL은 초기화 과정에서 auto.cnf 파일을 생성해야 하는데, 디스크 공간 부족으로 인해 파일 생성에 실패했고 결국 컨테이너가 종료된 것이었습니다.

우선 디스크 사용량부터 점검했습니다.

```bash
$ df -h /home/sanghoon/mysql
```

결과는 다음과 같았습니다.

```text
Filesystem      Size  Used Avail Use%
/dev/sda1        12G   12G     0 100%
```
 
테스트 환경을 구축하면서 다양한 도커 이미지를 다운로드했고, 그 결과 가상머신에 할당된 디스크 공간이 모두 소진된 것입니다.

그래서 일단 꼭 필요한 도커 이미지만 남기고, 나머지는 삭제해야만 했습니다.

디스크 여유 공간이 확보되면서 컨테이너도 정상적으로 실행되는 것을 확인할 수 있었습니다.

---

## 4. 마무리

이번 경험을 통해 하나의 오류 메시지만 보고 성급하게 원인을 단정하면 안 된다는 점을 다시 한번 느낄 수 있었습니다.

처음에는 MySQL 컨테이너 자체에 문제가 있다고 생각했습니다. 하지만 실제로는 도커 데몬의 접근 권한 문제와 디스크 공간 부족 문제가 함께 존재하고 있었습니다.

도커 데몬의 접근 권한 문제를 해결한 후에야 MySQL이 남긴 로그를 확인할 수 있었고, 그 과정에서 디스크 공간 부족이라는 진짜 원인을 발견할 수 있었습니다.

트러블슈팅 과정에서는 눈에 보이는 첫 번째 오류만 해결하는 것이 아니라, 오류 메시지를 하나씩 확인하며 원인을 좁혀 나가는 과정이 중요합니다.

특히 컨테이너 환경에서는 애플리케이션 로그뿐만 아니라 도커 컨테이너의 상태, 운영체제의 디스크 사용량, 네트워크 설정 등 주변 환경도 함께 점검해야 한다는 점을 다시 한번 배울 수 있었습니다.

이번 경험은 "첫 번째 오류가 항상 진짜 원인은 아니다"라는 점을 다시 한번 확인할 수 있었던 좋은 학습 기회였습니다.
