애플리케이션을 설계할 때 `인증(Authentication)`과 `인가(Authorization)`는 필수적인 보안 요소입니다.

* 인증(Authentication) : 사용자가 본인임을 증명하는 과정
* 인가(Authorization) : 인증된 사용자가 무엇을 할 수 있는지를 결정하는 과정

이 두 개념을 설명하다 보면 자연스럽게 토큰(Token) 이라는 용어가 등장합니다.

그렇다면 토큰은 무엇이고, 또 JWT는 왜 등장하게 되었을까요?

## 토큰(Token)

토큰은 사전적으로 “증표”, “표식”이라는 의미를 가집니다. `인증` 관점에서는 다음과 같이 정의할 수 있습니다.

> 서버가 `인증` 결과를 표현하기 위해 발급하는 증표

사용자가 `인증`에 성공하면 서버는 해당 사용자의 신원을 확인합니다. 그리고 이후 요청에서도 그 `인증` 결과를 사용할 수 있도록 어떤 형태의 값을 발급합니다.

이 값이 바로 토큰입니다.

즉, 토큰은 “이미 인증이 완료되었다”는 사실을 반복적으로 증명하기 위한 수단입니다.

토큰은 다양한 형태를 가질 수 있습니다.

* 단순 난수 문자열
* 세션 ID
* 구조화된 문자열

중요한 점은 토큰은 단순 문자열이 아니라, `인증` 결과를 표현하는 매개체라는 것입니다.

## 세션(Session)과 토큰(Token)의 차이

JWT를 이해하려면 세션과 토큰이 어떤 차이가 있는지를 알아야합니다.

### 세션(Session)

세션은 서버가 클라이언트의 `인증` 상태를 직접 보관하는 방식입니다.

**세션(Session) 기반 인증 구조**

1. 로그인 성공
2. 서버가 세션 생성
3. 세션 정보를 서버 저장소에 보관
4. 클라이언트는 세션 ID만 전달
5. 서버는 세션 저장소를 조회하여 인증 확인

즉,

세션은 인증 상태를 서버가 보관하는 Stateful 구조입니다.

**토큰(Token) 기반 인증 구조**

반면, 토큰 기반 구조에서는 인증 상태를 서버가 보관하지 않습니다.

1. 로그인 성공
2. 서버가 토큰 발급
3. 클라이언트가 토큰을 보관
4. 요청 시마다 토큰 전달
5. 서버는 토큰 자체를 검증

즉,

토큰 기반 구조는 인증 상태를 클라이언트가 보관하는 Stateless 방식입니다.

이 차이는 단순 구현 차이가 아니라, 아키텍처 방향성의 차이입니다.

## JWT(JSON Web Token)

JWT는 토큰의 한 종류입니다.

정확히는, JSON 기반으로 구성된 Self-contained Token 표준(RFC 7519)입니다. Self-contained라는 의미는
토큰 자체에 `인증`과 `인가` 판단에 필요한 정보가 포함되어 있다는 뜻입니다.

JWT는 단순 난수 문자열이 아니라, 구조화된 데이터를 포함하는 토큰입니다.

아래는 테스트를 위해서 생성해 본 JWT입니다.

```nohighlight
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJ1c2VyIiwiaWF0IjoxNzcyMjQyNjc5LCJleHAiOjE3NzIyNDYyNzl9.i7vBINqbjZ2G_e6zGrYp9oTNSt-Pmb-hOaARX3hXg-g
```

JWT는 다음과 같이 세 부분으로 구성됩니다.

```nohighlight
Header.Payload.Signature
```
BASE64로 인코딩된 문자열이고, 각각의 영역은 점(.)으로 구분됩니다.

| 구분 | 인코딩된 문자열 |
| --- | --- |
| Header | eyJhbGciOiJIUzI1NiJ9 |
| Payload |eyJzdWIiOiJ1c2VyIiwiaWF0IjoxNzcyMjQyNjc5LCJleHAiOjE3NzIyNDYyNzl9 |
| Signature | i7vBINqbjZ2G_e6zGrYp9oTNSt-Pmb-hOaARX3hXg-g |

위의 JWT 문자열을 디코딩해보면 아래와 같은 결과를 얻을 수 있습니다.
  
**디코딩된 Header 문자열** 
```json
{
  "alg":"HS256"
}
```

Header에는 토큰이 어떤 알고리즘으로 서명되었는지에 대한 정보가 포함되어 있습니다.

**디코딩된 Payload(Claim) 문자열**

```json
{
  "sub":"user",
  "iat":1772242679,
  "exp":1772246279
}
```

Payload 영역에는 토큰이 무엇을 증명하고 있는지에 대한 선언을 담고 있는 Claim이라는 정보가 들어갑니다. Claim에는 아래와 같이 다양한 정보가 포함될 수 있습니다.

Claim의 종류

1. Registered Claim
    * iss (issuer)
    * sub (subject)
    * exp (expiration)
    * iat (issued at)
    * nbf (not before)
2. Public Claim
    * role
    * userId
    * tenantId 등
3. Private Claim
    * 특정 시스템 내부 전용 정보

Claim은 단순 데이터 필드가 아닙니다.

어떤 정보를 Claim에 포함할 것인가는
토큰 크기, 보안 정책, 시스템 결합도에 영향을 주는 설계 요소입니다.

**디코딩된 Signature 문자열**

```nohighlight
 ڛ)Jߏ9_xW
```
Signature는 토큰 위조를 방지하기 위한 서명 값입니다. 서명은 다음과 같은 방식으로 생성됩니다.

```nohighlight
HMACSHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  secretKey
)
```

서명 값 검증으로 서버는 다음의 사실을 확인할 수 있습니다.

* 토큰이 변조되지 않았는가?
* 신뢰할 수 있는 서버가 발급한 것인가?

여기서 중요한 점이 있습니다.

JWT는 암호화 토큰이 아니라, 서명 기반 무결성 검증 토큰이라는 것입니다. BASE64 URL로 인코딩되어 있기 때문에, 누구나 디코딩이 가능합니다. 하지만, 서명 기반이기 때문에 내용을 마음대로 변조할 수는 없습니다.

## 정리

JWT는 단순 문자열 포맷이 아니라,
Stateless 인증 구조를 선택했을 때 등장하는 설계 결과물입니다.

중요 내용은 다음과 같습니다.

* 토큰은 인증 결과를 표현하는 증표이다.
* 세션은 인증 상태를 서버가 보관하는 Stateful 방식이다.
* 토큰 기반 구조는 인증 상태를 클라이언트가 보관하는 Stateless 방식이다.
* JWT는 JSON 기반의 Self-contained Token 표준이다.
* Claim은 토큰이 주장하는 인증 정보이다.
* Signature는 토큰의 무결성을 보장한다.
