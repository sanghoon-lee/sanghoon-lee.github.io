애플리케이션에서 `인증(Authentication)`을 이야기할 때, 개발자들은 자연스럽게 **토큰**이라는 단어를 사용합니다.

근데 토큰이 뭔가요? 저도 평소 **토큰**이란 용어를 많이 사용하는데, 그것이 정확히 무엇인지는 깊게 생각해보지 않았습니다. 대충 뭔지는 알겠지만, 말로 설명하기는 어려웠습니다. 단순히 “인증 수단” 혹은 "인증 문자열"이라고 설명하기에는 뭔가 부족해보이기도 합니다.
 
## 토큰(Token)의 개념

**토큰**은 사전적으로 `“증표”`, `“표식”`, `“대체물”`을 의미합니다. 애플리케이션의 `인증` 관점에서는 토큰을 다음과 같이 정의할 수 있습니다.

> 서버가 인증 결과를 증명하기 위해 발급하는 증표

**토큰**은 다음과 같은 형태를 가질 수 있습니다.

* 단순 난수 문자열
* 세션 ID
* 구조화된 문자열

즉, **토큰**은 단순 문자열이 아니라 **인증 결과를 표현하는 매개체**입니다.

## 토큰의 필요성

로그인은 대표적인 `인증` 수단입니다. 그러나 로그인에 성공한 이후에도 인증이 필요한 요청은 계속 발생할 수 있습니다.

로그인은 보통 한번만 수행합니다. 서비스를 이용하는 사용자에게 매 요청마다 아이디와 비밀번호를 입력하라고 요구하는 것이 현실적이지 않기 때문입니다. 따라서, `인증` 결과를 재사용할 수 있는 형태가 반드시 필요합니다. 

이때, 사용되는 것이 **토큰**입니다. **토큰**을 활용해서 **“이미 인증이 완료되었다”**는 사실을 증명할 수 있습니다.

> 토큰은 서버가 검증 가능한 **“자기 완결적 인증 정보(Self-contained authentication data)”**입니다.

## 세션(Session)의 개념

**토큰**과 함께 많이 언급되는 용어가 세션입니다. **세션**은 무엇인가요? 쉽게 말하자면, 세션은 서버가 클라이언트의 상태를 저장하는 메커니즘입니다.

**세션** 기반의 `인증` 구조는 보통 다음과 같이 동작합니다.

1. 사용자가 로그인 정보 입력 
2. 서버에서 로그인 검증 후, 세션을 생성
3. 세션 정보를 서버 메모리나 저장소에 보관
4. 세션 ID가 클라이언트의 쿠키로 전달

이후 요청마다 서버는 세션 저장소를 조회해 인증을 확인합니다. 즉, 세션은 인증 상태를 서버가 보관하는 방식입니다.

## 토큰 vs 세션 기반의 인증 방식 차이

| 구분       | 토큰 기반 | 세션 기반 |
| -------- | ---------- | -------------- |
| 인증 상태 보관 |  클라이언트          | 서버         |
| 서버 저장소   | 불필요(Stateless) | 필요         | 
| 확장성      | 상대적으로 유리      | 세션 공유 필요   | 
| 검증 방식    | 토큰 자체 검증       | 세션 조회      | 

**토큰** 기반의 `인증` 구조에서는 인증 상태를 서버가 저장하지 않습니다. 대신, 인증 결과를 **토큰** 안에 담아 클라이언트가 보관합니다. 그리고 서버는 매 요청마다 토큰을 검증합니다.

즉, **토큰**은 인증 상태를 서버에서 클라이언트로 이동시킨 설계인 것입니다. 이를 단순 구현 방식의 차이가 아니라,
아키텍처 방향성의 차이로 볼 수도 있습니다.

## JWT(JSON Web Token)의 개념

JWT는 **토큰**의 한 종류입니다. 정확히는,
JSON 기반의 Self-contained Token 표준(RFC 7519) 입니다. Self-contained라는 의미는 다음과 같습니다. 토큰 자체에 인증과 인가 판단에 필요한 정보가 포함되어 있다.

JWT는 단순 문자열이 아닌, 구조화된 데이터를 포함하는 토큰입니다.

JWT는 다음과 같이 세 부분으로 구성됩니다.

```nohighlight
Header.Payload.Signature
```

**예시**

> eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJ1c2VyIiwiaWF0IjoxNzcyMjQyNjc5LCJleHAiOjE3NzIyNDYyNzl9.i7vBINqbjZ2G_e6zGrYp9oTNSt-Pmb-hOaARX3hXg-g


## JWT의 구성

### Header 

**예시**
```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

* alg: 서명 알고리즘
* typ: 토큰 타입

### Payload(Claim)

Payload 영역에는 토큰이 무엇을 증명하고 있는지에 대한 선언을 담고 있는 Claim이라는 정보가 들어갑니다.

**예시**
```json
{
  "sub": "user123",
  "role": "ADMIN",
  "exp": 1710000000
}
```

Claim의 종류

1. Registered Claim
    * iss (issuer)
    * sub (subject)
    * exp (expiration)
    * iat (issued at)
    * nbf (not before)
2. Public Claim
    * role
    * userId
    * tenantId 등
3. Private Claim
    * 특정 시스템 내부 전용 정보

Claim은 단순 데이터 필드가 아니라, 인증 아키텍처의 설계를 결정하는 핵심 요소에 해당됩니다. 어떤 정보를 토큰에 포함할 것인가는 토큰 크기, 보안 수준, 시스템 결합도에 직접적인 영향을 주기 때문입니다.

### Signature

Signature는 토큰 위조 방지를 위한 서명입니다.

```
HMACSHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  secretKey
)
```

Signature를 통해 서버는 토큰이 변조되지 않았는지를 검증합니다.

> JWT는 암호화가 아니라 서명 기반 무결성 검증 방식입니다.

Payload는 누구나 디코딩할 수 있습니다. 보안의 핵심은 “위조가 불가능하다”는 점입니다.
