## 1. Transit Engine이란?

Vault는 다양한 Secret을 관리하는 기능을 제공하지만, 그 중에서도 KMS 대체 관점에서 가장 중요한 기능은 Transit Engine입니다.

Transit Engine은 데이터를 Vault 내부에 저장하지 않고, 암호화와 복호화 기능만 API 형태로 제공하는 기능입니다.

즉, 애플리케이션에서는 암호화 키를 직접 다루지 않습니다. 대신 Vault에 요청을 보내 암·복호화를 수행하게 됩니다.

> 암호화 키는 Vault 내부에만 존재하고, 외부로 노출되지 않습니다.

Transit Engine의 동작 구조를 간단하게 표현하면 다음과 같습니다.

```text
애플리케이션
   ↓ (암호화 요청)
Vault (Transit Engine)
   ↓ (결과 반환)
애플리케이션
```

1. 애플리케이션은 평문 데이터를 Vault로 전달
2. Vault는 내부 키를 사용해 암호화 수행
3. 암호화된 결과만 반환

👉 이 과정에서 암호화 키는 외부로 절대 전달되지 않습니다

---

## 2. Transit Engine 사용해보기

이제 실제로 Transit Engine을 활성화하고 암·복호화를 수행해보겠습니다.

---

### 2.1. Transit Engine 활성화

```nohighlight
/ # vault secrets enable transit
```

위 명령어를 사용해서 Transit Engine을 활성화하려고 했습니다. 하지만, 아래와 같은 에러가 발생했습니다.

```nohighlight
Error enabling: Error making API request.

URL: POST http://127.0.0.1:8200/v1/sys/mounts/transit
Code: 403. Errors:

* permission denied
```

Vault CLI는 요청을 보낼 때 반드시 인증 토큰이 필요합니다. Vault CLI는 기본적으로 VAULT_TOKEN 환경변수를 통해 인증 토큰을 사용합니다.

하지만 컨테이너 내부에서는 해당 환경변수가 설정되어 있지 않았기 때문에, 인증되지 않은 상태로 요청이 전달되면서 permission denied 에러가 발생한 것이었습니다.

```nohighlight
/ # export VAULT_TOKEN=root
```

위와 같이 root 토큰을 환경변수로 설정하면 정상적으로 동작합니다.

이후 다시 명령어를 실행하면 정상적으로 Transit Engine이 활성화됩니다.

```nohighlight
/ # vault secrets enable transit
```

그리고 다시 명령어를 실행해보면, 이번에는 아래와 같은 정상적인 응답을 받을 수 있었습니다.

```nohighlight
Success! Enabled the transit secrets engine at: transit/
```
---

### 2.2. 암호화 키 생성

```nohighlight
/ # vault write -f transit/keys/test-key
```

위 명령어를 사용해서 test-key라는 이름의 암호화 키를 생성했습니다. 키가 정상적으로 생성되고, 아래와 같은 응답을 받을 수 있었습니다.

```nohighlight
Key                       Value
---                       -----
allow_plaintext_backup    false
auto_rotate_period        0s
deletion_allowed          false
derived                   false
exportable                false
imported_key              false
keys                      map[1:1775968290]
latest_version            1
min_available_version     0
min_decryption_version    1
min_encryption_version    0
name                      test-key
supports_decryption       true
supports_derivation       true
supports_encryption       true
supports_signing          false
type                      aes256-gcm96
```

Transit Engine에서는 암호화 시점에 알고리즘을 선택하는 방식이 아니라, 키를 생성할 때 알고리즘(type)이 결정됩니다.

이후 해당 키를 사용하는 모든 암·복호화는 동일한 알고리즘으로 수행됩니다.

기본적으로는 aes256-gcm96과 같은 안전한 알고리즘이 사용되기 때문에, 별도로 알고리즘을 선택하지 않아도 안전한 방식으로 암호화를 사용할 수 있습니다.

```nohighlight
/ # vault write -f transit/keys/test-key type=aes128-gcm96
```

위 명령어처럼 키를 생성하는 명령어에서 type 변수를 통해 사용하려는 알고리즘을 직접 지정할 수도 있습니다. 


---

### 2.3. 암호화

```nohighlight
/ # vault write transit/encrypt/test-key plaintext="hello,world"
```

"hello,world"라는 문자열을 앞에서 생성한 test-key로 암호화해보고 싶었습니다. 그래서 위의 명령어를 사용했지만, 아래와 같은 에러가 발생했습니다.

```nohighlight
Error writing data to transit/encrypt/test-key: Error making API request.

URL: PUT http://127.0.0.1:8200/v1/transit/encrypt/test-key
Code: 400. Errors:

* illegal base64 data at input byte 5
```
---

Vault는 내부적으로 바이너리 데이터를 처리합니다. 

따라서 입력값을 Base64 형태로 받도록 설계되어 있습니다. Transit Engine의 입력값을 문자열 그대로 전달하면 Base64 디코딩 과정에서 오류가 발생합니다.

```nohighlight
/ # echo -n "hello,world" | base64
```

그래서 암호화를 요청하기 전에 먼저 위의 명령어를 사용해서 문자열 "hello,world"를 Base64로 인코딩했습니다. 

```nohighlight
/ # vault write transit/encrypt/test-key plaintext="aGVsbG8sd29ybGQ="
```

이번에는 문자열 "hello,world" 대신 Base64로 인코딩된 값(aGVsbG8sd29ybGQ=)을 전달했습니다. 그리고 다음과 같은 암호화 결과를 얻을 수 있었습니다.

```nohighlight
Key            Value
---            -----
ciphertext     vault:v1:jJE8zpj9O0rlSmRHH/VBEyJSBGnBZKFqJsmsXJpbmnyjfpjdzD/9
key_version    1
```

ciphertext 값이 Vault에서 생성된 암호화 결과입니다. 이렇게 암호화가 수행되는 과정에서 암호화 키는 외부로 절대 전달되지 않습니다. 이것이 Transit Engine의 가장 중요한 특징입니다.

> 애플리케이션이 암호화 키를 직접 다루지 않아도 된다는 점에서, KMS를 대체할 수 있는 핵심 기능이라고 볼 수 있습니다.

---

### 2.4. 복호화

```nohighlight
/ # vault write transit/decrypt/test-key ciphertext="vault:v1:jJE8zpj9O0rlSmRHH/VBEyJSBGnBZKFqJsmsXJpbmnyjfpjdzD/9"
```

위 명령어를 사용해서 아래와 같이 정상적으로 복호화되는 것을 확인할 수 있었습니다.

```nohighlight
Key          Value
---          -----
plaintext    aGVsbG8sd29ybGQ=
```

암호화와 동일하게 복호화된 결과도 Base64로 인코딩된 값입니다.

## 3. Transit Engine과 HSM(Hardware Security Module)의 차이

Transit Engine을 보면 HSM과 유사하게 느껴질 수 있습니다.
하지만 두 개념은 동일하지 않습니다.

| 구분    | Transit Engine | HSM       |
| ----- | -------------- | --------- |
| 형태    | 소프트웨어          | 하드웨어      |
| 키 저장  | Vault 내부       | 물리 장비 내부  |
| 키 노출  | 없음             | 없음        |
| 보안 수준 | 높음             | 매우 높음     |
| 비용    | 낮음             | 높음        |
| 용도    | 일반 서비스         | 금융/고보안 환경 |

Transit Engine은 HSM과 동일한 개념이라기보다는, HSM 없이도 KMS 기능을 제공하는 소프트웨어 구현으로 볼 수 있습니다.

필요한 경우 Vault는 HSM과 결합하여 더 높은 보안 수준을 확보할 수 있습니다.

**핵심 차이**

👉 Transit Engine
→ 소프트웨어 기반 KMS 기능

👉 HSM
→ 하드웨어 기반 키 보호 장치
