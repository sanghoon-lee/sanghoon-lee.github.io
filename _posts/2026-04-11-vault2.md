실습을 통해 시크릿 관리 기능을 제공하는 KV Engine을 활용하면 암호화 키를 중앙에서 저장하고 관리하는 기능을 구현할 수 있다는 사실을 확인할 수 있었습니다.

단순히 KMS를 암호화 키 저장소 역할로만 사용한다면 이 정도 기능의 구현만으로도 충분할 것입니다.

하지만 이 방식에서는 암호화 키가 결국 애플리케이션으로 전달됩니다. 따라서 암호화 키가 노출될 가능성을 완전히 제거할 수는 없습니다.

이러한 이유로 KMS가 직접 암·복호화 연산까지 수행하는 방식이 더 권장됩니다.

Transit Engine은 암호화 키를 생성·관리하고, 이를 이용한 암·복호화 기능을 함께 제공합니다. 따라서 암호화 키를 외부로 노출하지 않으면서 보다 안전한 방식으로 KMS의 핵심 기능을 구현할 수 있을 것으로 보였습니다.

---

## 1. Transit Engine

Vault의 Transit Engine은 Vault 내부에 보관하고 있는 암호화 키를 사용해 암·복호화 연산을 수행합니다.

이를 활용하면 애플리케이션은 암호화 키를 직접 다루지 않고, 암·복호화가 필요한 데이터만 Vault에 전달한 뒤 결과를 받아 사용할 수 있습니다.

Transit Engine의 동작 구조를 간단하게 표현하면 다음과 같습니다.

```nohighlight
[애플리케이션]
       │
       │ 평문 또는 암호문 전달
       ▼
[Vault Transit Engine]
       │
       │ Vault 내부 키 사용
       ▼
    암·복호화 수행
       │
       ▼
      결과 반환
```

---

## 2. 실습 : 암·복호화

지금까지 Transit Engine의 역할과 동작 방식을 개념적으로 살펴봤습니다.

이제 직접 Transit Engine에서 암호화 키를 생성한 뒤, 실제로 암·복호화 연산이 어떻게 수행되는지 확인해보겠습니다.

실습을 통해 암호화 키가 외부로 노출되지 않은 상태에서도 암·복호화가 가능하다는 점을 확인할 수 있습니다.

---

### 2.1. 컨테이너 재구성

실습에 앞서 Vault 컨테이너를 조금 수정했습니다.

지난 포스팅에서 트러블슈팅을 위해 환경변수 VAULT_ADDR과 VAULT_TOKEN의 값을 아래와 같이 주입했었습니다.

* VAULT_ADDR=http://127.0.0.1:8200
* VAULT_TOKEN=root

환경변수 주입을 위해 컨테이너 내부에 접속해야 했습니다. 이렇게 환경변수를 매번 수동으로 설정하는 과정이 번거로웠습니다.

그래서 컨테이너 생성 시점에 환경변수를 함께 설정하도록 기존 컨테이너를 제거하고 다시 구성했습니다.

**컨테이너 제거**
```bash
$ docker rm -f vault
```

**컨테이너 재구성**
```bash
$ sudo docker run --cap-add=IPC_LOCK -d \
> -p 8200:8200 \
> --name vault \
> -e "VAULT_DEV_ROOT_TOKEN_ID=root" \
> -e "VAULT_DEV_LISTEN_ADDRESS=0.0.0.0:8200" \
> -e "VAULT_ADDR=http://127.0.0.1:8200" \
> -e "VAULT_TOKEN=root" \
> hashicorp/vault
```

이제는 환경변수 VAULT_ADDR과 VAULT_TOKEN이 컨테이너 생성 시점에 함께 설정되었기 때문에, 컨테이너에 접속할 때마다 별도로 환경변수를 주입할 필요가 없습니다.

---

### 2.2. Transit Engine 활성화

Transit Engine을 사용하기 위해서는 먼저 엔진을 활성화해야 합니다. 

엔진을 활성화하려면 Vault CLI를 사용해야 합니다. 지난 포스팅에서 이야기했던 것처럼 호스트에는 CLI가 설치되어 있지 않기 때문에, 컨테이너 내부에 다시 접속했습니다. 

```bash
$ sudo docker exec -it vault sh
```

컨테이너 내부에 접속한 상태에서 아래 명령으로 엔진을 활성화했습니다.

```nohighlight
/ # vault secrets enable transit
```

그리고 아래와 같은 정상적인 응답을 받을 수 있었습니다.

```nohighlight
Success! Enabled the transit secrets engine at: transit/
```

Transit Engine이 활성화되면 transit/ 경로 아래에서 암호화 키를 생성하고 암·복호화 기능을 사용할 수 있습니다.

---

### 2.3. 암호화 키 생성

```nohighlight
/ # vault write -f transit/keys/test-key
```

위 명령어를 사용해서 test-key라는 이름의 암호화 키를 생성했습니다. 키가 정상적으로 생성되고, 아래와 같은 응답을 받을 수 있었습니다.

```nohighlight
Key                       Value
---                       -----
allow_plaintext_backup    false
auto_rotate_period        0s
deletion_allowed          false
derived                   false
exportable                false
imported_key              false
keys                      map[1:1775968290]
latest_version            1
min_available_version     0
min_decryption_version    1
min_encryption_version    0
name                      test-key
supports_decryption       true
supports_derivation       true
supports_encryption       true
supports_signing          false
type                      aes256-gcm96
```

Transit Engine에서는 암호화 시점에 알고리즘을 선택하는 방식이 아니라, 키를 생성할 때 알고리즘(type)이 결정됩니다.

이후 해당 키를 사용하는 모든 암·복호화는 동일한 알고리즘으로 수행됩니다.

기본적으로는 aes256-gcm96 알고리즘이 사용됩니다. 이는 AES-256 기반의 인증 암호화(AEAD) 방식으로 현재 널리 사용되는 안전한 알고리즘 중 하나입니다.

아래 명령어처럼 키를 생성하는 시점에 type 변수를 통해 사용하려는 알고리즘을 직접 지정할 수도 있습니다. 

```nohighlight
/ # vault write -f transit/keys/test-key-128 type=aes128-gcm96
```

---

### 2.4. 암호화

"hello,world"라는 문자열을 앞에서 생성한 test-key로 암호화해보고 싶었습니다. 그래서 아래와 같이 암호화를 요청하는 명령을 실행했습니다.

```nohighlight
/ # vault write transit/encrypt/test-key plaintext="hello,world"
```

하지만, 아래와 같은 오류가 발생했습니다.

```nohighlight
Error writing data to transit/encrypt/test-key: Error making API request.

URL: PUT http://127.0.0.1:8200/v1/transit/encrypt/test-key
Code: 400. Errors:

* illegal base64 data at input byte 5
```
---

Vault는 내부적으로 바이너리 데이터를 처리합니다. 따라서 Transit Engine API는 평문을 Base64로 인코딩한 형태의 입력값을 받도록 설계되어 있습니다.

Transit Engine의 입력값을 문자열 그대로 전달하면 Base64 디코딩 과정에서 오류가 발생하게 됩니다.

그래서 암호화를 요청할 문자열 "hello,world"를 Base64로 인코딩했습니다. 

```nohighlight
/ # echo -n "hello,world" | base64
```

그리고 다시 암호화를 요청했습니다.

```nohighlight
/ # vault write transit/encrypt/test-key plaintext="aGVsbG8sd29ybGQ="
```

문자열 "hello,world" 대신 Base64로 인코딩된 값(aGVsbG8sd29ybGQ=)을 전달하니 정상적으로 암호화 결과를 얻을 수 있었습니다.

```nohighlight
Key            Value
---            -----
ciphertext     vault:v1:jJE8zpj9O0rlSmRHH/VBEyJSBGnBZKFqJsmsXJpbmnyjfpjdzD/9
key_version    1
```

응답의 ciphertext 필드에는 Vault에서 생성한 암호화 결과가 위치합니다. 

암호화가 수행되는 과정에서 암호화 키가 외부로 절대 전달되지 않았습니다. 이것이 Transit Engine의 가장 중요한 특징입니다.

> 애플리케이션이 암호화 키를 직접 다루지 않아도 된다는 점에서, KMS를 대체할 수 있는 핵심 기능이라고 볼 수 있습니다.

---

### 2.5. 복호화

이번에는 아래와 같이 복호화 요청하는 명령을 실행했습니다. 

```nohighlight
/ # vault write transit/decrypt/test-key ciphertext="vault:v1:jJE8zpj9O0rlSmRHH/VBEyJSBGnBZKFqJsmsXJpbmnyjfpjdzD/9"
```

복호화 명령이 정상적으로 실행되고, 응답을 받을 수 있었습니다. 

```nohighlight
Key          Value
---          -----
plaintext    aGVsbG8sd29ybGQ=
```

복호화 결과 역시 Base64로 인코딩된 값이 반환됩니다. Transit Engine은 입력과 출력 모두 바이너리 데이터를 안전하게 전달하기 위해 Base64 형식을 사용합니다.

따라서 원본 문자열을 확인하려면 다시 Base64 디코딩을 수행해야 합니다.

```bash
$ echo "aGVsbG8sd29ybGQ=" | base64 -d
```

```text
hello,world
```

## 3. Transit Engine과 HSM(Hardware Security Module)의 차이

Transit Engine을 사용해보면 암호화 키를 외부로 노출하지 않는다는 점에서 HSM과 유사하게 느껴질 수 있습니다. 하지만 두 개념은 동일하지 않습니다.

| 구분    | Transit Engine | HSM       |
| ----- | -------------- | --------- |
| 형태    | 소프트웨어          | 하드웨어      |
| 키 저장  | Vault 내부       | 물리 장비 내부  |
| 키 노출  | 없음             | 없음        |
| 보안 수준 | 높음             | 매우 높음     |
| 비용    | 낮음             | 높음        |
| 용도    | 일반 서비스         | 금융/고보안 환경 |

Transit Engine은 HSM과 동일한 개념이라기보다는, HSM 없이도 암호화 키를 외부로 노출하지 않고 암·복호화 기능을 제공하는 소프트웨어 기반 구현에 가깝습니다.

필요한 경우 Vault는 HSM과 결합하여 더 높은 보안 수준을 확보할 수 있습니다.

Transit Engine은 KMS 기능을 제공하는 소프트웨어이고, HSM은 암호화 키를 물리적으로 보호하는 하드웨어 장치라는 차이가 있습니다.

---

## 4. 마무리

Transit Engine을 사용해서 암호화 키를 외부로 전달하지 않고, 암·복호화 연산을 직접 수행해봤습니다.

이를 통해 Vault가 단순한 시크릿 관리 기능을 넘어 KMS의 핵심 기능까지 제공할 수 있다는 사실도 확인했습니다.

KV Engine과 Transit Engine만으로도 일반적인 KMS가 제공하는 주요 기능 대부분을 구현할 수 있다는 확신을 얻을 수 있었습니다.

다만 실제 시스템에 적용하기 위해서는 애플리케이션이 Vault API를 호출할 수 있어야 합니다.

다음 포스팅에서는 Java 애플리케이션에서 Vault Transit Engine을 연동하는 방법을 알아보도록 하겠습니다.
