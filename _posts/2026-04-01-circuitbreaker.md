여러 서비스가 상호 연동되는 시스템을 운영하다 보면, 다음과 같은 상황을 자주 마주하게 됩니다.

* 외부 API 응답 지연
* DB 조회 지연
* 내부 서비스 호출 실패 또는 응답 오류

이러한 예외 상황을 적절하게 처리하지 못하면 문제가 다른 서비스로 전파될 수 있습니다.

> 하나의 서비스에서 발생한 문제가 다른 서비스로 전파되며  
> 전체 시스템에 영향을 주는 현상을 **연쇄 장애(Cascading Failure)**라고 합니다.

다음과 같은 구조를 가진 시스템이 있다고 가정해보겠습니다.

```text
API Gateway → 주문 서비스 → 결제 서비스 → 외부 PG
```

만약, 결제 서비스에서 응답 지연이 발생하게 되면 어떻게 될까요?

주문 서비스는 결제 서비스의 응답을 기다리게 되고,  
그 영향으로 주문 서비스의 요청 처리도 함께 지연됩니다.

이 상태가 지속되면 API Gateway 역시 주문 서비스의 응답을 기다리게 되면서,  
응답 지연은 결국 전체 시스템으로 확산됩니다.

---

## 1. 단순 Retry(재시도) 처리 방식의 위험성

이러한 문제를 피하려면, 연동된 서비스에 문제가 발생했을 때 어떻게 처리해야 할까요?

실무에서는 이러한 상황에서 가장 먼저 떠오르는 방법이 아마 Retry(재시도)일 것입니다. 
하지만 이 방식은 문제를 해결하기보다는 오히려 상황을 더 악화시키는 경우가 많습니다.

문제가 발생한 서비스에 계속해서 요청을 보내게 되면,
이미 과부하 상태인 서비스에 추가적인 부하를 주게 됩니다.

그 결과, 전체 시스템의 지연으로 이어질 수 있습니다.

개별 서비스에서 시작된 문제가 전체 시스템의 장애로 쉽게 확산되는 것입니다.

저 역시 이러한 상황을 반복해서 경험하면서  
장애가 발생한 서비스에 Retry를 계속 보내는 것이 과연 의미가 있는지 의문이 생겼습니다.

오히려 부하만 증가시키는 방식이라는 생각이 들었기 때문입니다.

문제가 발생한 서비스에 대한 호출을 계속 시도하는 것이 아니라  
아예 차단해야 한다는 접근이 필요하다고 느꼈고,  
그 과정에서 **서킷 브레이커(Circuit Breaker)** 패턴을 알게 되었습니다.

---

## 2. 서킷 브레이커의 개념

**서킷 브레이커**는 전기 회로의 차단기에서 유래한 개념입니다.  
문제가 발생하면 회로를 끊어서 더 큰 문제의 발생을 막는 것입니다.

소프트웨어에서는 문제가 발생한 서비스에 대한 호출을 일정 조건에서 차단하는 방식입니다.

“실패하는 서비스와의 연결을 의도적으로 끊는 전략”입니다.

이 방식은 장애가 발생한 서비스에 불필요한 부하를 주지 않으면서,  
전체 시스템을 보호하기 위한 목적을 가집니다.

동작 방식은 다음과 같습니다.

장애가 감지되면 해당 서비스 호출을 아예 시도하지 않고,  
즉시 실패하거나 대체 응답을 반환합니다.

```text
[Client]
   |
   v
[Circuit Breaker]
   |            \
   |             \ (Open 상태)
   v              X
[Service]   (즉시 실패 / fallback)
```

## 3. 서킷 브레이커의 동작 상태 (State)

서킷 브레이커는 단순히 호출을 차단하는 것이 아니라,  
서비스의 상태에 따라 동작 방식을 변경합니다.

일반적으로 다음과 같은 3가지 상태를 가집니다.

### 1) Closed (정상 상태)

정상적인 상태로, 모든 요청이 그대로 전달됩니다.

* 요청을 실제 서비스로 전달
* 성공/실패 여부를 계속 기록

즉, 평소에는 일반적인 호출과 동일하게 동작합니다.

### 2) Open (차단 상태)

일정 기준 이상으로 실패가 발생하면, 서킷 브레이커는 Open 상태로 전환됩니다.

이 상태에서는 더 이상 해당 서비스로 요청을 보내지 않습니다.

* 모든 요청을 즉시 차단
* 빠르게 실패하거나 fallback 응답 반환

장애가 발생한 서비스에 추가 부하를 주지 않기 위한 상태입니다.

### 3) Half-Open (복구 확인 상태)

일정 시간이 지나면 일부 요청만 제한적으로 허용하여  
서비스가 정상으로 돌아왔는지 확인합니다.

* 일부 요청만 실제 서비스로 전달
* 성공 여부에 따라 상태 전환
    - 성공 → Closed (정상 상태로 복귀)  
    - 실패 → 다시 Open (차단 유지)

---

## 4. 상태 전이

```
[Closed]     --(실패 증가)-->        [Open]
[Open]       --(일정 시간 경과)-->   [Half-Open]
[Half-Open]  --(성공)-->            [Closed]
[Half-Open]  --(실패)-->            [Open]
```

이러한 상태 전이를 통해 서킷 브레이커는  
장애 상황에서는 빠르게 차단하고,  
서비스가 회복되면 다시 정상적으로 요청을 전달합니다.

👉 즉, 서킷 브레이커는 단순히 요청을 차단하는 것이 아니라  
서비스 상태를 기반으로 호출 여부를 제어하는 메커니즘입니다.
