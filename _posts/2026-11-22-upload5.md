이제 **실제 파일 업로드 기능을 구현하면서 정확성과 안정성을 확보하려면 어떤 방법을 사용해야 하는지** 알아보려고 합니다.

## 1. 파일 업로드에서 정확성과 안정성이 중요한 이유

파일 업로드 요청이 성공했다고 모든 처리가 정확하게 이루어졌다고 단정할 수는 없습니다. 전송 과정에서 데이터가 손상되거나, 저장 과정에서 발생한 오류를 제대로 감지하지 못할 가능성도 있기 때문입니다.

그래서 **정확성**과 **안정성**에 대한 고려가 필요합니다. 

- **정확성:** 업로드된 파일이 전송 과정에서 손상되지 않고 의도한 대로 저장되었는가?
- **안정성:** 업로드 도중 오류나 장애가 발생했을 때 적절하게 대응하고 정상적인 상태로 복구할 수 있는가?

## 2. Google Cloud Storage의 데이터 무결성 검증

`Google Cloud Storage`에서는 파일 업로드와 다운로드 과정에서 데이터가 손상되지 않았는지 확인하기 위해 **Checksum을 이용한 무결성 검증**을 지원한다고 설명하고 있습니다.

### 2.1. Checksum이란?

Checksum은 데이터의 내용을 기반으로 계산한 값으로 **데이터가 전송되거나 저장되는 과정에서 변경되었는지 확인**하는 용도로 사용됩니다.

파일을 업로드하기 전에 Checksum을 계산하고, 서버에서 수신한 파일에 대해 동일한 방식으로 Checksum을 계산합니다. 만약 두 값이 일치한다면 데이터가 전송 과정에서 손상되지 않았을 가능성이 높다고 판단할 수 있습니다.

반대로 두 값이 다르다면 전송된 데이터에 문제가 발생했다는 의미가 될 것입니다.

| 구분 | Checksum | 검증 결과 |
|---|---|---|
| 업로드 전 원본 파일 | ABC123 | |
| 저장소에서 수신한 파일 | ABC123 | 일치 |
| 저장소에서 수신한 파일 | DEF456 | 불일치 |

*위 Checksum 값은 원리를 설명하기 위한 예시입니다.*

물론 **Checksum이 일치한다고 해서 데이터의 안전성이 완벽하게 보장되는 것은 아닙니다.** 서로 다른 데이터에서 동일한 Checksum 값이 나오는 충돌(Collision)이 발생할 수 있기 때문입니다.

### 2.2. Google Cloud Storage의 CRC32C 검증

`Google Cloud Storage`에서는 데이터 무결성을 검증하기 위해 `CRC32C` 알고리즘으로 생성한 Checksum의 사용을 권장하고 있습니다.

CRC는 데이터를 이진수로 취급하고, 정해진 생성 다항식(Polynomial)을 이용한 연산을 수행하여 검사값을 계산하는 오류 검출 방식입니다. `CRC32C`에서 32는 **검사값의 크기가 32비트라는 의미**이며, C는 Castagnoli 생성 다항식을 사용하는 CRC 변형을 구분하는 표기입니다.

일반적인 `CRC32`와 `CRC32C`는 모두 32비트 검사값을 생성하지만 사용하는 생성 다항식이 다릅니다.

| 구분 | CRC32 | CRC32C |
|---|---|---|
| 검사값 크기 | 32비트 | 32비트 |
| 생성 다항식 | IEEE | Castagnoli |
| 주요 사용 사례 | ZIP, PNG 등 | Google Cloud Storage, iSCSI 등 |

`CRC32C`는 데이터 전송 및 저장 과정에서 발생하는 오류를 효율적으로 검출하도록 설계된 알고리즘입니다. 하지만 **악의적인 데이터 변조를 방지하거나 데이터의 진위성을 보장하는 암호학적 기술은 아닙니다.**

### 2.3. 파일 업로드의 정확성과 연결되는 점

파일 업로드 요청에 성공 응답을 반환하는 것과 파일이 정확하게 저장되었는지를 검증하는 것은 서로 다른 문제입니다. 안전한 파일 업로드 기능을 구현하려면 아래와 같은 질문에 답할 수 있어야 합니다.

- 업로드 과정에서 데이터가 손상되었는지 검증할 수 있는가?
- 저장된 파일의 내용이 업로드한 원본과 일치하는가?
- 검증에 실패했다면 해당 파일을 어떻게 처리할 것인가?
- 저장된 파일을 다시 다운로드할 때도 무결성을 검증해야 하는가?

다만 이미지 재인코딩과 같이 파일의 내용을 의도적으로 변경하는 기능이라면 원본 파일과 저장된 파일의 Checksum이 달라지는 것이 정상일 것입니다. 이러한 경우에는 원본과의 일치 여부가 아니라 **변환된 결과가 요구사항에 맞게 생성되었는지를 검증**해야 합니다.

## 3. Amazon S3의 업로드 실패 처리

`Amazon S3`에서는 대용량 파일을 효율적으로 업로드하기 위해 `Multipart Upload` 기능을 제공합니다. `Multipart Upload`는 하나의 파일을 여러 부분(Part)으로 나누어 전송한 뒤, 업로드가 완료되면 하나의 객체(Object)로 구성하는 방식입니다.

이 방식은 대용량 파일의 전송 성능을 높이는 데 유용할 뿐만 아니라, 업로드 도중 일부 전송에 실패했을 때 해당 부분만 다시 전송할 수 있다는 장점이 있습니다.

### 3.1. Multipart Upload의 처리 과정

`Amazon S3`의 `Multipart Upload`는 크게 세 단계로 구성됩니다.

| 단계 | API | 설명 |
|---|---|---|
| 1 | CreateMultipartUpload | 업로드를 시작하고 Upload ID를 발급 |
| 2 | UploadPart | 파일을 여러 부분으로 나누어 업로드 |
| 3 | CompleteMultipartUpload | 업로드된 부분들을 하나의 객체로 구성하여 완료 |

예를 들어 파일을 5개의 Part로 나누어 업로드한다고 가정해 보겠습니다.

`Part 1`, `Part 2`, `Part 3`, `Part 4`, `Part 5`를 각각 업로드한 후 모든 Part의 업로드가 완료되면 `CompleteMultipartUpload`를 요청합니다.

`Amazon S3`는 완료 요청이 성공하면 업로드된 Part를 조합하여 하나의 객체를 생성합니다. 이처럼 **파일의 전송 과정과 최종 업로드 완료 과정을 구분**하여 관리하는 것이 특징입니다.

### 3.2. 업로드 실패 시 재전송

`Multipart Upload`의 장점 중 하나는 **특정 Part의 전송이 실패하더라도 전체 파일을 처음부터 다시 업로드할 필요가 없다는 것**입니다.

예를 들어 5개 Part 중 `Part 3`의 전송이 실패했다면, 정상적으로 업로드한 나머지 Part는 유지하면서 실패한 부분만 다시 전송할 수 있습니다. 특히 이 방식은 네트워크가 불안정하거나 파일의 크기가 클수록 유용합니다.

다만 실패한 부분의 재전송은 애플리케이션이나 클라이언트에서 적절하게 처리해야 합니다. `Multipart Upload`를 사용한다는 사실만으로 모든 실패 상황에서 자동 복구가 보장되는 것은 아니기 때문입니다.

### 3.3. 미완료 업로드 관리

그렇다면 일부 Part를 업로드한 상태에서 클라이언트가 종료되거나 더 이상 업로드를 진행할 수 없는 상황이 발생하면 어떻게 될까요?

`Amazon S3`에서는 `Multipart Upload`가 정상적으로 완료되거나 중단되기 전까지 업로드된 Part를 유지합니다.

이러한 데이터는 최종 객체로 완성되지 않았더라도 저장 공간을 소비하며 비용이 발생할 수 있습니다.

따라서 `Amazon S3`에서는 다음과 같은 방법을 제공합니다.

**AbortMultipartUpload**

> 진행 중인 Multipart Upload를 중단하고 업로드된 Part를 정리하기 위한 API입니다.
>
> 다만 중단 요청 시점에 진행 중인 Part 업로드가 있다면 해당 요청이 이후 완료될 수도 있으므로, 모든 데이터가 정리되었는지 확인하는 과정이 필요할 수 있습니다.

**AbortIncompleteMultipartUpload**

> S3의 Lifecycle 규칙을 이용하여 일정 기간 동안 완료되지 않은 Multipart Upload를 자동으로 중단하고 정리하는 기능입니다.
>
> 예를 들어 업로드를 시작한 후 지정된 기간이 지나도록 완료되지 않았다면 해당 업로드를 정리하도록 설정할 수 있습니다.

특히 Lifecycle을 이용한 정리 방식은 애플리케이션이 비정상 종료되어 직접 정리 작업을 수행하지 못하는 상황에서도 유용합니다.

### 3.4. 파일 업로드의 안정성과 연결되는 점

`Amazon S3`의 `Multipart Upload`와 미완료 업로드 관리 기능을 살펴보면서 **파일 업로드 기능은 정상적으로 완료되는 상황뿐만 아니라 실패하거나 중단되는 상황도 고려해야 한다**는 점을 확인할 수 있었습니다.

실제 파일 업로드 기능에서도 다음과 같은 사항을 검토할 필요가 있습니다.

- 파일 전송 도중 오류가 발생하면 재시도할 수 있는가?
- 업로드가 완료되지 않은 파일이 정상적인 파일로 제공되지 않도록 할 수 있는가?
- 업로드 실패 후 남아 있는 불완전한 파일을 정리할 수 있는가?
- 애플리케이션이 비정상 종료되더라도 미완료 파일을 식별하고 정리할 수 있는가?
- 업로드 성공 후 응답이 유실되어 동일한 요청이 다시 전달된다면 어떻게 처리할 것인가?

마지막 질문은 `Amazon S3`의 `Multipart Upload`만으로 해결되는 문제는 아닙니다.

특히 파일 저장과 데이터베이스의 메타데이터 저장이 별도의 작업으로 이루어지는 경우에는, 두 작업의 결과가 서로 달라질 수 있으므로 이를 일관되게 관리하는 방법도 고려해야 합니다.

## 4. 안전한 파일 업로드를 위해 고려해야 할 사항

`Google Cloud Storage`와 `Amazon S3`의 기술 문서를 살펴보면서 **정상적인 처리 결과를 검증하는 것뿐만 아니라, 실패 상황에서도 시스템이 예측 가능한 상태를 유지하도록 관리하는 것이 중요하다**는 점을 알 수 있었습니다.

앞서 학습한 보안성까지 포함하면 안전한 파일 업로드 기능을 구현하기 위해 다음과 같은 사항을 고려해야 할 것입니다.

| 관점 | 주요 고려사항 |
|---|---|
| 보안성 | 파일 형식 및 내용 검증, 안전한 저장 위치, 접근 권한 통제 |
| 정확성 | 파일 전송 및 저장 결과 검증, 데이터 무결성, 메타데이터 일관성 |
| 안정성 | 업로드 실패 처리, 재시도, 불완전한 파일 정리, 장애 복구 |

**참고**

> 안정성은 소프트웨어 품질 표준의 신뢰성(Reliability)과 밀접하게 연결되는 개념입니다. 두 개념의 관계는 이전 포스팅에서 살펴봤습니다.

물론 위의 항목들이 서로 완전히 독립적인 것은 아닙니다. 실제 기능을 구현할 때는 **각 요구사항이 어떤 문제를 해결하기 위한 것인지 이해하고, 서비스의 특성과 운영환경을 고려하여 적용 범위를 결정**해야 할 것입니다.

`Google Cloud Storage`와 `Amazon S3`에서 제공하는 기능을 그대로 구현해야 한다는 의미는 아닙니다. 각 서비스에서 사용하고 있는 기술의 목적과 원리를 참고하여, 실제 구현하려는 파일 업로드 기능에 필요한 요구사항을 도출하는 것이 중요하다고 생각합니다.

## 5. 마무리

이번 시리즈는 기존 파일 업로드 기능을 살펴보면서 보안과 예외 처리 등에 대한 고려가 충분하지 않았다는 문제의식에서 시작했습니다.

처음에는 안전한 파일 업로드 기능을 구현하기 위해 무엇을 고려해야 하는지 막연하게 생각했지만, OWASP와 KISA의 보안 가이드, 소프트웨어 품질 표준, 실제 클라우드 스토리지의 기술 문서를 살펴보면서 조금 더 구체적으로 이해할 수 있었습니다.

특히 **안전한 파일 업로드는 단순히 악의적인 파일을 차단하는 것이 아니라, 의도한 결과를 정확하게 제공하고 오류나 장애 상황에서도 안정적으로 동작하도록 만드는 것**이라는 점을 다시 확인할 수 있었습니다.

물론 지금까지 살펴본 내용만으로 모든 요구사항을 정의하거나 안전성을 보장할 수 있는 것은 아닙니다. 실제 구현 과정에서는 사용 환경과 요구사항에 따라 추가적인 검토와 테스트가 필요할 것입니다.
