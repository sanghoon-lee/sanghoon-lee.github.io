최근 구입한 **『소문난 명강의 크리핵티브의 한 권으로 끝내는 웹 해킹 바이블』**을 읽으며 웹 보안을 공부하고 있습니다.

웹 보안에 대해서 공부하기 전에는 인증/인가, 암호화, 시큐어코딩 등과 같이 애플리케이션 영역에만 관심이 있었습니다.

하지만 공부를 조금 해보니 인프라 영역에도 관심을 가져야 할 필요성을 느끼게 되었습니다. 외부 요청을 어떻게 수신하는지, 서버를 어떤 방식으로 노출하는지, 트래픽을 어떻게 분산하는지와 같은 인프라 영역 역시 서비스의 보안과 안정성에 큰 영향을 미치고 있다는 사실을 배울 수 있었기 때문입니다.

이 책을 통해 실제 서비스 환경에서는 애플리케이션만 안전하다고 해서 충분하지 않다는 사실을 인지하게 된 것만으로도 큰 수확이라고 생각합니다.

인프라 영역에서 개발자가 자주 접하게 되는 시스템 중 하나가 Reverse Proxy입니다.

실제 서비스 운영 환경에서 Reverse Proxy를 사용하고 있지만, 서비스의 보안과 안정성을 위해 어떤 역할을 수행하는지 깊게 생각해볼 기회는 많지 않았습니다.
 
그래서 직접 구축해보면서 Reverse Proxy의 개념과 동작 원리를 제대로 이해해보고 싶었습니다.

---

## 1. Reverse Proxy란 무엇인가?

Reverse Proxy는 클라이언트와 애플리케이션 서버 사이에서 요청을 대신 받아 처리하는 서버를 의미합니다.

클라이언트는 서비스를 이용하기 위해 필요한 요청을 보내지만, 그 요청은 애플리케이션 서버가 아닌 Reverse Proxy에 먼저 전달됩니다.

Reverse Proxy가 적절한 애플리케이션 서버로 요청을 전달하고, 처리 결과를 받아 다시 클라이언트에게 반환합니다.

일반적으로 클라이언트는 Reverse Proxy만 인식할 수 있으며, 실제 애플리케이션 서버의 위치나 구성 정보는 외부에 노출되지 않습니다.

```text
 클라이언트
   ↓↑
 Reverse Proxy
   ↓↑
 애플리케이션 서버
```

Reverse Proxy가 대신 노출되면서 클라이언트와 애플리케이션 서버 사이에서 요청과 응답을 중계하는 역할을 수행합니다.

즉, 클라이언트는 Reverse Proxy와만 통신하고 실제 애플리케이션 서버와는 직접 통신하지 않습니다.

마치 애플리케이션 서버 앞에 배치된 방패와 같은 존재라고 볼 수 있습니다.

## 2. Reverse Proxy를 사용하는 이유

그렇다면 많은 서비스들이 운영 환경에서 Reverse Proxy를 사용하는 이유는 무엇일까요?

실제 Reverse Proxy는 단순한 요청 중계 서버가 아닙니다. 

서비스의 보안성뿐만 아니라, 확장성과 운영 효율성을 높이는 다양한 기능을 제공하며 현대적인 웹 서비스 환경에서 중요한 역할을 수행하고 있습니다.

---

### 2.1. 애플리케이션 서버 보호

애플리케이션 서버가 외부에 직접 노출되어 있다면 모든 요청이 애플리케이션 서버로 바로 전달될 것입니다.

공격자는 공개된 서버를 대상으로 포트 스캔이나 취약점 탐색을 시도할 수 있으며, 서버가 사용하는 포트나 소프트웨어 정보를 파악할 가능성도 높아집니다.

반면 Reverse Proxy를 사용하면 애플리케이션 서버가 외부에 직접 노출되는 것을 방지할 수 있습니다.

애플리케이션 서버는 외부로부터 한 단계 분리되어 내부 네트워크에만 위치합니다.

그렇기 때문에 공격자가 애플리케이션 서버에 직접 접근하거나 내부 정보를 파악하는 것은 더욱 어려워집니다.

또한 Reverse Proxy를 통해 애플리케이션 서버에 적용되는 접근 제어와 보안 정책도 중앙 집중적으로 적용할 수 있게 됩니다.

---

### 2.2. 로드밸런싱

서비스 이용자가 증가하면 하나의 애플리케이션 서버만으로는 모든 요청을 처리하기 어렵게 됩니다. 

이런 상황에서는 다수의 애플리케이션 서버를 운영하면서 Reverse Proxy가 요청을 각 서버에 분산하여 전달할 수 있도록 구성해야 합니다.

```text
클라이언트
   ↓
Reverse Proxy
   ├─ 서버 1
   ├─ 서버 2
   └─ 서버 3
```

이를 로드밸런싱(Load Balancing)이라고 합니다.

로드밸런싱을 적용하면 특정 서버에 트래픽이 집중되는 것을 방지하면서 전체적인 서비스 처리 성능과 가용성을 높일 수 있습니다.

---

### 2.3. SSL 종료

오늘날 대부분의 웹 서비스는 보안을 이유로 HTTP 대신에 HTTPS를 사용합니다.

하지만 HTTPS 통신에서는 TLS 암호화와 복호화 과정이 필요하기 때문에, 서버 자원 사용량이 증가하게 됩니다.

Reverse Proxy를 사용하면 클라이언트와는 HTTPS 통신을 수행하지만, 내부 애플리케이션 서버에는 HTTP로 요청을 전달할 수 있도록 인프라를 구성할 수 있습니다.

```text
클라이언트
  ↓↑ HTTPS
Reverse Proxy
  ↓↑ HTTP
애플리케이션 서버
```

이러한 방식을 SSL 종료(SSL Termination)라고 합니다.

외부 클라이언트와의 통신은 HTTPS로 보안성을 유지하면서 애플리케이션 서버는 비즈니스 로직 처리에 더 많은 자원을 사용할 수 있습니다.

또한 SSL 인증서 관리 지점을 Reverse Proxy로 일원화할 수 있다는 장점도 있습니다.

여러 애플리케이션 서버가 존재하더라도 SSL 인증서는 Reverse Proxy에서만 관리하면 되기 때문입니다.

---

### 2.4. 정적 콘텐츠 처리

웹 서비스에는 이미지, CSS, JavaScript 파일과 같은 정적 콘텐츠가 많이 사용됩니다.

이러한 파일까지 모두 애플리케이션 서버가 처리할 수는 있습니다. 하지만 그만큼 애플리케이션 서버의 부하는 증가하게 됩니다.

Reverse Proxy는 이미지, CSS, JavaScript 파일과 같은 정적 콘텐츠를 직접 제공할 수 있습니다.

```text
클라이언트
  ↓↑ 
Reverse Proxy
```

따라서 정적 콘텐츠 요청이 발생하더라도 애플리케이션 서버까지 요청을 전달하지 않고 Reverse Proxy가 직접 응답할 수 있습니다.

그렇게 인프라를 구성하면 애플리케이션 서버의 불필요한 부하를 감소시켜 API 처리와 같은 핵심 업무에 더 많은 자원을 사용할 수 있게 됩니다.

---

## 3. 대표적인 Reverse Proxy 솔루션

그렇다면 Reverse Proxy를 구현할 수 있는 솔루션에는 어떤 것들이 있을까요?

대표적인 솔루션은 다음과 같습니다.

* Nginx
* Apache HTTP Server
* HAProxy

각 솔루션마다 특징과 강점은 다르지만, 모두 Reverse Proxy 구현에 필요한 기능을 제공하고 있습니다.

---

### 3.1. Nginx

Nginx는 현재 가장 널리 사용되는 Reverse Proxy 솔루션 중 하나입니다.

높은 성능과 간단한 설정을 제공하며, Reverse Proxy뿐만 아니라 웹 서버와 로드밸런서 역할도 수행할 수 있습니다.

특히 적은 자원으로도 많은 동시 접속을 처리할 수 있어 다양한 규모의 서비스에서 널리 활용되고 있습니다.

---

### 3.2. Apache HTTP Server

Apache HTTP Server는 오랜 기간 사용되어 온 대표적인 웹 서버입니다.

웹 서버 기능뿐만 아니라 Reverse Proxy 기능도 제공하며, 다양한 모듈과 풍부한 운영 경험을 가지고 있습니다.

특히 오랜 기간 축적된 문서와 커뮤니티 지원이 풍부하여 안정적인 운영 환경을 구축하는 데 유리한 장점을 가지고 있습니다.

---

### 3.3. HAProxy

HAProxy는 고성능 로드밸런싱에 특화된 솔루션입니다.

대규모 트래픽을 처리하는 환경에서 많이 사용되며, 뛰어난 성능과 안정성을 제공합니다.

특히 다수의 서버에 트래픽을 효율적으로 분산하는 기능이 강력하여 대규모 서비스 환경에서 많이 활용되고 있습니다.

---

## 4. 마치며

이번 포스팅에서는 Reverse Proxy의 개념과 동작 원리에 대해서 알아보았습니다.

사실 그동안 Reverse Proxy를 단순히 애플리케이션 서버 앞에 위치한 인프라 구성 요소 정도로만 생각하고 있었습니다. 

하지만 이번 학습을 통해 Reverse Proxy가 단순히 요청을 전달하는 역할만 수행하는 것이 아니라, 애플리케이션 서버 보호·로드밸런싱·SSL 종료·정적 콘텐츠 처리 등 다양한 기능을 제공한다는 사실을 알 수 있었습니다.

또한 이러한 기능들이 서비스의 보안성과 운영 효율성을 높이는 데 중요한 역할을 수행한다는 점도 이해할 수 있었습니다.

개념을 이해하는 것도 중요하지만, 실제로 구축해보면서 동작 과정을 직접 확인해보는 것이 더 좋은 학습 방법이라고 생각합니다.

그래서 Nginx를 이용해 Reverse Proxy를 직접 구성하고, 각 기능들이 실제로 어떻게 동작하는지 단계별로 검증해보게 되었습니다.
