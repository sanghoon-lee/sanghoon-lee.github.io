최근 구입한 **『소문난 명강의 크리핵티브의 한 권으로 끝내는 웹 해킹 바이블』**을 읽으며 웹 보안을 공부하고 있습니다.

웹 보안에 대해서 공부하기 전에는 인증/인가, 암호화, 시큐어코딩 등과 같이 애플리케이션 영역에만 관심이 있었습니다.

하지만 학습을 진행하면서 실제 서비스 환경에서는 애플리케이션만 안전하다고 해서 충분하지 않다는 사실을 알게 되었습니다.

외부 요청을 어떻게 수신하는지, 서버를 어떤 방식으로 노출하는지, 트래픽을 어떻게 분산하는지와 같은 인프라 영역 역시 서비스의 보안과 안정성에 큰 영향을 미치는 중요한 요소입니다. 

그래서 인프라 영역에도 관심을 가질 필요가 있다고 생각했습니다. 인프라 영역에서 개발자가 자주 접하게 되는 구성 요소 중 하나가 Reverse Proxy일 것입니다.

생각해보면 실제 사용하고 있지만 어떤 역할을 수행하는지 깊게 생각해보지 않았던 것 같습니다.
 
그래서 Reverse Proxy를 직접 구축하고, 주요 기능인 애플리케이션 서버 보호·로드밸런싱·SSL 종료·정적 콘텐츠 처리가 실제로 어떻게 동작하는지 단계적으로 검증해보고 싶었습니다. 

---

## 1. Reverse Proxy란 무엇인가?

Reverse Proxy는 클라이언트와 애플리케이션 서버 사이에 위치합니다. 

이 구조에서는 애플리케이션 서버가 외부에 직접 노출되지 않고 Reverse Proxy만 외부에 공개됩니다. 클라이언트는 실제 애플리케이션 서버의 위치나 구성 정보를 알 수 없습니다. 

대신 Reverse Proxy를 통해 필요한 요청을 전달하고 결과를 받을 수 있습니다. Reverse Proxy가 클라이언트의 요청을 적절한 애플리케이션 서버로 전달하고, 처리 결과를 다시 클라이언트에게 반환하기 때문입니다.

```text
 클라이언트
   ↓↑
 Reverse Proxy
   ↓↑
 애플리케이션 서버
```

클라이언트와 애플리케이션 서버 사이에서 요청과 응답을 중계하는 것이 Reverse Proxy의 핵심 역할이라고 보면 됩니다.

<img class="main-image" src="/assets/images/websecurity.png" alt="웹 보안">

애플리케이션 서버를 외부로부터 보호하는 방패와 같은 존재가 Reverse Proxy라고 볼 수 있습니다.

---

## 2. Reverse Proxy를 사용하는 이유

그렇다면 많은 서비스들이 운영 환경에서 Reverse Proxy를 사용하는 이유는 무엇일까요?

실제 Reverse Proxy는 단순한 요청 중계 서버가 아닙니다. 

서비스의 보안성뿐만 아니라, 확장성과 운영 효율성을 높이는 다양한 기능을 제공하며 현대적인 웹 서비스 환경에서 중요한 역할을 수행하고 있습니다.

---

### 2.1. 애플리케이션 서버 보호

애플리케이션 서버가 외부에 직접 노출되어 있다면 모든 요청이 애플리케이션 서버로 바로 전달될 것입니다.

공격자는 공개된 서버를 대상으로 포트 스캔이나 취약점 탐색을 시도할 수 있으며, 서버가 사용하는 포트나 소프트웨어 정보를 파악할 가능성도 높아집니다.

반면 Reverse Proxy를 사용하면 애플리케이션 서버가 외부에 직접 노출되는 것을 방지할 수 있습니다.

애플리케이션 서버는 외부로부터 한 단계 분리되어 내부 네트워크에만 위치합니다.

그렇기 때문에 공격자가 애플리케이션 서버에 직접 접근하거나 내부 정보를 파악하는 것은 더욱 어려워집니다.

또한 Reverse Proxy를 통해 애플리케이션 서버에 적용되는 접근 제어와 보안 정책도 중앙 집중적으로 적용할 수 있게 됩니다.

---

### 2.2. 로드밸런싱

서비스 이용자가 증가하면 하나의 애플리케이션 서버만으로는 모든 요청을 처리하기 어렵게 됩니다. 

이런 상황에서는 다수의 애플리케이션 서버를 운영해야 합니다. 요청을 여러 애플리케이션 서버로 분산시켜야 하는데 이를 로드밸런싱(Load Balancing)이라고 합니다.

```text
클라이언트
   ↓
Reverse Proxy
   ├─ 서버 1
   ├─ 서버 2
   └─ 서버 3
```

Nginx와 같은 Reverse Proxy 솔루션은 로드밸런싱 기능도 제공할 수 있습니다.

로드밸런싱을 적용해서 특정 서버에 트래픽이 집중되는 것을 방지하면서 전체적인 서비스 처리 성능과 가용성을 높일 수 있습니다.

---

### 2.3. SSL 종료

오늘날 대부분의 웹 서비스는 보안을 이유로 HTTP 대신에 HTTPS를 사용합니다.

하지만 HTTPS 통신에서는 TLS 암호화와 복호화 과정이 필요하기 때문에 추가적인 서버 자원이 사용됩니다.

Reverse Proxy를 사용하면 클라이언트와는 HTTPS 통신을 수행하지만, 내부 애플리케이션 서버에는 HTTP로 요청을 전달할 수 있도록 인프라를 구성할 수 있습니다.

```text
클라이언트
  ↓↑ HTTPS
Reverse Proxy
  ↓↑ HTTP
애플리케이션 서버
```

이러한 방식을 SSL 종료(SSL Termination)라고 합니다.

즉, 외부 클라이언트와의 통신은 HTTPS로 보안성을 유지하면서 애플리케이션 서버는 비즈니스 로직 처리에 더 많은 자원을 사용할 수 있게 됩니다.

이러한 구성을 선택하면 다수의 애플리케이션 서버에 인증서를 각각 배포할 필요없이 Reverse Proxy에서 일괄 관리할 수 있다는 운영상의 장점도 가질 수 있습니다.

---

### 2.4. 정적 콘텐츠 처리

웹 서비스에는 이미지, CSS, JavaScript 파일과 같은 정적 콘텐츠가 많이 사용됩니다.

이러한 파일까지 모두 애플리케이션 서버가 처리할 수는 있습니다. 하지만 그만큼 애플리케이션 서버의 부하는 증가하게 됩니다.

Nginx와 같은 Reverse Proxy 솔루션은 웹 서버 기능도 함께 제공할 수 있습니다. 그래서 정적 콘텐츠를 Nginx가 직접 제공하도록 구성하는 것이 가능합니다.

```text
클라이언트
  ↓↑ 
Reverse Proxy
```

그렇게 되면 애플리케이션 서버는 API 처리와 같은 핵심 업무에 더 많은 자원을 사용할 수 있습니다. 또한 정적 콘텐츠 요청을 효율적으로 처리함으로써 전체적인 시스템 성능 향상도 기대할 수 있습니다.

---

## 3. 대표적인 Reverse Proxy 솔루션

그렇다면 Reverse Proxy를 구현할 수 있는 솔루션에는 어떤 것들이 있을까요?

대표적인 솔루션은 다음과 같습니다.

* Nginx
* Apache HTTP Server
* HAProxy

각 솔루션마다 특징과 강점은 다르지만, 모두 Reverse Proxy 구현에 필요한 기능을 제공하고 있습니다.

---

### 3.1. Nginx

Nginx는 현재 가장 널리 사용되는 Reverse Proxy 솔루션 중 하나입니다.

높은 성능과 간단한 설정을 제공하며, Reverse Proxy뿐만 아니라 웹 서버와 로드밸런서 역할도 수행할 수 있습니다.

특히 적은 자원으로도 많은 동시 접속을 처리할 수 있어 다양한 규모의 서비스에서 널리 활용되고 있습니다.

---

### 3.2. Apache HTTP Server

Apache HTTP Server는 오랜 기간 사용되어 온 대표적인 웹 서버입니다.

웹 서버 기능뿐만 아니라 Reverse Proxy 기능도 제공하며, 다양한 모듈과 풍부한 운영 경험을 가지고 있습니다.

특히 오랜 기간 축적된 문서와 커뮤니티 지원이 풍부하여 안정적인 운영 환경을 구축하는 데 유리한 장점을 가지고 있습니다.

---

### 3.3. HAProxy

HAProxy는 고성능 로드밸런싱에 특화된 솔루션입니다.

대규모 트래픽을 처리하는 환경에서 많이 사용되며, 뛰어난 성능과 안정성을 제공합니다.

특히 다수의 서버에 트래픽을 효율적으로 분산하는 기능이 강력하여 대규모 서비스 환경에서 많이 활용되고 있습니다.

---

## 4. 마치며

사실 그동안 Reverse Proxy를 단순히 애플리케이션 서버 앞에 위치한 인프라 구성 요소 정도로만 생각하고 있었습니다. 

하지만 이번 학습으로 Reverse Proxy가 단순히 요청을 전달하는 역할만 수행하는 것이 아니라, 애플리케이션 서버 보호·로드밸런싱·SSL 종료·정적 콘텐츠 처리 등 다양한 기능을 제공한다는 사실을 알 수 있었습니다.

또한 이러한 기능들이 서비스의 보안성과 운영 효율성을 높이는 데 중요한 역할을 수행한다는 점도 이해할 수 있었습니다.

하지만 문서로 개념만 이해하는 것과 실제로 구축해보는 것은 큰 차이가 있습니다.
