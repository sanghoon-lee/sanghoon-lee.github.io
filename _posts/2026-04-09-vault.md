사내에서 사용하고 있는 KMS(Key Management System)의 EOS(End of Support)가 다가오면서 대체 방안을 고민해야 했습니다.

암호화 키뿐만 아니라 시크릿(Secret) 정보의 관리와 접근 통제 체계까지 함께 강화할 수 있는 방안을 찾고 싶었습니다.

특정 업체에 기술적으로 종속되지 않으면서 비용 부담 없이 사용할 수 있는 오픈소스 기반의 시스템이 있는지 찾아보는 과정에서 **HashiCorp Vault**를 알게 되었습니다.

<img class="main-image" src="/assets/images/hashicorp.jpg" alt="HashiCorp Vault">

Vault는 다양한 보안 기능을 함께 제공하는 플랫폼입니다. 그만큼 처음에는 다소 복잡하게 느껴지기도 했습니다.

그래도 직접 설치하고 사용해보면서 실제 운영 환경에서 활용할 수 있을지 확인해보기로 했습니다.

---

## 1. KMS(Key Management System)와 Vault의 차이

Vault를 KMS 대체 후보로 검토하기 위해서는 먼저 두 시스템의 역할과 범위를 이해할 필요가 있었습니다.

처음에는 두 시스템 모두 암호화 키를 관리하는 비슷한 역할을 수행한다고 생각했습니다. 하지만 실제로는 관리 대상과 제공 기능에 차이가 있었습니다.

KMS와 Vault의 개념을 비교하면서 어떤 차이가 있는지 살펴보도록 하겠습니다.

---

### 1.1. KMS 

KMS는 암호화에 사용되는 키를 생성하고 안전하게 보관하며 관리하는 시스템입니다.

암호화 키가 유출될 경우 암호화된 데이터도 함께 노출될 수 있기 때문에, 키는 데이터와 분리하여 별도로 관리하는 것이 중요합니다.

애플리케이션에서 암호화 키를 직접 보관할 경우 유출 위험이 있습니다. 그래서 키는 애플리케이션과 분리된 KMS와 같은 외부 시스템에 보관하는 방식이 권장됩니다.

특히 최근에는 애플리케이션 내부에서 직접 암호화 연산을 수행하지 않고, KMS를 통해 암·복호화를 수행하는 방식(암호화 연산 외부화)도 널리 사용되고 있습니다.

일반적으로 KMS는 다음과 같은 기능을 제공합니다.

**KMS의 주요 기능**

* 암호화 키 생성 및 저장
* 암·복호화 기능 제공(암호화 연산 외부화)
* 키 접근 제어
* 키 회전(Key Rotation)

KMS의 핵심 역할은 **암호화 키를 안전하게 생성·보관·통제**하는 것입니다.

---

### 1.2. Vault

Vault를 활용하면 KMS와 비슷한 방식으로 암호화 키를 관리할 수 있습니다. 하지만 Vault는 암호화 키뿐만 아니라 더 넓은 범위의 시크릿을 관리하기 위한 보안 기능을 제공합니다.

시크릿은 외부에 노출될 경우 보안 사고로 이어질 수 있기 때문에 안전하게 관리하고 통제할 필요가 있습니다.

아래와 같은 민감 정보들이 시크릿에 해당됩니다.

* 암호화 키
* API Key
* DB 계정 정보
* 토큰(Token)
* 인증서(Certificate)

즉, KMS가 암호화 키 관리에 초점을 맞춘 시스템이라면 Vault는 암호화 키를 포함한 다양한 시크릿을 통합적으로 관리하기 위한 플랫폼이라고 볼 수 있습니다.

**Vault의 주요 기능**

* 암호화 키 및 다양한 시크릿 관리
* 동적 시크릿 생성 및 자동 폐기
* 접근 제어 및 인증

Vault의 핵심 역할은 **암호화 키를 포함한 다양한 시크릿을 하나의 플랫폼에서 통합적으로 관리**하는 것입니다.

---

### 1.3. KMS vs Vault 비교

| 구분            | KMS         | Vault                   |
| ------------- | ----------- | ----------------------- |
| **주요 목적**     | 암호화 키 관리    | 시크릿 통합 관리            |
| **관리 대상**     | 암호화 키       | 암호화 키, API Key, 계정, 토큰 등 |
| **암·복호화 기능**   | 제공          | 제공 (Transit Engine)     |
| **접근 제어**     | 암호화 키 접근 중심       | 세밀한 정책 기반 제어            |
| **확장성**       | 암호화 키 관리 중심  | 다양한 보안 기능으로 확장 가능       |
| **운영 복잡성**    | 낮음          | 상대적으로 높음                |
| **적합한 용도**    | 단순 암호화 키 관리 | 통합 보안 플랫폼               |

👉 KMS
→ 암호화 키를 안전하게 관리하기 위한 시스템

👉 Vault
→ 암호화 키를 포함한 다양한 시크릿을 통합적으로 관리하기 위한 플랫폼

비교해보면 Vault는 단순히 KMS를 대체하기 위한 도구라기보다는 통합 보안 플랫폼에 가깝습니다.

Vault의 시크릿 관리 기능과 암·복호화 기능을 활용해 현재 사용 중인 KMS의 역할을 어느 수준까지 대체할 수 있을지 더 자세히 살펴보기로 했습니다.

---

## 2. HashiCorp Vault 설치와 실행

지금까지 Vault와 KMS와의 차이를 개념적으로 살펴봤습니다. 이제 직접 설치해서 동작 방식을 확인해보도록 하겠습니다.

아직 Vault에 대해서 깊이 있는 학습이 되어 있는 상태는 아니었습니다. 그래서 우선 가장 간단하게 테스트해볼 수 있도록 개발 모드(dev mode)로 Vault를 실행했습니다.

---

### 2.1. Vault 이미지 준비와 컨테이너 실행

아래 명령으로 최신 **HashiCorp Vault**의 도커 이미지를 가져왔습니다.

```bash
$ sudo docker pull hashicorp/vault:latest
```

그리고 복잡한 초기 설정을 생략하고 바로 테스트가 가능하도록 개발 모드로 구성해서 컨테이너를 실행했습니다.

```bash
$ sudo docker run --cap-add=IPC_LOCK -d \
> -p 8200:8200 \
> --name vault \
> -e "VAULT_DEV_ROOT_TOKEN_ID=root" \
> -e "VAULT_DEV_LISTEN_ADDRESS=0.0.0.0:8200" \
> hashicorp/vault
```

아래는 컨테이너 실행에 사용한 주요 옵션에 대한 설명입니다.

* --cap-add=IPC_LOCK: Vault는 메모리에 저장된 민감한 정보가 디스크로 스왑되는 것을 방지하기 위해 메모리를 잠그는 기능(mlock)을 제공합니다. 이 기능을 사용할 수 있도록 권한을 부여하는 설정입니다. 실습 환경에서는 필수는 아니지만 운영 환경에서는 보안 강화를 위해 사용하는 것이 권장됩니다.

* -e VAULT_DEV_ROOT_TOKEN_ID=root: Vault의 dev 개발 모드에서는 root 토큰이 자동으로 생성됩니다. 해당 root 토큰 값을 환경변수에 직접 지정하는 옵션입니다. 이 설정을 사용하면 로그인 시 사용할 토큰을 미리 알고 있기 때문에 실습이 훨씬 간편해집니다.

* -e VAULT_DEV_LISTEN_ADDRESS=0.0.0.0:8200: Vault 서버가 어떤 주소와 포트에서 요청을 받을지 지정하는 설정입니다. (0.0.0.0 → 모든 네트워크 인터페이스에서 접근 가능, 8200 → Vault 기본 포트)

---

### 2.2. 개발 모드(dev mode)

개발 모드는 Vault를 빠르게 테스트할 수 있도록 제공되는 실행 모드입니다.

다음과 같은 특징이 있습니다.

* 초기화(init) 과정 없이 바로 사용 가능
* 자동으로 root 토큰 생성
* 데이터가 메모리에 저장됨 (재시작 시 초기화)
* TLS 없이 HTTP로 동작

즉, **실습과 테스트를 위한 간편 실행 모드**입니다. 

**HashiCorp Vault**의 공식 도커 이미지는 기본 entrypoint가 `vault server -dev`로 설정되어 있습니다. 따라서 별도로 entrypoint가 지정되지 않으면 개발 모드로 동작합니다.

개발 모드는 테스트를 위한 실행 방식이므로 운영 환경에서는 반드시 서버 모드(server mode)로 실행해야 합니다.

개발 모드와 운영 모드의 차이는 다음과 같습니다.

| 항목        | 개발 환경(개발 모드) | 운영 환경(서버 모드)       |
| --------- | -------- | ----------- |
| 초기화(init) | 자동       | 수동          |
| unseal    | 필요 없음    | 필요          |
| 저장소       | 메모리      | 디스크/외부 스토리지 |
| 보안        | 낮음       | 높음          |
| TLS       | 없음       | 필수          |
| 용도        | 테스트      | 운영          |

---

### 2.3. Vault 상태 확인

Vault는 CLI를 통해 동작 상태를 확인하거나 설정 작업을 수행할 수 있습니다. 하지만 도커로 실행한 경우에는 호스트 환경에는 Vault CLI가 존재하지 않습니다. 

그래서 아래 명령으로 컨테이너 내부에 접속해서 CLI를 사용했습니다.

```bash
$ sudo docker exec -it vault sh
```

Vault의 동작 상태를 확인하는 CLI 명령은 다음과 같습니다.

```nohighlight
/ # vault status
```

하지만 CLI 명령을 실행하면 아래와 같은 오류가 발생했습니다. 

```nohighlight
WARNING! VAULT_ADDR and -address unset. Defaulting to https://127.0.0.1:8200.
Error checking seal status: Get "https://127.0.0.1:8200/v1/sys/seal-status": http: server gave HTTP response to HTTPS client
```

확인해보니 Vault CLI의 기본 접속 주소(VAULT_ADDR)가 설정되지 않아 발생한 것이었습니다.

개발 모드에서는 Vault 서버가 HTTP로 동작하지만, Vault CLI는 기본적으로 HTTPS로 접속을 시도하기 때문에 충돌이 발생하는 것이었습니다.

그래서 아래와 같이 환경변수를 추가적으로 설정해야 했습니다.

```nohighlight
/ # export VAULT_ADDR='http://127.0.0.1:8200'
```

환경변수를 설정하고 다시 CLI 명령을 실행했습니다. 

```nohighlight
/ # vault status
```

이제는 아래와 같이 정상적인 응답이 수신되었습니다.

```nohighlight
Key             Value
---             -----
Seal Type       shamir
Initialized     true
Sealed          false
Total Shares    1
Threshold       1
Version         1.21.4
Build Date      2026-03-04T17:40:05Z
Storage Type    inmem
Cluster Name    vault-cluster-ebd273bd
Cluster ID      8db3a19c-718d-f4f6-16ea-325f4979fba7
HA Enabled      false
```

응답 결과를 보면 `Initialized=true`, `Sealed=false` 상태인 것을 확인할 수 있습니다.

이는 Vault가 초기화되어 있으며 현재 사용할 수 있는 상태라는 의미입니다. 또한 `Storage Type=inmem`으로 표시되는 것을 통해 개발 모드에서 메모리 기반 저장소를 사용하고 있음을 확인할 수 있습니다.

## 3. 마무리

지금까지 Vault와 KMS의 개념적 차이를 살펴보고, CLI를 통해 정상적으로 Vault가 동작하는 것도 확인했습니다.

아직 본격적으로 Vault가 제공하는 보안 기능들을 사용해보지는 않았습니다. 

Vault는 보안 기능을 엔진(Engine) 단위로 제공하며, 필요한 기능만 선택적으로 사용할 수 있습니다.

대표적으로 시크릿을 저장하고 관리하는 KV Engine과 암·복호화 연산을 수행하는 Transit Engine이 있습니다.

KV Engine을 활용하면 암호화 키를 저장하고 조회하는 수준의 기본적인 KMS 기능은 비교적 쉽게 구현할 수 있을 것으로 보였습니다.

다음 포스팅에서는 KV Engine을 이용해 암호화 키를 저장하고 조회하면서 실제로 어떻게 활용할 수 있는지 알아보도록 하겠습니다.
