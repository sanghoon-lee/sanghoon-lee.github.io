사내에서 사용하고 있는 KMS(Key Management System)의 EOS(End of Support)가 다가오면서, 대체 방안을 검토하게 되었습니다. 

단순히 기능만 대체하는 것이 아니라, 앞으로의 확장성과 운영 방식까지 고려해야 했습니다.

그래서 가급적 특정 업체에 기술적으로 종속되지 않으면서, 비용 부담 없이 사용할 수 있는 오픈소스 기반의 시스템을 중심으로 살펴보게 되었습니다.

이 과정에서 **HashiCorp Vault**를 알게 되었고, KMS보다 넓은 범위의 보안 기능을 제공한다는 점에서 관심을 가지게 되었습니다.

다만, 운영 복잡성은 커질 수 있다는 점도 함께 확인할 수 있었습니다. 

그래서 직접 설치하고 사용해보면서 판단해보기로 했습니다.

---

## 1. KMS(Key Management System)와 Vault의 차이

### 1.1. KMS 

KMS는 암호화에 사용되는 키를 생성하고 안전하게 보관하며 관리하는 시스템입니다.

일반적으로 애플리케이션에서 암호화 키를 직접 보관할 경우 유출 위험이 있기 때문에,
키를 내부에 저장하지 않고 KMS를 통해 암복호화 기능을 호출하는 방식으로 사용하는 것이 권장됩니다.

이러한 방식에서는 실제 암호화 키가 외부로 노출되지 않기 때문에, 키 관리의 안전성을 높일 수 있다는 장점이 있습니다.

**KMS의 주요 기능**
> * 암호화 키 생성 및 저장
> * 암복호화 기능 제공
> * 키 접근 제어
> * 키 회전(Key Rotation)

핵심은 **암호화 키를 안전하게 관리하는 것**입니다.

---

### 1.2. Vault

Vault는 단순한 데이터 저장소가 아니라, 민감한 정보인 Secret을 안전하게 관리하고 통제하기 위한 보안 시스템입니다. 

여기서 말하는 Secret에는 다음과 같은 정보가 포함됩니다.

* 암호화 키
* API Key
* DB 계정 정보
* 토큰(Token)
* 인증서(Certificate)

이러한 정보는 외부에 노출될 경우 보안 사고로 이어질 수 있기 때문에, 별도의 저장소에서 안전하게 관리하고 통제할 필요가 있습니다. 

즉, **“민감한 정보를 안전하게 다루기 위한 중앙 관리 시스템”**이라고 볼 수 있습니다. 단순한 Secret 저장소를 넘어, KMS 기능을 포함한 확장된 보안 플랫폼입니다.

**Vault의 주요 기능**

> * 암호화 키 관리 (KMS의 주요 기능 포함)
> * 다양한 Secret 관리 (API Key, DB 계정 등)
> * 접근 제어 및 인증
> * 동적 Secret 생성 및 자동 폐기

핵심은 **민감한 정보를 통합적으로 관리하는 것**입니다.

<img class="main-image" src="/assets/images/hashicorp.jpg" alt="HashiCorp Vault">

Vault 개념을 구현한 대표적인 오픈소스 플랫폼은 인프라 자동화 도구를 제공하는 HashiCorp에서 개발한 **HashiCorp Vault**입니다. 

---

### 1.3. KMS vs Vault 비교

| 구분            | KMS         | Vault                   |
| ------------- | ----------- | ----------------------- |
| **주요 목적**     | 암호화 키 관리    | Secret 통합 관리            |
| **관리 대상**     | 암호화 키       | 키 + API Key + 계정 + 토큰 등 |
| **암복호화 기능**   | 제공          | 제공 (Transit Engine)     |
| **Secret 관리** | 제한적         | 다양한 Secret 관리 가능        |
| **동적 Secret** | 지원하지 않음     | 지원 (자동 생성/폐기)           |
| **접근 제어**     | 기본 제공       | 세밀한 정책 기반 제어            |
| **확장성**       | 제한적         | 다양한 보안 기능으로 확장 가능       |
| **운영 복잡성**    | 낮음          | 상대적으로 높음                |
| **적합한 용도**    | 단순 암호화 키 관리 | 통합 보안 플랫폼               |

👉 KMS
→ 암호화 키 관리에 최적화된 시스템

👉 Vault
→ 키 관리를 포함한 통합 보안 플랫폼

### 2.2. 컨테이너 실행하기

```bash
$ sudo docker run --cap-add=IPC_LOCK -d \
> -p 8200:8200 \
> -name vault \
> -e "VAULT_DEV_ROOT_TOKEN_ID=root" \
> -e "VAULT_DEV_LISTEN_ADDRESS=0.0.0.0:8200" \
> hashicorp/vault
```
```text
378eaf70c0781c3842e819ba5f06f0bc6bade83b5880ea556eeba6b6e2a8d444
```

위 명령어는 개발 환경인 dev mode로 Vault를 실행하는 방식이며, 초기 설정 없이 바로 테스트할 수 있습니다.

아래는 컨테이너 실행을 위해 사용한 주요 옵션에 대한 설명입니다.

**--cap-add=IPC_LOCK**

Vault는 메모리에 저장된 민감한 정보가 디스크로 스왑되는 것을 방지하기 위해 메모리를 잠그는 기능(mlock)을 사용합니다. 

--cap-add=IPC_LOCK는 도커의 컨테이너(Container)에서 이 기능을 사용할 수 있도록 권한을 추가하는 설정입니다. 

> 실습 환경에서는 필수는 아니지만, 운영 환경에서는 보안 강화를 위해 사용하는 것이 권장됩니다.

**-e VAULT_DEV_ROOT_TOKEN_ID=root**

Vault의 dev mode에서는 초기 root 토큰이 자동으로 생성됩니다. 이 환경 변수는 해당 root 토큰 값을 직접 지정하는 옵션입니다. 

이 설정을 사용하면 로그인 시 사용할 토큰을 미리 알고 있기 때문에 실습이 훨씬 간편해집니다.

**-e VAULT_DEV_LISTEN_ADDRESS=0.0.0.0:8200**

Vault 서버가 어떤 주소와 포트에서 요청을 받을지 지정하는 옵션입니다. 이 설정을 통해 브라우저나 외부 클라이언트에서 Vault에 접근할 수 있습니다.

* 0.0.0.0 → 모든 네트워크 인터페이스에서 접근 가능
* 8200 → Vault 기본 포트

### 2.3. dev mode

dev mode는 Vault를 빠르게 테스트할 수 있도록 제공되는 실행 모드입니다.

다음과 같은 특징이 있습니다.

* 초기화(init) 과정 없이 바로 사용 가능
* 자동으로 root token 생성
* 데이터가 메모리에 저장됨 (재시작 시 초기화)
* TLS 없이 HTTP로 동작

즉, **실습과 테스트를 위한 간편 실행 모드**입니다.

**HashiCorp Vault**의 공식 도커 이미지는
기본 entrypoint가 `vault server -dev`로 설정되어 있습니다. 따라서 특별히 entrypoint를 지정하기 않으면 dev mode로 동작합니다.

dev mode는 테스트를 위한 실행 방식이므로, 운영 환경에서는 반드시 production mode로 구성해야 합니다.

개발 환경(dev mode)과 운영 환경(production mode)의 차이는 다음과 같습니다.

| 항목        | 개발 환경(dev mode) | 운영 환경(production mode)       |
| --------- | -------- | ----------- |
| 초기화(init) | 자동       | 수동          |
| unseal    | 필요 없음    | 필요          |
| 저장소       | 메모리      | 디스크/외부 스토리지 |
| 보안        | 낮음       | 높음          |
| TLS       | 없음       | 필수          |
| 용도        | 테스트      | 운영          |
