지난 포스팅에서 애플리케이션 설정이 무엇인지부터 시작해서
`@Value` 어노테이션의 한계와 이를 극복하기 위해서 `@ConfigurationProperties` 어노테이션을 사용해 설정을 객체로 묶어 표현하는 방법까지 살펴봤습니다.

설정을 객체로 정의하면 설정의 구조와 의도가 코드에 자연스럽게 드러난다는 점은 확인했습니다. 하지만, 한 가지 질문이 남습니다.

`@ConfigurationProperties` 어노테이션으로 정의한 설정 클래스는
언제, 어떻게 스프링 빈으로 등록되는 걸까요?

단순히 클래스를 선언하는 것만으로는 스프링 컨텍스트에 자동으로 등록되지 않습니다. 설정 객체도 결국은 스프링 빈이어야 다른 컴포넌트에서 주입받아 사용할 수 있기 때문입니다.

이 지점에서 등장하는 것이 `@EnableConfigurationProperties` 어노테이션입니다.

## 설정을 활성화하는 방법, @EnableConfigurationProperties 어노테이션

`@ConfigurationProperties` 어노테이션은 설정을 객체에 바인딩하는 역할을 담당합니다. 하지만, 이 객체를 실제로 스프링 컨텍스트에 등록하고 활성화하는 역할은 `@EnableConfigurationProperties` 어노테이션이 담당합니다.

* @ConfigurationProperties → 설정 구조를 정의
* @EnableConfigurationProperties → 설정 객체를 활성화

`ExternalApiProperties` 클래스는 지난 포스팅에서 `@ConfigurationProperties` 어노테이션으로 선언되어 설정이 객체로 바인딩되었습니다.

이 상태에서 `ExternalApiProperties` 클래스를 아래 코드처럼 `@EnableConfigurationProperties` 어노테이션으로 스프링 컨텍스트에 등록할 수 있습니다. 

```java
@Configuration
@EnableConfigurationProperties(ExternalApiProperties.class)
public class ExternalApiConfig {
}
```

컨텍스트에 정상적으로 등록되면, 스프링이 관리하는 빈이 됩니다. 이제는 아래 코드처럼 설정이 바인딩된 객체(`properties`)를 통해서 애플리케이션에 설정 값을 주입할 수 있습니다.

```java
@Component
public class ExternalApiClient {

    private final ExternalApiProperties properties;

    public ExternalApiClient(ExternalApiProperties properties) {
        this.properties = properties;
    }

    public void call() {
        String url = properties.getUrl(); // https://example.com
        int timeout = properties.getTimeout(); // 3000
        // ...
    }
}

@Component
public class ExternalApiRetryPolicy {

    private final ExternalApiProperties properties;

    public ExternalApiRetryPolicy(ExternalApiProperties properties) {
        this.properties = properties;
    }

    public int retryCount() {
        return properties.getRetry(); // 3
    }
}
```

## @Component와 @EnableConfigurationProperties 어노테이션의 차이

그렇다면 이런 질문이 자연스럽게 떠오릅니다.

`@EnableConfigurationProperties` 어노테이션을 사용하지 않고, 그냥 설정 클래스인 `ExternalApiProperties`를 선언할 때 `@Component` 어노테이션을 붙이면 되는 것 아닐까?

실제로 다음과 같이 작성하는 것도 가능합니다.

```java
@Component
@ConfigurationProperties(prefix = "external.api")
public class ExternalApiProperties {

    private String url;
    private int timeout;
    private int retry;

    // getter / setter
}
```

이렇게 하면 `ExternalApiProperties` 클레스는 컴포넌트 스캔 대상이 되어 자동으로 스프링 컨텍스트에 빈으로 등록됩니다.

그렇다면 굳이 `@EnableConfigurationProperties` 어노테이션을 사용할 필요가 있을까요?

두 방식의 차이점을 정리해보면 다음과 같습니다.

| 구분        | @Component | @EnableConfigurationProperties |
| --------- | ---------- | ------------------------------ |
| 등록 방식     | 자동 컴포넌트 스캔 | 명시적 등록                         |
| 설정 클래스 성격 | 일반 컴포넌트    | 구성 요소                          |
| 라이브러리/모듈화 | 적합하지 않음    | 적합                             |
| 구조적 명확성   | 비교적 낮음     | 높음                             |

`@Component` 어노테이션을 사용하는 방식이 분명 빠르고 간편해 보입니다. 하지만, 설정 클래스가 많아질수록 설정 객체와 일반 컴포넌트의 구분이 모호해질 수 있습니다.

반면 `@EnableConfigurationProperties` 어노테이션을 사용하면
설정은 “구성 단계에서 활성화되는 요소”라는 인식이 더 분명해질 수 있습니다.

그래서 애플리케이션을 **라이브러리/모듈화** 형태로 제공할 계획이 있거나, 설정의 구성(Configuration)을 명확히 분리하고 싶다면 `@EnableConfigurationProperties` 어노테이션을 사용하는 것이 더 적합해보입니다.

## 설정에 따라 동작을 제어하는 방법, @ConditionalOnProperty 어노테이션

때로는 특정 설정 값에 따라 애플리케이션의 동작을 수행하는 코드를 분기 처리해야 할 필요가 있습니다. 

**예시) 설정 값에 따라 코드 분기가 필요한 경우**
* 특정 기능의 동작을 ON/OFF
* 운영 환경에서만 특정 빈을 활성화
* 테스트 환경에서만 특정 빈을 비활성화

이때, `@ConditionalOnProperty`을 사용할 수 있습니다.

`@ConditionalOnProperty`는 설정 값이 존재하거나, 특정한 조건과 일치할 때만 스프링 컨텍스트에 빈을 등록하도록 제어하는 어노테이션입니다.

예를 들어 `external.api.url`의 값이 **https://example.com**인 경우에만 `ExternalApiClient` 클래스를 빈으로 등록하려면 `@ConditionalOnProperty` 어노테이션으로 다음과 같이 선언하면 됩니다.
```java
@Component
@ConditionalOnProperty(
        prefix = "external.api",
        name = "url",
        havingValue = "https://example.com",
        matchIfMissing = false)
public class ExternalApiClient {

    private final ExternalApiProperties properties;

    public ExternalApiClient(ExternalApiProperties properties) {
        this.properties = properties;
    }

    public void call() {
        String url = properties.getUrl(); // https://example.com
        int timeout = properties.getTimeout(); // 3000
        // ...
    }
}
```

`@ConditionalOnProperty` 어노테이션을 사용하면
설정이 단순히 값을 전달하는 역할을 넘어,
애플리케이션의 구성 자체를 제어하는 역할을 하게 됩니다.

즉, 설정이 애플리케이션이 어떻게 동작해야 하는지 결정하게 되는 것을 의미합니다.

## 마무리...

사실 지금까지 애플리케이션의 설정의 중요성을 제대로 인지하지 못하고 있었습니다. 그러다보니 운영을 계속 하다보면 설정은 관리가 어려워지고, 코드도 점점 복잡해지는 것은 당연했던 것 같습니다. 

뒤늦게라도 중요성을 깨닫고, 조금이라도 공부하게 된 것이 그나마 다행인 것 같습니다. 실무에 공부한 내용을 활용하면 설정 구조와 방식을 보다 효과적으로 개선하는데 도움이 될 것 같습니다.
