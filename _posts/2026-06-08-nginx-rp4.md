Nginx가 Reverse Proxy로 동작할 수 있도록 최소한의 구성까지 적용해봤습니다. 

이제 클라이언트가 Reverse Proxy(nginx-rp)의 80포트를 통해 요청을 보내면 애플리케이션 서버까지 전달될 수 있습니다.

하지만 컨테이너의 실행 상태를 조회해보면 애플리케이션 서버는 여전히 8001 포트를 외부에 노출한 상태로 실행되고 있는 것을 알 수 있습니다.

이는 클라이언트가 Reverse Proxy를 우회하여 애플리케이션 서버에 직접 접근할 수 있다는 의미입니다.

```bash
$ docker ps

CONTAINER ID   IMAGE        COMMAND                  CREATED      STATUS      PORTS                                         NAMES
2bd57b3e33a6   nginx        "/docker-entrypoint.…"   4 days ago   Up 4 days   0.0.0.0:80->80/tcp, [::]:80->80/tcp           nginx-rp
85b2de399fc1   simple-api   "java -jar simple-ap…"   5 days ago   Up 4 days   0.0.0.0:8001->8000/tcp, [::]:8001->8000/tcp   api-01
```

즉, 현재 구조는 다음과 같습니다.

```nohighlight
┌─────────────────────────┐
│       Windows 11        │
│       (Client)          │
└───────┬─────────┬───────┘
        │         │
        │         │
        ▼         ▼
     Port 80   Port 8001
        │         │
        │         │
┌───────┴─────────┴───────┐
│   Oracle VM (Ubuntu)    │
│   IP : 192.168.56.11    │
│                         │
│ ┌───────────────────┐   │
│ │ nginx-rp          │   │
│ │ Host Port: 80     │   │
│ │ Container Port: 80│   │
│ └───────────────────┘   │
│                         │
│ ┌───────────────────┐   │
│ │ api-01            │   │
│ │ Host Port: 8001   │   │
│ │ Container Port:   │   │
│ │            8000   │   │
│ └───────────────────┘   │
└─────────────────────────┘
```

* Client → nginx-rp(80 포트) → api-01
* Client → api-01(8001 포트)

현재 구조에서는 Reverse Proxy가 구성되었지만, 애플리케이션 서버 보호라는 목적을 달성했다고 보기 어렵습니다.

애플리케이션 서버 보호라는 목적을 달성하려면 애플리케이션 서버는 Reverse Proxy를 통해서만 접근할 수 있어야 하기 때문입니다.

---

## 1. Docker Network 생성

우선 가상머신 외부에 있는 클라이언트가 애플리케이션 서버에 직접 접근하는 것부터 차단해야 합니다. 

하지만 Reverse Proxy가 역할을 하려면 애플리케이션 서버에 접근할 수 있어야 합니다. 결국 가상머신 내부에서 구동되는 컨테이너끼리의 통신은 허용되어야 합니다.

그래서 Docker Network를 이용했습니다.

Docker Network에서는 동일 네트워크에 연결된 컨테이너끼리 통신할 수 있으며, Docker가 제공하는 내부 DNS 기능을 사용할 수 있습니다.

따라서 컨테이너 이름을 호스트명처럼 사용하여 서로를 찾고 통신할 수 있습니다.


> api-01이라는 이름을 가진 컨테이너가 실행 중이라면 다른 컨테이너는 api-01이라는 이름만으로 해당 컨테이너를 찾을 수 있습니다.

다음의 명령을 실행해서 **rp-network**라는 이름으로 Docker Network를 생성했습니다.

```bash
$ docker network create rp-network
```

생성되어 있는 Docker Network 목록을 조회하는 명령은 다음과 같습니다.

```bash
$ docker network ls
```

Docker Network가 정상적으로 생성되었다면, 다음과 같이 rp-network가 목록에 포함되어 있어야 합니다.

```nohighlight
NETWORK ID     NAME         DRIVER    SCOPE
4347c31fdfbe   bridge       bridge    local
278e34f32899   host         host      local
1efc34a92de3   none         null      local
65dbef218e5a   rp-network   bridge    local
```

---

## 2. 애플리케이션 서버 재구성

Docker Network가 정상적으로 생성된 것을 확인하고, 애플리케이션 서버(api-01)를 재구성하기 위해서 기존의 컨테이너를 제거했습니다.

```bash
$ docker rm -f api-01
```

그리고 컨테이너를 재구성해서 아래와 같이 실행했습니다.

```bash
$ docker run -d \
  --name api-01 \
  --network rp-network \
  -e SERVER_NAME=api-01 \
  simple-api
```

이전과 비교하면 -p 8001:8000 옵션이 제거되었고, --network rp-network 옵션이 추가되었습니다. rp-network라는 이름으로 생성된 Docker Network가 사용되도록 컨테이너가 구성된 것을 알 수 있습니다.

컨테이너가 실행되면 이제 애플리케이션 서버의 8001 포트는 더 이상 외부에 노출되지 않습니다. 이 상태에서는 rp-network에 연결된 다른 컨테이너를 통해서만 애플리케이션 서버에 접근할 수 있습니다.

하지만 Reverse Proxy 역시 동일한 Docker Network를 사용하도록 재구성해야 합니다.

---

## 3. Nginx 설정 변경

Nginx를 Reverse Proxy로 구성하면서 nginx.conf 파일을 아래와 같이 작성했었습니다.

**nginx.conf 수정 전**
```nohighlight
events {
}

http {
    server {

        listen 80;

        location / {
            proxy_pass http://192.168.56.11:8001;
        }
    }
}
```

하지만 애플리케이션 서버가 더 이상 호스트 포트로 노출되지 않기 때문에 기존과 같은 방식으로 접근할 수 없습니다.

그래서 아래와 같이 nginx.conf 파일을 수정해야 합니다.

**nginx.conf 수정 후**
```nohighlight
events {
}

http {
    server {

        listen 80;

        location / {
            proxy_pass http://api-01:8000;
        }
    }
}
```

nginx.conf 파일에서 변경된 부분은 proxy_pass 설정입니다.

* 기존 : http://192.168.56.11:8001
* 변경 : http://api-01:8000

> 애플리케이션 서버(api-01)는 rp-network라는 이름을 가진 Docker Network로 통신합니다. Spring Boot 설정에 따라 8000 포트에서 동작하고 있으므로 api-01:8000으로 요청을 전달해야 합니다.

---

## 4. Reverse Proxy 서버 재구성

Reverse Proxy 서버(nginx-rp)도 재구성하기 위해서 기존 컨테이너를 제거했습니다.  

```bash
$ docker rm -f nginx-rp
```

그리고 컨테이너를 재구성해서 아래와 같이 실행했습니다.

```bash
$ docker run -d \
  --name nginx-rp \
  --network rp-network \
  -p 80:80 \
  -v /home/sanghoon/nginx/nginx.conf:/etc/nginx/nginx.conf:ro \
  nginx
```

이전과 비교하면 Docker Network를 사용하도록 --network rp-network 옵션이 추가된 것을 확인할 수 있습니다. 

즉, 변경된 구조는 다음과 같습니다.

```nohighlight
┌─────────────────────────┐
│       Windows 11        │
│       (Client)          │
└──────────┬──────────────┘
           │
           ▼
        Port 80
           │
┌─────────────────────────┐
│   Oracle VM (Ubuntu)    │
│                         │
│ ┌───────────────────┐   │
│ │ nginx-rp          │   │
│ │ Host Port: 80     │   │
│ │ Container Port: 80│   │
│ └─────────┬─────────┘   │
│           │             │
│      rp-network         │
│           │             │
│           ▼             │
│ ┌───────────────────┐   │
│ │ api-01            │   │ 
│ │ Container Port:   │   │
│ │            8000   │   │
│ └───────────────────┘   │
└─────────────────────────┘
```

* Client → nginx-rp(80 포트) → api-01

이제 애플리케이션 서버(api-01)은 rp-network 내부에서만 접근 가능하며, 외부 클라이언트는 Reverse Proxy(nginx-rp)를 통해서만 요청을 전달할 수 있습니다.

> 외부에 노출되던 애플리케이션 서버의 포트 매핑이 제거되었고, rp-network에 연결된 컨테이너만 접근이 가능하게 되었습니다.

## 5. 실습 : 애플리케이션 서버의 보호 기능 검증

Reverse Proxy가 제공하는 애플리케이션 서버 보호 기능이 정상적으로 동작하는지 검증하는 방법은 매우 간단합니다.

애플리케이션 서버에 직접 접근이 허용되는지 확인해보면 되기 때문입니다. 

그래서 애플리케이션 서버에 직접 접근을 시도했습니다.

```bash
$ curl http://192.168.56.11:8001/api/server
```

하지만 아래와 같이 연결은 실패했습니다. 

```nohighlight
curl: (7) Failed to connect to 192.168.56.11 port 8001 after 0 ms: Couldn't connect to server

```

기존에 사용하던 8001 포트는 더 이상 호스트 포트와 매핑되어 있지 않습니다. 따라서 운영체제 수준에서도 해당 포트로 수신 대기(Listen)하는 서비스가 존재하지 않습니다.

또한 애플리케이션 서버가 사용하는 컨테이너 포트 8000 역시 외부에 노출되어 있지 않기 때문에 클라이언트는 직접 접근할 수 없습니다.

반면 Reverse Proxy를 통해 요청을 보내면 정상적으로 응답이 반환되는 것은 확인할 수 있었습니다.

```bash
$ curl http://192.168.56.11/api/server
```

```json
{
    "time":"2026-06-11T14:08:35.498203914",
    "serverName":"api-01"
}
```

애플리케이션 서버는 외부에서 직접 접근할 수 없고, Reverse Proxy를 통해서만 서비스 요청을 처리할 수 있게 되었기 때문입니다.

이런 구조에서는 클라이언트는 Reverse Proxy의 주소만 인식할 수 있으며, 실제 애플리케이션 서버의 위치와 포트 정보는 더 이상 외부에 노출되지 않습니다.

이를 통해 Reverse Proxy가 단순히 요청을 전달하는 역할만 수행하는 것이 아니라, 애플리케이션 서버를 외부로부터 보호하는 보안 계층으로도 동작한다는 점을 직접 확인할 수 있었습니다.
