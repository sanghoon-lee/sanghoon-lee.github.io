지난 포스팅에서 Nginx를 설치하고, Reverse Proxy로 동작할 수 있도록 최소한의 구성을 적용해봤습니다. 

그 결과 클라이언트가 Reverse Proxy(nginx-rp)의 80포트를 통해 요청을 보내면 애플리케이션 서버까지 전달될 수 있습니다.

하지만 아래와 같이 컨테이너의 실행 상태를 조회해보면 애플리케이션 서버는 여전히 8001 포트를 외부에 노출한 상태로 실행되고 있는 것을 알 수 있습니다.

```bash
$ docker ps

CONTAINER ID   IMAGE        COMMAND                  CREATED      STATUS      PORTS                                         NAMES
2bd57b3e33a6   nginx        "/docker-entrypoint.…"   4 days ago   Up 4 days   0.0.0.0:80->80/tcp, [::]:80->80/tcp           nginx-rp
85b2de399fc1   simple-api   "java -jar simple-ap…"   5 days ago   Up 4 days   0.0.0.0:8001->8000/tcp, [::]:8001->8000/tcp   api-01
```

그렇기 때문에 클라이언트가 8001 포트를 통해 애플리케이션 서버(api-01)에 직접 요청을 보내는 것도 가능한 상태입니다. 

즉, 현재 구조는 다음과 같습니다.

```nohighlight
┌─────────────────────────┐
│       Windows 11        │
│       (Client)          │
└───────┬─────────┬───────┘
        │         │
        │         │
        ▼         ▼
     Port 80   Port 8001
        │         │
        │         │
┌───────┴─────────┴───────┐
│   Oracle VM (Ubuntu)    │
│   IP : 192.168.56.11    │
│                         │
│ ┌───────────────────┐   │
│ │ nginx-rp          │   │
│ │ Port : 80         │   │
│ └───────────────────┘   │
│                         │
│ ┌───────────────────┐   │
│ │ api-01            │   │
│ │ Port : 8000       │   │
│ └───────────────────┘   │
└─────────────────────────┘
```

* Client → nginx-rp(80 포트) → api-01
* Client → api-01(8001 포트)

현재 상태는 Reverse Proxy가 구성되었지만 애플리케이션 서버 보호라는 목적을 완전히 달성했다고 보기 어렵습니다.

애플리케이션 서버는 Reverse Proxy를 통해서만 접근할 수 있어야 하기 때문입니다.

---

## 1. Docker Network 생성

지금부터 애플리케이션 서버에 대한 직접 접근을 차단하고, Reverse Proxy를 통해서만 접근할 수 있도록 구성을 변경해보도록 하겠습니다.

동일한 네트워크에 연결되어 있는 컨테이너들은 Docker Network를 통해 서로 통신할 수 있습니다.

Docker는 동일한 네트워크에 연결된 컨테이너에 대해 내부 DNS 기능을 제공합니다. 따라서 컨테이너 이름만으로도 상대 컨테이너를 찾을 수 있습니다.

다음의 명령으로 **rp-network**라는 이름으로 Docker Network를 생성했습니다.

```bash
$ docker network create rp-network
```

현재 생성되어 있는 Docker Network 목록을 조회하는 명령은 다음과 같습니다.

```bash
$ docker network ls
```

위 명령에 대한 응답으로 반환되는 Docker Network 목록에 다음과 같이 rp-network가 포함되어 있어야 합니다.

```nohighlight
NETWORK ID     NAME         DRIVER    SCOPE
4347c31fdfbe   bridge       bridge    local
278e34f32899   host         host      local
1efc34a92de3   none         null      local
65dbef218e5a   rp-network   bridge    local
```

---

## 2. 애플리케이션 서버 재구성

Docker Network가 정상적으로 생성된 것을 확인하고, 아래의 명령으로 애플리케이션 서버(api-01)의 컨테이너를 제거했습니다.

```bash
$ docker rm -f api-01
```

그리고 애플리케이션 서버의 컨테이너를 아래와 같이 다시 생성했습니다.

```bash
$ docker run -d \
  --name api-01 \
  --network rp-network \
  -e SERVER_NAME=api-01 \
  simple-api
```

이전과 비교하면 -p 8001:8000 옵션이 제거되었고, --network rp-network 옵션이 추가되면서 앞서 생성한 rp-network라는 이름의 Docker Network를 사용하도록 컨테이너가 구성된 것을 알 수 있습니다.

애플리케이션 서버의 8001 포트는 이제 더 이상 외부에 노출되지 않습니다. rp-network에 연결된 컨테이너만 애플리케이션 서버에 접근할 수 있는 상태가 되었습니다.

하지만 아직 Reverse Proxy 컨테이너는 동일한 네트워크에 연결되어 있지 않습니다.

---

## 3. Nginx의 설정 변경

Nginx가 Reverse Proxy로 동작할 수 있도록 nginx.conf 파일을 아래와 같이 작성했었습니다.

**nginx.conf 수정 전**
```nohighlight
events {
}

http {

    server {

        listen 80;

        location / {
            proxy_pass http://192.168.56.11:8001;
        }
    }
}
```

하지만 이제는 더 이상 192.168.56.11:8001로 애플리케이션 서버에 접근할 수 없기 때문에 아래와 같이 nginx.conf 파일을 수정했습니다.

**nginx.conf 수정 후**
```nohighlight
events {
}

http {

    server {

        listen 80;

        location / {
            proxy_pass http://api-01:8000;
        }
    }
}
```

변경된 내용은 proxy_pass 설정뿐입니다.

* 기존 : http://192.168.56.11:8001
* 변경 : http://api-01:8000

이전 구성에서는 애플리케이션 서버를 다음과 같이 실행했습니다.
* -p 8001:8000

Docker의 포트 매핑은 {호스트 포트}:{컨테이너 포트} 형식으로 지정됩니다.

따라서 클라이언트는 가상머신의 8001 포트로 접근했지만, 실제 요청은 컨테이너 내부의 8000 포트로 전달되었습니다.

하지만 -p 8001:8000 옵션을 제거하고, Docker Network를 통해 컨테이너 간 통신을 수행하도록 구성을 변경했습니다. 그래서 호스트 포트를 사용할 필요는 없습니다. 

하지만 애플리케이션 서버가 Spring Boot 설정에 따라 8000 포트에서 동작하고 있으므로 Nginx 역시 api-01:8000으로 요청을 전달해야 합니다.

---

## 4. Reverse Proxy 서버 재구성

Reverse Proxy 컨테이너도 애플리케이션 서버와 마찬가지로 제거했습니다.

```bash
$ docker rm -f nginx-rp
```

그리고 아래와 같이 다시 생성했습니다.

```bash
$ docker run -d \
  --name nginx-rp \
  --network rp-network \
  -p 80:80 \
  -v /home/sanghoon/nginx/nginx.conf:/etc/nginx/nginx.conf:ro \
  nginx
```

이전과 비교하면 Docker Network 사용을 위해 --network rp-network 옵션이 추가된 것을 확인할 수 있습니다. 

즉, 변경된 구조는 다음과 같습니다.

```nohighlight
┌─────────────────────────┐
│       Windows 11        │
│       (Client)          │
└──────────┬──────────────┘
           │
           ▼
        Port 80
           │
┌─────────────────────────┐
│   Oracle VM (Ubuntu)    │
│                         │
│ ┌───────────────────┐   │
│ │ nginx-rp          │   │
│ │ Port : 80         │   │
│ └─────────┬─────────┘   │
│           │             │
│      rp-network         │
│           │             │
│           ▼             │
│ ┌───────────────────┐   │
│ │ api-01            │   │
│ │ Port : 8000       │   │
│ │ Internal Only     │   │ 
│ └───────────────────┘   │
└─────────────────────────┘
```

* Client → nginx-rp(80 포트) → api-01

## 5. 동작 확인

먼저 애플리케이션 서버에 직접 접근을 시도했습니다.

```bash
$ curl http://192.168.56.11:8001/api/server
```

하지만 애플리케이션 서버의 포트 노출을 제거했기 때문에 연결에 실패했습니다.

```nohighlight
curl: (7) Failed to connect to 192.168.56.11 port 8001 after 2004 ms: Couldn't connect to server
```

반면 Reverse Proxy를 통해 요청을 보내면 정상적으로 응답이 반환되었습니다.

```bash
$ curl http://192.168.56.11:80/api/server
```

```json
{
    "time":"2026-06-11T14:08:35.498203914",
    "serverName":"api-01"
}
```

이제 애플리케이션 서버는 외부에 직접 노출되지 않으며, Reverse Proxy를 통해서만 접근할 수 있는 구조가 되었습니다.

이를 통해 애플리케이션 서버를 외부에 직접 노출하지 않고도 서비스를 정상적으로 제공할 수 있음을 확인할 수 있었습니다.

또한 클라이언트는 Reverse Proxy만 인식할 수 있으며, 실제 애플리케이션 서버는 내부 네트워크 뒤에 위치하게 됨으로써 Reverse Proxy가 애플리케이션 서버를 보호하는 역할을 수행한다는 점도 직접 검증할 수 있었습니다.
