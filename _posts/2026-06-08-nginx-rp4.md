현재 애플리케이션 서버는 8001 포트로 접근이 가능하도록 외부에 노출되어 있습니다.

따라서 가상머신 외부에 있는 클라이언트는 Reverse Proxy(nginx-rp)를 통해 서비스에 접근할 수도 있고, 애플리케이션 서버(api-01)에 직접 접근할 수도 있습니다.

현재 구조는 다음과 같습니다.

```nohighlight
┌─────────────────────────┐
│       Windows 11        │
│       (Client)          │
└───────┬─────────┬───────┘
        │         │
        │         │
        ▼         ▼
     Port 80   Port 8001
        │         │
        │         │
┌───────┴─────────┴───────┐
│   Oracle VM (Ubuntu)    │
│   IP : 192.168.56.11    │
│                         │
│ ┌───────────────────┐   │
│ │ nginx-rp          │   │
│ │ Port : 80         │   │
│ └───────────────────┘   │
│                         │
│ ┌───────────────────┐   │
│ │ api-01            │   │
│ │ Port : 8001       │   │
│ └───────────────────┘   │
└─────────────────────────┘
```

* Client → nginx-rp (80)
* Client → api-01   (8001)

Reverse Proxy가 존재하더라도 애플리케이션 서버가 외부에 노출되어 있다면 애플리케이션 서버 보호라는 목적을 완전히 달성했다고 보기 어렵습니다.

애플리케이션 서버는 Reverse Proxy를 통해서만 접근할 수 있어야 하기 때문입니다.

그래서 이번 포스팅에서는 애플리케이션 서버에 대한 직접 접근을 차단하고, Reverse Proxy를 통해서만 서비스에 접근할 수 있도록 구성을 변경해보도록 하겠습니다.

## 1. Docker Network 생성

애플리케이션 서버를 외부에 노출하지 않으면서도 Nginx가 정상적으로 요청을 전달할 수 있어야 합니다.

이를 위해 Docker Network를 생성하고, Nginx와 애플리케이션 서버가 Docker 내부 네트워크를 통해 통신하도록 구성해보겠습니다.

먼저 Nginx와 애플리케이션 서버가 사용할 Docker Network를 생성했습니다.

```bash
$ docker network create rp-network
```
Docker Network가 생성되면 동일한 네트워크에 연결된 컨테이너들은 서로 통신할 수 있습니다.

또한 컨테이너 이름을 이용해서 다른 컨테이너에 접근할 수 있기 때문에 별도의 포트 노출 없이도 서비스 간 통신이 가능합니다.

생성된 네트워크는 다음 명령어를 통해 확인할 수 있습니다.

```bash
$ docker network ls
```

다음은 제가 사용하는 가상머신에서 위의 명령어를 실행한 결과입니다. rp-network가 생성된 것을 확인할 수 있었습니다.

```nohighlight

278e34f32899   host         host      local
1efc34a92de3   none         null      local

```
