스프링에서 의존관계를 자동으로 설정해주는 **의존성 주입(Dependency Injection, DI)**은 매우 중요한 기능입니다. 하지만, 이에 대해서 제대로 공부하기보다는 그냥 "@Autowired를 붙이는 기술” 정도로만 알고 사용하는 개발자들도 의외로 많이 있는 것 같습니다. 의존성 주입은 단순히 @Autowired를 붙이는 기술이 아니라, 객체의 생성 책임과 사용 책임을 분리하는 설계 원칙입니다. 

<img class="main-image" src="/assets/images/springboot.png" alt="스프링부트">

### 1. 의존성 주입의 개념

본격적으로 시작하기에 전에 **의존성(Dependency)**이 무엇인지 개념부터 정리해보겠습니다.

```java
public class SomeService {
    private SomeDependency someDependency = new SomeDependency();
}
```

위의 코드에서 SomeService는 SomeDependency 없이는 정상적으로 동작할 수 없습니다. 이처럼 한 객체가 또 다른 객체를 필요로 하는 경우, 의존성이 있는 관계라고 설명할 수 있습니다. 즉, SomeService가 SomeDependency에 의존성이 있는 것입니다. 

스프링에서는 컨테이너가 객체에 필요한 의존성을 생성해서 전달하는 **의존성 주입(Dependency Injection)** 기능을 제공하고 있습니다. 따라서, 객체는 필요한 의존성을 직접 생성하고 관리할 필요가 없습니다. 

의존성 주입 기능이 없다면, 다음과 같은 문제가 발생하게 됩니다.

1️⃣ 객체 간 결합도 상승

구현체가 코드에 직접 지정되어 있기 때문에, 다른 구현체로 변경하려면 반드시 코드를 수정해야 합니다. 변경에 취약한 구조가 됩니다.

2️⃣ 테스트 제약

가상의 Mocking 객체 주입이 사실상 불가능해지면서 외부 시스템(DB, API 등)에 의존한 테스트만 가능하게 됩니다. 결국, 단위 테스트보다는 통합 테스트 위주로 진행될 수 밖에 없습니다.

3️⃣ 객체 생성의 책임 분산

각 객체가 스스로 의존성이 있는 객체를 생성하면서, 자원 관리(생명주기, 설정 변경)가 어려워지게 됩니다.

4️⃣ 초기화 순서와 상태 관리의 불안정

의존성 관계에 있는 객체가 언제, 어떤 상태로 생성되는지 보장하기 어렵습니다. 이는 런타임 오류(NullPointerException 등)의 발생 가능성 증가로 이어지게 됩니다.

### 2. 의존성 주입 방법 : 생성자 주입 vs 필드 주입

스프링에서는 아래와 같은 의존성 주입 방법을 제공하고 있습니다.

* **생성자 주입** 
* **필드 주입** 
* **수정자(setter) 주입**
* **일반 메소드 주입** 

저희 팀에서 관리하고 있는 서비스의 소스코드를 정적분석 도구인 Sonarqube로 분석해 본 결과, 의존성 주입 방법을 부적절하게 사용하고 있는 사례를 다수 확인할 수 있었습니다. 대부분은 **생성자 주입**과 **필드 주입**의 차이점을 제대로 구분하지 못해서 발생한 것으로 보였습니다.

두 방법의 차이는 아래 표와 같이 정리할 수 있습니다.

| 특징 | 생성자 주입 | 필드 주입 |
| --- | --- | --- |
| 주입 시점	| 	객체 생성 시, 생성자에서 의존성 주입됨 | 객체 생성 후, 필드 초기화 시점에 의존성 주입됨 |
| 의존성 관리 |	의존성이 명확하게 주입되고, 생성자에서 초기화됨 | 의존성 주입 전에 변수 사용 시 예외 발생 가능 |
| 불변성 |	final 키워드를 사용하여 불변성 보장 | 불변성 보장되지 않음 |	
| 테스트 용이성	| 생성자 주입을 통해 의존성 주입이 명확하여 테스트가 용이 | 의존성 주입이 명확하지 않아서 테스트가 어려울 수 있음	 | 
| 컴파일 타임 검증	| 컴파일 시점에 의존성 누락 문제를 발견할 수 있음 | 의존성 주입 순서나 누락에 대한 검증이 어려움	 | 

### 3. 부적절한 의존성 주입 사용 사례

저희 팀의 경우에는 의존성 주입이 적합한 상황에도 불구하고, 필드 주입이 사용되고 있는 사례가 많았습니다. 아래 코드에서는 필드 주입을 사용하고 있습니다.

**잘못된 코드**

```java
public class SomeService {
    @Autowired
    private SomeDependency someDependency;

    private String name = someDependency.getName();  // 의존성 주입 전에 사용됨
}
```

필드 주입을 사용하면 객체가 생성된 후에 의존성이 주입됩니다. 의존성 주입 순서는 보장되지 않습니다. 그렇기 때문에, name을 선언하는 시점에는 someDependency의 의존성 주입 여부가 불확실합니다. someDependency에 의존성이 주입되지 못한 상태에서 getName() 메소드가 호출되면 **NullPointerException**이 발생할 수 있습니다. 

이 문제를 해결하기 위해서 아래 코드처럼, 생성자 주입 방식을 사용할 수 있습니다.

**수정된 코드**

```java
public class SomeService {
    private final SomeDependency someDependency;
    private final String name;

    @Autowired
    public SomeService(SomeDependency someDependency) {
        this.someDependency = someDependency;
        this.name = someDependency.getName();  // 생성자에서 의존성 주입 후 초기화
    }
}
```

someDependency는 생성자에서 의존성 주입이 이루어지고, 그 후에 name 변수를 초기화하므로 NullPointerException을 방지할 수 있습니다. 또한, final 키워드를 사용하여 someDependency와 name을 초기화 후 변경할 수 없게 만듭니다. 이로 인해 객체가 **불변성(Immutable)**을 가지게 되어, 상태가 변경되지 않음을 보장할 수 있습니다.

생성자 주입은 의존성 주입이 명확하게 드러나므로 테스트 코드에서 필요한 가상의 Mocking 객체를 주입하기도 용이합니다.

### 4. 결론

생성자 주입 방식은 의존성 주입 후 변수 초기화를 보장하고, 불변성을 유지하며, 컴파일 타임에 의존성 문제를 해결할 수 있는 강력한 방식입니다. 반면, 필드 주입 방식은 의존성이 주입되기 전에 필드를 사용할 가능성이 있어 예기치 않은 오류가 발생할 수 있습니다.

따라서, 일반적인 경우에는 의존성 주입을 사용할 때는 생성자 주입 방식을 사용하는 것이 바람직합니다. 그리고 필드 주입 방식은 예외적인 경우에만 사용해야 합니다.

✔ 기본 원칙
* 비즈니스 로직을 가진 핵심 클래스 → 생성자 주입
* 초기화 순서가 중요 → 생성자 주입
* 불변 객체 → 생성자 주입

✔ 예외적으로 필드 주입을 사용
* 테스트 코드
* 선택적 의존성
* 단순 어댑터 / 설정 / 레거시 코드
