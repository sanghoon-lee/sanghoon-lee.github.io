최근 소프트웨어 개발에서 보안의 중요성은 점점 더 커지고 있습니다. 개인정보 유출과 같은 보안 사고가 지속적으로 발생하면서, 데이터를 안전하게 보호하기 위해 암호화는 이제 선택이 아니라 필수적인 요소가 되었습니다.

이러한 흐름 속에서 대칭키 암호화 알고리즘인 AES는 사실상 표준처럼 사용되고 있습니다. 다양한 라이브러리와 플랫폼에서 **AES**를 기본 알고리즘으로 지원하고 있습니다.

하지만, **AES** 알고리즘을 사용한다고 해서 무조건 안전하다고 할 수 있을까요?

---

## 1. 대칭키 알고리즘의 암호화 모드

**AES**는 데이터를 일정한 크기의 블록 단위로 나누어 암호화하는 블록 암호(Block Cipher) 방식의 알고리즘입니다. 

여러 개로 나눠진 데이터 블록을 어떤 방식으로 암호화할지 결정하는 것이 바로 **암호화 모드(Mode of Operation)** 입니다.

암호화 모드는 단순한 구현 방식의 차이가 아니라, 보안 수준과 특성을 결정짓는 중요한 요소입니다.

대표적으로 사용되는 암호화 모드에는 ECB, CBC, GCM 등이 있습니다. 이 모드들은 시간의 흐름에 따라 점진적으로 발전해 왔습니다.

---

### 1.1. ECB 모드

가장 단순한 방식은 ECB(Electronic Codebook) 모드입니다.

ECB는 각 블록을 독립적으로 암호화하는 방식으로, 동일한 평문 블록은 항상 동일한 암호문 블록으로 변환됩니다. 

```nohighlight
[ P1 ] → AES → [ C1 ]
[ P2 ] → AES → [ C2 ]
[ P3 ] → AES → [ C3 ]
[ P4 ] → AES → [ C4 ]

P1~4: PlainText Block
C1~4: Ciphered Block(Result)
```

구현이 단순하다는 장점이 있지만, 데이터의 패턴이 그대로 노출되는 치명적인 문제가 있습니다.

---

### 1.2. CBC 모드

이러한 문제를 개선하기 위해 등장한 방식이 CBC(Cipher Block Chaining) 모드입니다.

CBC 모드에서는 이전 블록의 암호화 결과를 다음 블록에 반영하는 방식으로 같은 데이터라도 서로 다른 암호문을 생성합니다. 이로 인해 ECB 모드에서 발생하던 패턴 노출 문제는 해결할 수 있었습니다.

```nohighlight
IV(Initial Vector)
   ↓
[ P1 ] ⊕ IV  → AES → [ C1 ]
[ P2 ] ⊕ C1  → AES → [ C2 ]
[ P3 ] ⊕ C2  → AES → [ C3 ]
[ P4 ] ⊕ C3  → AES → [ C4 ]

P1~4: PlainText Block
C1~4: Ciphered Block(Result)
```

하지만 CBC 모드 역시 한계를 가지고 있습니다.

암호화 자체는 안전하지만 데이터의 위·변조를 검증하는 기능은 제공하지 않습니다. 따라서 무결성을 보장하기 위해서는 MAC(Message Authentication Code)이 별도로 필요합니다. (예: HMAC과 같은 방식)

그리고 구현 방식에 따라 Padding Oracle Attack과 같은 보안 취약점이 발생할 수 있습니다.

---

### 1.3. GCM 모드

GCM 모드는 데이터를 암호화하면서 무결성까지 함께 보장할 수 있는 AEAD(Authenticated Encryption with Associated Data) 방식입니다. 

즉, 암호화된 데이터의 위·변조 여부까지 확인할 수 있기 때문에 현대의 보안 요구사항을 충족하는 방식이라고 볼 수 있습니다.

또한 병렬 처리가 가능해 성능 측면에서도 유리합니다. 이런 이유로 현재는 TLS와 같은 주요 보안 프로토콜에서도 기본으로 사용되고 있습니다.

```nohighlight
Nonce (Initial Value for Counter)
   ↓
Counter Mode (암호화)
[ CTR1 ] → AES → [ K1 ] ⊕ [ P1 ] → [ C1 ]
[ CTR2 ] → AES → [ K2 ] ⊕ [ P2 ] → [ C2 ]
[ CTR3 ] → AES → [ K3 ] ⊕ [ P3 ] → [ C3 ]
[ CTR4 ] → AES → [ K4 ] ⊕ [ P4 ] → [ C4 ]
           ↓

Authentication (무결성 검증)
[ C1, C2, C3, C4 ] → GHASH → Authentication Tag

CTR1 = Nonce + 1
CTR2 = Nonce + 2
CTR3 = Nonce + 3
CTR4 = Nonce + 4

K1 = AES(Key, CTR1)
K2 = AES(Key, CTR2)
K3 = AES(Key, CTR3)
K4 = AES(Key, CTR4)

Nonce: Number used once
P1~4: PlainText Block
C1~4: Ciphered Block(Result)
```

GCM은 데이터를 직접 암호화하는 방식이 아니라, AES를 이용해 키스트림(K1~K4)을 생성한 뒤 평문(P1~P4)과 XOR하는 방식으로 동작합니다. 

이때 CTR 값은 AES의 입력으로 사용되며, AES의 출력으로 생성된 키스트림이 실제 암호화에 사용됩니다.

> GCM → `✅ 암호화 + 무결성 보장(현대 표준)`

---

### 1.4. 암호화 모드 선택의 중요성

이처럼 같은 동잃한 알고리즘을 사용하더라도 어떤 암호화 모드를 선택하느냐에 따라 보안 수준은 크게 달라집니다. 

즉, 암호화 알고리즘 자체보다 암호화 모드 선택이 보안 수준을 결정한다고 볼 수 있습니다.

| 항목 | ECB | CBC | GCM |
|------|-----|-----|-----|
| 보안성 | ❌ 매우 낮음 | ⚠️ 보통 | ✅ 높음 |
| 패턴 노출 | 있음 | 없음 | 없음 |
| 무결성 검증 | 없음 | 없음 | 있음 |
| 병렬 처리 | 가능 | 불가능 | 가능 |
| 실무 권장 | ❌ 사용 금지 | ⚠️ 제한적 | ✅ 권장 |

과거에는 CBC 모드가 표준적인 선택이었지만 현재는 무결성까지 함께 보장되는 GCM 모드가 사실상의 표준으로 자리잡고 있습니다.

---

## 2. CBC 모드의 IV와 GCM 모드의 Nonce 비교

CBC 모드의 IV와 GCM 모드의 Nonce가 비슷한 개념처럼 보일 수 있습니다. 실제로 두 값 모두 암호화 과정에서 초기값으로 사용된다는 공통점이 있습니다. 

하지만 중요한 차이가 있습니다.

---

### 2.1. CBC 모드의 IV(Initial Vector)

CBC 모드에서 IV는 첫 번째 블록을 암호화할 때 사용되는 초기값입니다.

```nohighlight
C1 = AES(P1 ⊕ IV)
```

IV의 가장 중요한 요구사항은 **예측 불가능성(Randomness)** 입니다. 같은 평문이라도 다른 암호문이 생성되도록 하기 위해 매번 랜덤하게 생성해야 합니다.

IV가 재사용되면 즉시 암호화가 깨지는 수준의 문제로 이어지지는 않지만, 보안성이 약해질 수 있습니다. 

하지만 많은 개발자들이 이런 개념을 정확하게 인지하지 못하고 IV를 동일한 값으로 재사용하는 경우가 실무에서도 자주 보이는 편입니다.

---

### 2.2. GCM 모드의 Nonce

GCM 모드에서는 Nonce는 카운터의 시작값으로 사용됩니다.

```nohighlight
Counter Block = Nonce + Counter

CTR1 = Counter Block(1)
CTR2 = Counter Block(2)
...
```

이 값은 AES의 입력으로 사용되어 키스트림을 생성하는 데 사용됩니다. GCM 모드에서 가장 중요한 요구사항은 **유일성(Uniqueness)** 입니다. 

즉, 같은 키에서 동일한 Nonce를 절대 재사용해서는 안 됩니다. 같은 키에서 동일한 Nonce가 재사용되면 동일한 키스트림이 생성되기 때문입니다. 

그렇게 되면 키스트림과 평문 간의 관계가 그대로 노출되는 치명적인 문제가 발생합니다. 즉, 암호문만으로도 평문 정보를 유추할 수 있게 됩니다.

---

### 2.3. 핵심 차이 요약

| 항목 | CBC (IV) | GCM (Nonce) |
|------|----------|-------------|
| 역할 | 첫 블록 랜덤화 | 카운터 시작값 |
| 요구 조건 | 랜덤 (예측 불가) | 유일 (중복 금지) |
| 재사용 | 가능하지만 위험 | ❌ 절대 금지 |
| 영향 | 패턴 노출 가능 | 암호화 자체 붕괴 |


IV와 Nonce를 동일하게 생각할 수 있지만, 실제로는 보안 요구사항이 완전히 다른 개념입니다. 

CBC의 IV와 GCM의 Nonce는 모두 초기값이라는 공통점을 가지고 있습니다. 하지만 CBC 모드에서는 랜덤성이 중요하고, GCM 모드에서는 유일성이 더 중요합니다. 

특히 GCM에서는 Nonce 재사용이 치명적인 보안 문제로 이어질 수 있기 때문에, 실무에서는 Nonce 관리에 각별한 주의가 필요합니다.

---

## 3. GCM 모드의 장점

GCM 모드는 현대 보안 요구사항을 반영한 실무 중심의 암호화 표준이라고 볼 수 있습니다. 

따라서 특별한 이유가 없다면 대칭키 암호화에서는 GCM 모드를 사용하는 것이 가장 안전한 선택지가 됩니다. 

구체적으로 GCM 모드의 장점은 다음과 같습니다.

---

### 3.1. 암호화와 무결성을 동시에 제공 (AEAD)

CBC 모드에서는 무결성을 보장하기 위해서 별도로 MAC(Message Authentication Code)을 구성해야 했지만, GCM 모드를 사용하면 데이터의 기밀성과 무결성을 동시에 보장할 수 있습니다.

이로 인해 구현이 단순해지고, 잘못된 구성으로 인한 보안 취약점 발생 가능성도 줄어듭니다.

---

### 3.2. 높은 성능 (병렬 처리 가능)

GCM은 CTR(Counter) 모드를 기반으로 동작하기 때문에 블록 간 의존성이 없습니다.

따라서 여러 블록을 동시에 처리할 수 있어 병렬 처리가 가능합니다. 특히 하드웨어 가속(AES-NI)과 함께 사용할 경우 매우 높은 성능을 제공합니다. 

이는 대량의 데이터를 처리해야 하는 환경에서 큰 장점이 됩니다.

---

### 3.3. 현대 보안 표준에서의 채택

GCM은 현재 주요 보안 표준에서 기본적으로 사용되고 있습니다.

대표적으로 TLS 1.3 표준에서는 CBC 기반 암호화가 제거되고 GCM 모드와 같은 AEAD 방식이 기본으로 사용됩니다. 

이는 GCM 모드가 단순한 대안이 아니라, 현대 보안 환경에 최적화된 사실상의 표준이라는 것을 의미합니다.

---

### 3.4. 구현 실수 가능성 감소

CBC 모드를 안전하게 사용하기 위해서는 암호화와 MAC을 올바른 순서로 결합(Encrypt-then-MAC)해야 합니다. 하지만 이러한 구성은 구현 난이도가 높고, 실수로 인해 취약점이 발생할 가능성이 존재합니다.

GCM 모드에서는 이러한 과정이 내부적으로 처리되기 때문에 개발자가 보안 구성을 잘못할 가능성을 줄여듭니다.
