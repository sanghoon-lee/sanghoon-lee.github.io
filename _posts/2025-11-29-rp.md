이번주 제가 소속된 개발팀에서 운영과 유지보수를 담당하고 있는 서비스의 인프라 구성을 변경했습니다. DMZ에 배치되어 있던 API게이트웨이를 TrustZone으로 이전하는 것이 핵심으로 장기간 누적되어 있던 기술부채를 청산하는 의미도 있었습니다. 

## 1. 작업 필요성

인프라 구성을 변경하는 작업을 실시하기 전에는 서비스의 운영 관점에서 다음과 같은 문제가 보였습니다.

* 보안 설정 관리의 복잡성 증가 : 12대의 API 게이트웨이 서버가 DMZ에서 운영되고 있었는데, 각각의 서버마다 보안 설정을 개별적으로 적용해야 했습니다. 작업자의 실수로 설정이 누락되거나 불일치하는 상황이 발생할 수 있었고, 설정 변경에 많은 시간이 소요되었습니다. 
* 보안 취약점 노출 : DMZ는 외부에 개방된 구간으로 API 게이트웨이가 이곳에 배치되면 불필요하게 공격 표면이 넓어질 수 있습니다.

## 2. 작업 목표와 방법

문제를 해결하기 위해서 사내 인프라팀과 협의하여 수립한 작업 목표는 다음과 같았습니다.

> "DMZ는 최소한의 기능만 담당하고, API 게이트웨이는 TrustZone으로 이동시켜 보안을 강화하고, 관리 효율성의 향상을 기대"

목표를 달성하기 위해 제시된 방법은 다음과 같습니다.

* RP(Reverse Proxy)를 DMZ에 배치하여 외부 요청을 받아 TrustZone으로 이동한 API 게이트웨이에 전달하도록 인프라 구성을 변경
* 인프라 구성 변경 후, API 게이트웨이의 보안 설정은 TrustZone 내부에서 일원화

## 3. 작업 내용

1. RP 서버 구축 및 트래픽 라우팅
* DMZ에 Nginx 서버를 설치하고, RP로 활용
2. API 게이트웨이 이동
* API 게이트웨이와 API 서버가 안전한 내부 보안 영역에서 연동될 수 있도록 DMZ에 배치되어 있는 API 게이트웨이를 TrustZone으로 이동
3. 보안 정책 통합
* 모든 API 요청에 대해서 일관된 보안 정책이 적용될 수 있도록 TrustZone 내부에서 일원화하여 관리

## 4. 인프라 구성

### 4.1. 작업 전

```
+-----------------------+
|     Client (Browser)  |          <-- 외부에서 서비스 호출
+-----------------------+
            |
            v
+-----------------------+
|      API Gateway      |          <-- DMZ 영역에서 운영 (API 요청 처리)
|         (DMZ)         |
+-----------------------+
            |
            v
+-----------------------+
|      API Server       |          <-- TrustZone에서 서비스 비즈니스 처리
|      (TrustZone)      |
+-----------------------+

```
### 4.2. 작업 후

```
+-----------------------+
|     Client (Browser)  |          <-- 외부에서 서비스 호출
+-----------------------+
            |
            v
+-----------------------+
|      RP Server        |          <-- DMZ 영역에 배치 (요청 라우팅 및 보안 강화)
|        (DMZ)          |
+-----------------------+
            |
            v
+-----------------------+
|      API Gateway      |        <-- TrustZone으로 이동 (보안 강화 및 관리 일원화)
|      (TrustZone)      |
+-----------------------+
            |
            v
+-----------------------+
|      API Server       |          <-- TrustZone에서 서비스 비즈니스 처리
|      (TrustZone)      |
+-----------------------+

```
## 5. 기대효과

### 5.1. 보안성 강화
* DMZ 역할을 최소 기능으로 단순화 → 공격 표면 축소  
* 보안 정책 일원화 → 보안 설정의 일관성과 효율성을 보장

### 5.2. 운영 효율성 증가
* 작업 단순화 → 모든 보안 정책 적용과 배포 작업이 TrustZone 내에서만 이루어지기 때문에, 작업속도가 빠름(이전처럼 여러 서버에 개별 적용할 필요 없음)
* 정애대응 속도 향상 → 모든 API 요청이 TrustZone 내에서만 처리되므로, 모니터링이 용이

## 6. 용어설명

1. API 게이트웨이 : 여러 내부 서비스들을 외부에서 하나의 앤드포인트로 접근할 수 있도록 함으로써, 클라이언트와 서버 간 통신을 단순화
2. RP : 클라이언트의 요청을 받아 내부 서버로 전달하는 중계 서버
