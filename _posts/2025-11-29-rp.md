이번주 회사에서 운영되고 있는 서비스의 인프라 구성을 변경하는 작업을 수행했습니다. 

DMZ에 배치되어 있던 API 게이트웨이를 TrustZone으로 이전하는 것이 핵심 내용으로 장기간 누적되어 있던 기술부채를 청산하는 의미도 있었습니다. 

<img class="main-image" src="/assets/images/network.png" alt="네트워크 이미지">

---

## 1. 작업 필요성

서비스의 운영 관점에서 다음과 같은 문제가 있었습니다.

---

### 1.1. 보안 설정 관리의 복잡성 증가 

다수의 API 게이트웨이가 DMZ에서 운영되고 있었는데, 각각의 게이트웨이마다 보안 설정을 개별적으로 적용해야 했습니다. 

작업자의 실수로 설정이 누락되거나 불일치하는 상황이 발생할 수 있었고, 설정 변경에 많은 시간이 소요되기도 했습니다. 

---

### 1.2. 보안 취약점 노출

DMZ는 외부와 접점이 있는 영역으로 API 게이트웨이가 이곳에 배치되면서 불필요하게 공격 표면이 넓어지게 되었습니다.

---

## 2. 작업 목표

문제를 해결하기 위해서 수립한 작업 목표는 다음과 같았습니다.

> "API 게이트웨이는 DMZ에서 TrustZone으로 이동시켜 보안을 강화하고, 관리 효율성의 향상을 기대"

먼저, DMZ에 RP(Reverse Proxy)를 배치했습니다. 그리고 API 게이트웨이를 TrustZone으로 이전했습니다. 

이제 외부의 요청은 API 게이트웨이가 아닌 RP가 받아서 API 게이트웨이로 전달하는 구조가 되었습니다.

이렇게 함으로써 API 게이트웨이와 API 서버에 대한 공격 표면을 좁히면서, TrustZone 내부에서 보안 정책을 일원화하여 관리할 수 있게 되었습니다.

---

## 3. 인프라 구성

### 3.1. 작업 전

```text
+-----------------------+
|    Client(Internet)   |          
+-----------------------+
            |
            v
+-----------------------+
|      API Gateway      |          
|         (DMZ)         |
+-----------------------+
            |
            v
+-----------------------+
|      API Server       |          
|      (TrustZone)      |
+-----------------------+

```
---

### 3.2. 작업 후

```text
+-----------------------+
|     Client(Internet)  |         
+-----------------------+
            |
            v
+-----------------------+
|      RP Server        |          <-- 요청 라우팅 및 보안 강화
|        (DMZ)          |
+-----------------------+
            |
            v
+-----------------------+
|      API Gateway      |          <-- 보안 강화 및 관리 일원화
|      (TrustZone)      |
+-----------------------+
            |
            v
+-----------------------+
|      API Server       |          
|      (TrustZone)      |
+-----------------------+

```

---

## 4. 기대효과

**보안성 강화**

* DMZ 역할을 최소 기능으로 단순화 → 공격 표면 축소  
* 보안 정책 일원화 → 보안 설정의 일관성과 효율성을 보장

**운영 효율성 증가**

* 작업 단순화 → 모든 보안 정책 적용과 배포 작업이 TrustZone 내에서만 이루어지기 때문에, 작업속도가 빠름(이전처럼 여러 서버에 개별 적용할 필요 없음)
* 장애대응 속도 향상 → 모든 API 요청이 TrustZone 내에서만 처리되므로, 모니터링이 용이
